§1Зачем искать target

Сравнение из жизни
Список смены

Охрана не переписывает инструкцию, когда меняется смена. Она смотрит список дежурных на сегодня.

Service discovery

Prometheus не правит настройки, когда меняются копии сервиса. Он читает текущий список target.

До сих пор target были записаны прямо в prometheus.yml блоком static_configs. Для новой копии сервиса нужно править файл и перезагружать настройки, а остановленная копия остаётся в списке и висит в состоянии DOWN. Поиск target (service discovery) убирает эту ручную работу: Prometheus сам берёт список из внешнего источника. Самый простой источник — файл.

§3Изменение без перезапуска

Опыт: в проекте запущена вторая копия сервиса, api2. В 15:15:22 её адрес дописан в файл. Скрипт раз в секунду спрашивал Prometheus, сколько у него target, и второй появился через 2 секунды. Перезапуска и перезагрузки настроек не было.

Prometheus следит за файлами и применяет изменения сразу. Кроме того, он перечитывает их по таймеру refresh_interval, по умолчанию раз в 5 минут, — на случай, если файловая система не сообщает об изменениях.

Удаление работает так же. Адрес api2 убран из файла — через 5 секунд target исчез со страницы Target health, а запрос up{job="orders"} вернул один ряд вместо двух. Ряды пропавшего target Prometheus помечает устаревшими, как ряд, исчезнувший из ответа (глава 2.4). Висящего DOWN, как со static_configs, не остаётся.

§4Метки, найденные вместе с target

Вместе с адресом Prometheus получает о target служебные метки. Их видно на странице Status → Service discovery: слева — всё, что найдено, справа — что осталось у target.

Слева восемь меток. Те, что начинаются с __, служебные: __address__ — куда идти за метриками, __meta_filepath — из какого файла пришёл target. Справа их нет: после поиска Prometheus отбрасывает все метки с __, а __address__ превращает в instance. Метка env из файла дошла до target и будет у всех его рядов. Как управлять этим переходом слева направо — тема главы 4.3.

§6Другие источники списка

Файл — самый простой источник. Prometheus умеет спрашивать список и у систем, которые сами знают, что запущено: Kubernetes (kubernetes_sd_configs), Consul, Docker, облака EC2 и других. Устроены они одинаково: источник отдаёт адреса и служебные метки __meta_*, например имя пода или контейнера, а дальше работают те же правила, что в §4. Для системы без готового источника пишут скрипт, который сохраняет список в файл, как в §5.

§7Проверьте себя

Вопрос 1В файл file_sd_configs дописан адрес новой копии сервиса. Что нужно сделать, чтобы Prometheus начал её опрашивать?

  • Не нужно: в опыте target появился через 2 секунды без перезапуска.

  • Верно. Prometheus следит за файлами и применяет изменения сразу.

  • Таймер — запасной путь на случай, когда слежение за файлами не работает.

Вопрос 2Скрипт записал в файл список с ошибкой в JSON. Что будет с target задания?

  • Prometheus оставляет последний правильный список.

  • Верно. Растёт и prometheus_sd_file_read_errors_total.

  • Ошибка в файле поиска не останавливает Prometheus.

Вопрос 3Будет ли у рядов target метка __meta_filepath?

  • На странице Service discovery её нет в правом столбце.

  • Верно. Остаются env, instance и job.

Вопрос 4Зачем скрипт пишет файл под другим именем и подменяет его через os.replace?

  • Верно. Подмена происходит за один шаг.

  • Старая версия при подмене исчезает.

  • Формат здесь ни при чём: дело в моменте чтения.
