§1Задача короче опроса

Сравнение из жизни
Записка на вахте

Ночной мастер уходит до прихода начальника, поэтому оставляет на вахте записку: что сделал и когда.

Pushgateway

Задача завершается до опроса, поэтому оставляет метрики в Pushgateway, а Prometheus забирает их оттуда.

Ночной отчёт в проекте строится 3 секунды, Prometheus опрашивает раз в 15. Даже если бы у задачи была страница /metrics, опрос почти всегда приходил бы, когда задача уже завершилась. Pushgateway — отдельная программа, которая принимает метрики по push и хранит их до удаления. Prometheus опрашивает Pushgateway через pull-модель.

Путь метрик пакетной задачи
0 сЗадача запускаетсястарт
3 сОтчёт готов, процесс завершёнрезультат
до 15 сPushgateway хранит отправленные рядысохранение
опросPrometheus забирает рядыpull
Числа показывают причину: трёх секунд работы недостаточно для гарантированного попадания под 15-секундный опрос.

На схеме процесс задачи заканчивается раньше следующего опроса. Отправка переносит результат в отдельный сервис, а Prometheus продолжает использовать pull-модель. Теперь посмотрим, какие ряды задача отправляет.

§2Отправка из Python

Задача складывает метрики в свой реестр и в самом конце отправляет его функцией push_to_gateway:

Отдельный CollectorRegistry нужен, чтобы отправить только метрики задачи, без метрик процесса Python. Параметр job задаёт группу: следующая отправка с тем же job заменит её целиком. Что теперь лежит в Pushgateway:

Что отправляется и что добавляет Pushgateway
registryreport_rows, report_duration_seconds, report_last_success_timestamp_seconds3 ряда задачи
push_to_gatewayjob = nightly_reportгруппа
Pushgatewaypush_time_seconds и push_failure_time_seconds2 служебных ряда
/metrics5 рядов с job = nightly_reportответ
Собственный реестр ограничивает отправку тремя рядами задачи. Pushgateway добавляет два ряда о попытках отправки.

На схеме слева находятся три значения отчёта, справа — два значения Pushgateway. Следующий шаг — подключить этот ответ к опросу Prometheus.

Три метрики задачи и две от Pushgateway. push_time_seconds — время последней отправки группы. push_failure_time_seconds — время последней неудачной отправки. Нулевое значение означает, что неудач не было. Значение report_rows здесь от первого запуска; второй дал 955.

§3Prometheus опрашивает Pushgateway

Метки job у рядов Pushgateway — это имя задачи. Обычный опрос поставил бы вместо него имя задания Prometheus, а имя задачи сохранил бы в exported_job (глава 2.2). Чтобы оставить метки как есть, в задании пишут honor_labels: true. В опыте Pushgateway опрашивают два задания — с этим параметром и без:

С honor_labels у ряда job="nightly_report", и пустой instance из отправки пропал — пустая метка равна отсутствию метки (глава 3.3). Без него ряд записан на задание Pushgateway. Ряд up в обоих случаях относится к Pushgateway, о самой задаче он ничего не говорит.

Два результата одного опроса
отправкаjob = nightly_reportметка задачи
honor_labelsjob = nightly_reportсохранить
без honorjob = pushgateway-bez-honor
exported_job = nightly_reportпереименовать
upв обоих вариантах относится к Pushgatewaytarget
Параметр меняет метки рядов задачи. Он не превращает up в признак успешного запуска пакетной задачи.

Схема разделяет две проверки: метки описывают происхождение ряда, а up — доступность сервиса Pushgateway. Для пакетной задачи понадобится отдельная отметка времени.

§4Метрики живут после задачи

Сервис Pushgateway отдаёт метрики группы при каждом опросе после завершения задачи. Отметка «устарел» из главы 4.6 к этим рядам не приходит. Через 21 минуту после второго запуска:

Поэтому значение report_rows само по себе не показывает свежесть. Если задача перестанет запускаться, число 955 останется в хранилище. Задача отправляет момент последнего успеха, а запрос проверяет его возраст: второй запрос показывает, что успех был 1 257 секунд назад. Для ночной задачи тревожный порог — больше суток.

Само значение report_rows не показывает свежесть. Её проверяют по возрасту отметки последнего успеха.

§5Когда Pushgateway не нужен

Документация Prometheus рекомендует Pushgateway для пакетных задач уровня сервиса, которые не привязаны к конкретной машине. Для долгоживущего сервиса этот способ создаёт ложную картину доступности. Ряды не устаревают, поэтому после остановки сервиса последнее значение остаётся в хранилище. Отдельного up для каждой копии такого сервиса нет. Сам Pushgateway становится точкой, через которую проходят метрики всех задач. Для задачи по расписанию на одной машине подходит сборщик textfile из node_exporter: задача пишет файл с метриками, node_exporter отдаёт его при опросе.

Способ выбирают по времени жизни и принадлежности задачи. Для постоянно работающего сервиса прямой опрос сохраняет признак сбоя.

Схема связывает три варианта с условиями применения. Вопросы ниже проверяют, отличаете ли вы доступность Pushgateway от свежести результата задачи.

§6Проверьте себя

Вопрос 1Ночная задача перестала запускаться неделю назад. Что показывает report_rows?

  • Верно. Pushgateway хранит группу, пока её не удалят.

  • Отметка «устарел» к метрикам Pushgateway не приходит.

  • Значение не меняется само.

Вопрос 2Как проверить, что задача отработала за последние сутки?

  • up говорит о Pushgateway, а не о задаче.

  • Верно. Задача отправляет момент успеха, проверяют его возраст.

  • Старое значение больше нуля и через неделю.

Вопрос 3В задании опроса Pushgateway нет honor_labels. Какой job будет у метрик задачи?

  • Это значение уйдёт в exported_job.

  • Верно. В опыте — pushgateway-bez-honor.

Вопрос 4Нужно собирать метрики веб-сервиса, который работает постоянно. Подходит ли Pushgateway?

  • Ряды не устареют, и упавший сервис будет выглядеть живым.

  • Верно. Pushgateway — для пакетных задач.
