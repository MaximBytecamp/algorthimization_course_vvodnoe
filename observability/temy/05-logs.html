§1Лог: запись о событии

Из главы 1.4 мы знаем, что метрика сообщает масштаб: за пять минут 5% запросов вернули ошибку. Но какая это ошибка, у каких запросов и в какой строке кода она возникла, метрика не сохраняет. Для этого нужна запись о каждом событии.

Лог (журнал событий) — последовательность записей о событиях, произошедших в программе. Каждая запись фиксирует, когда что-то произошло, где и с каким результатом.

Событием может быть что угодно: завершение HTTP-запроса, вход пользователя, неудачная попытка подключения к базе, запуск фоновой задачи. Разработчик сам решает, какие события записывать, и от этого решения зависит, что удастся выяснить при расследовании.

Сравним две записи об одном и том же запросе.

Первая строка сообщает только, что выполнение дошло до вызова логирования. Неизвестно, когда это было, какой запрос обработан и успешно ли. Если за минуту таких строк тысяча, связать хотя бы одну с жалобой пользователя невозможно.

Во второй строке есть ответы на вопросы, которые возникают при расследовании: время, уровень важности, сервис, тип события, маршрут, результат, длительность и идентификатор запроса. По идентификатору эту запись можно найти, получив его от пользователя.

§2Какие поля нужны записи

Состав полей определяется вопросами, на которые должна отвечать запись. Для веб-сервиса набор почти всегда один и тот же. Ниже запись учебного сервиса о запросе, завершившемся ошибкой. Выберите поле, чтобы прочитать, что оно даёт.

Запись о событии по полям
{"timestamp": "2026-09-15T13:07:57.857556+00:00", "level": "ERROR",
 "service": "products-api", "event": "request_completed", "status": 500,
 "request_id": "b5408f2265bb49168b4bdfbec2bc0dc7", "duration_ms": 72.936}

Выберите поле, чтобы увидеть, на какой вопрос оно отвечает и чего не гарантирует.

ПолеНа какой вопрос отвечаетПример
timestampКогда произошло событие2026-09-15T13:07:57.857556+00:00
levelНасколько событие важноERROR
serviceКакой компонент создал записьproducts-api
eventЧто произошлоrequest_completed
route, statusКакая операция и с каким результатом/products, 500
duration_msСколько длилась операция и в каких единицах72.936
request_idК какому запросу относится записьb5408f2265bb49168b4bdfbec2bc0dc7

Отдельно скажем о единицах. Поле duration со значением 72 допускает несколько трактовок: секунды, миллисекунды, микросекунды. Если единица записана в имени поля, как в duration_ms, ошибиться невозможно. Время события записывается в UTC с явным смещением +00:00, чтобы записи с разных серверов сравнивались без пересчёта.

В рабочих сервисах к этому набору добавляют версию приложения и имя экземпляра. Без версии нельзя понять, появилась ли ошибка после выпуска. Без экземпляра нельзя заметить, что сбоит только один сервер из трёх.

§3Уровни важности

У каждой записи есть уровень важности. Он позволяет отфильтровать поток: в обычной работе смотреть только предупреждения и ошибки, а при отладке включать подробные сообщения. В модуле logging Python пять стандартных уровней, у каждого есть числовое значение.

УровеньЧислоКогда использоватьПример
DEBUG10Подробности для отладки, которые в рабочей среде обычно выключеныЗначения параметров запроса к базе
INFO20Обычные события, подтверждающие работуЗапрос обработан, задача запущена
WARNING30Что-то пошло не так, но операция выполненаЗапрос длился дольше порога, выполнен повтор
ERROR40Операция не выполненаИсключение при обращении к зависимости
CRITICAL50Приложение не может продолжать работуНе удалось прочитать обязательную настройку при запуске

Логгер пропускает записи, уровень которых не ниже заданного. Если установить уровень INFO, записи DEBUG отбрасываются, а INFO, WARNING, ERROR и CRITICAL проходят. Сравнение идёт по числу, поэтому уровни можно задавать и своими значениями, хотя обычно хватает стандартных.

Уровень не показывает масштаб

Одна запись ERROR сообщает о сбое одной операции. Одинаковые записи ERROR могут появляться раз в месяц или в каждом запросе. Чтобы понять, насколько проблема серьёзна, число ошибочных событий сравнивают с числом всех операций за тот же интервал.

§4Модуль logging в Python

Для записи логов в Python есть стандартный модуль logging. Им пользуется и учебный сервис, и сам Uvicorn. Разберём минимальную настройку на отдельном примере.

Разберём программу по частям.

  • logging.basicConfig настраивает корневой логгер: куда писать и в каком виде. Без аргументов записи идут в стандартный поток ошибок.
  • level=logging.INFO задаёт порог. Поэтому строка debug в вывод не попала: её уровень 10 ниже порога 20.
  • format описывает шаблон строки. %(asctime)s — время, %(levelname)s — уровень, %(name)s — имя логгера, %(message)s — текст.
  • logging.getLogger("telemetry_lab") возвращает именованный логгер. Имя попадает в запись и показывает, какая часть программы её создала.
  • В logger.info значения переданы отдельными аргументами, а не через f-строку. Модуль подставит их в %s, только если запись пройдёт порог уровня.

Последний пункт важен для производительности. В записи logger.debug(f"данные: {big_object}") Python сначала построит строку, а потом логгер её отбросит, если DEBUG выключен. С отдельными аргументами строка не строится вовсе.

Время в выводе записано по местному времени машины и без часового пояса: 2026-09-15 16:17:58,865. Для одного компьютера это удобно, для нескольких серверов — нет. Учебный сервис поэтому формирует время события сам через datetime.now(timezone.utc).

§5Структурированные записи в JSON

Строка status=200 duration_ms=82.627 читается человеком, но программе её придётся разбирать. Если в тексте сообщения встретится пробел или знак равенства, разбор сломается. Поэтому в рабочих сервисах записи часто формируют в JSON: каждое поле становится ключом объекта.

Здесь запись собрана в словарь, а json.dumps превращает его в строку JSON. Параметр ensure_ascii=False оставляет русские буквы как есть, без замены на коды вида \u0442. В формате логгера оставлено только %(message)s, чтобы каждая строка вывода была корректным JSON.

Выгода проявляется при поиске. Системы хранения логов разбирают JSON на поля, и запрос «все записи, где status равен 500 и route равен /products» выполняется точно. С текстовыми строками пришлось бы писать регулярное выражение и надеяться, что формат сообщения нигде не отличается.

Формат JSON сам по себе запись не улучшает. Если в одном месте кода поле называется status, а в другом http_status, поиск по одному имени найдёт только половину записей. Имена и типы полей договариваются одинаковыми для всего сервиса.

Куда писать логи, в современных развёртываниях решают просто: в стандартный вывод процесса. Docker и Kubernetes собирают вывод каждого контейнера, а отдельный агент пересылает записи в хранилище. Приложению не нужно самому управлять файлами логов и их ротацией.

§6Исключение и traceback

Самые ценные записи при расследовании — записи об ошибках. Для них в логгере есть метод logger.exception, который добавляет к сообщению полный traceback текущего исключения.

Traceback — отчёт Python о цепочке вызовов, которая привела к исключению. Он показывает, в каком файле, строке и функции возникла ошибка и через какие вызовы выполнение туда пришло.

Traceback удобнее читать снизу вверх. Последняя строка называет тип исключения и сообщение: TimeoutError: dependency timeout. Над ней — место, где исключение возникло: файл, строка 8, функция load_products и сам код строки. Ещё выше — место вызова: строка 12, код верхнего уровня <module>. Так восстанавливается путь выполнения до ошибки.

Первая строка вывода — сообщение, которое мы передали в logger.exception. Метод всегда пишет запись уровня ERROR. Вызывают его только внутри блока except: вне обработки исключения traceback взять неоткуда.

В Python 3.12 traceback содержит абсолютный путь к файлу, например /home/deploy/app/log_exception.py. В журнал рабочего сервиса он попадёт вместе с устройством файловой системы сервера. Учебный сервис перед сохранением убирает путь к папке проекта и оставляет только имя файла.

§7Ошибка 500 на учебном стенде

Теперь посмотрим на настоящую ошибку. Запустим на странице стенда сценарий error. Обработчик ждёт зависимость, затем поднимает TimeoutError, перехватывает его, записывает событие и возвращает клиенту ответ 500.

Разберём снимок. Строка итога — HTTP 500 · клиент: 74.5 ms · обработчик: 72.9 ms. Ошибка вернулась быстрее, чем успешный быстрый ответ: этап serialize не выполнялся.

Блок HTTP показывает, что получил клиент: объект detail с кратким описанием simulated dependency timeout и request_id. Traceback клиенту не отправляется. Внутреннее устройство сервиса пользователю знать не нужно, а сведения о коде могут помочь злоумышленнику.

Блок LOG содержит полную запись. Уровень ERROR, код 500 и сценарий error. В поле exception — тот же traceback, что мы разобрали выше, только записанный в одну строку JSON: переносы строк заменены на \n. Прочитаем его снизу вверх: TimeoutError: Simulated dependency timeout; no database is connected возникла в файле app.py, строка 55, функция products.

Блок TRACE показывает только два этапа: validate — 11,1 мс и dependency.wait (simulated) — 61,1 мс. Третьего этапа нет, потому что исключение прервало выполнение до него.

Вся связка держится на request_id. Клиент получил b5408f2265bb49168b4bdfbec2bc0dc7 в ответе и в заголовке X-Request-ID. По этому значению разработчик найдёт запись с полным traceback, хотя у самого пользователя его нет.

Фрагмент кода показывает весь путь. traceback.format_exc() возвращает текст traceback текущего исключения в виде строки. Метод replace убирает из него путь к папке проекта. Строка попадает в поле exception записи, а logger.exception дополнительно выводит сообщение с traceback в терминал Uvicorn.

§8Можно ли считать метрики по логам

Раз в логах есть запись о каждом запросе, из них можно получить и количества. Возьмём файл events.json учебного прогона: в нём записи обо всех двадцати запросах.

Результат совпал с расчётом по CSV из главы 1.4. Так бывает, когда выполнены два условия: каждый запрос записан ровно один раз, и в записи есть нужное поле. В учебном сервисе оба условия выполняются: событие request_completed создаётся один раз в конце обработчика.

Пример

Почему нельзя просто посчитать строки с ERROR

Первый запрос трижды пытался обратиться к зависимости: две попытки завершились ошибкой, третья успешно. Каждая неудачная попытка записала строку ERROR. Второй запрос упал сразу, без повторов, и тоже записал ERROR.

Что считаемРезультат
Строк с уровнем ERROR3
Неуспешных попыток обращения к зависимости3
Неуспешных запросов1

Три числа отвечают на три разных вопроса. Чтобы по логам считать неуспешные запросы, нужно событие, которое пишется один раз на запрос и содержит итоговый статус.

Даже при правильных событиях считать метрики по логам дорого. Сервис с 1000 запросов в секунду и записью по 500 байт создаёт около 43 ГБ логов в сутки. Метрика с тем же смыслом занимает несколько рядов. Поэтому доли и длительности обычно считают метриками, а логи держат для подробностей.

§9Чего не должно быть в логах

Логи читают многие: разработчики, дежурные инженеры, иногда подрядчики. Их пересылают в отдельные системы и хранят месяцами. Поэтому в записи нельзя попадать данным, доступ к которым должен быть ограничен.

Нельзя записыватьПочемуЧто записать вместо
Пароли, токены, заголовок AuthorizationЛюбой читатель лога получит доступ к чужой учётной записиФакт успешной или неуспешной проверки
Полные номера банковских картТребования платёжных систем запрещают их хранение в открытом видеПоследние четыре цифры
Персональные данные: паспорт, адрес, телефонИх обработку регулирует закон, в России — 152-ФЗВнутренний идентификатор пользователя
Тело запроса целикомВ нём могут оказаться любые из перечисленных данныхРазмер тела и нужные для разбора поля

Лучше решать это при проектировании записи, а не после утечки. Удобный приём — перечислить поля, которые можно писать, вместо того чтобы запрещать отдельные. Тогда новое поле в запросе не попадёт в лог случайно.

§11Проверьте себя

Уровень логгера — WARNING. Какие из вызовов debug, info, warning, error попадут в вывод?

warning и error. Логгер пропускает записи с уровнем не ниже заданного: WARNING — 30, ERROR — 40, а DEBUG — 10 и INFO — 20 ниже порога.

В каком порядке удобно читать traceback и что находится в последней строке?

Снизу вверх. В последней строке тип исключения и сообщение, над ней — место, где оно возникло, выше — цепочка вызовов, которая туда привела.

Пользователь прислал снимок экрана с ошибкой 500 и значением request_id. Как найти причину?

Найти в хранилище логов запись с этим request_id. В ней уровень ERROR, маршрут и поле exception с traceback, которого у пользователя нет.

Почему на снимке сценария error в блоке TRACE только два этапа?

Исключение TimeoutError возникло после этапа dependency.wait и прервало выполнение блока try, поэтому этап serialize не выполнялся.

Один запрос выполнил два неудачных повтора и в итоге завершился успешно. Сколько неуспешных запросов он добавляет?

Ноль. Неуспешных попыток две, но итоговый результат запроса успешный.

§12Шпаргалка

  • Лог — последовательность записей о событиях: когда, где, что и с каким результатом.
  • Обязательные поля: время в UTC, уровень, сервис, событие, результат, длительность, идентификатор.
  • Уровни logging: DEBUG 10, INFO 20, WARNING 30, ERROR 40, CRITICAL 50.
  • Значения передают аргументами логгера, а не f-строкой.
  • JSON делает поля доступными для точного поиска; имена полей одинаковы во всём сервисе.
  • logger.exception внутри except добавляет traceback.
  • Traceback читают снизу вверх: исключение → место → цепочка вызовов.
  • Клиенту — краткое описание и request_id, в лог — полный traceback.
  • Число строк ERROR не равно числу неуспешных запросов.
  • Пароли, токены и персональные данные в лог не пишут.
