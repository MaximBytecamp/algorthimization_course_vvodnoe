1.8

Prometheus и Grafana: как метрики попадают на график

Проходим путь метрики сервиса от строки в /metrics до панели Grafana. По снимкам стенда разбираем, как Prometheus опрашивает приложение, как читать таблицу и график запроса и из чего состоит дашборд.

Главное в главе

Приложение отдаёт только текущие значения. Историю из них собирает Prometheus, который регулярно их читает.

§1Кто за что отвечает

В предыдущих главах мы разбирали, какие данные нужны для расследования. Теперь посмотрим на инструменты, которые эти данные собирают, хранят и показывают. Всё вместе часто называют «Grafana» или «мониторинг», но за каждый участок пути отвечает свой компонент.

Приложениесчитает и отдаёт /metrics
→
Prometheusопрашивает, хранит, считает PromQL
→
Grafanaзапрашивает и рисует панели

На стенде работают эти три компонента: API — обычный Python-процесс, Prometheus и Grafana — контейнеры Docker.

КомпонентЧто делаетЧего не делает
Приложение с инструментациейСчитает события и длительности, отдаёт текущие значения по адресу /metricsНе хранит историю: после перезапуска счётчики начинаются с нуля
PrometheusРегулярно опрашивает приложения, хранит временные ряды, выполняет запросы PromQL и проверяет правила оповещенияНе хранит логи и трассы; полноценные дашборды не рисует
GrafanaОтправляет запросы к источникам данных и показывает результаты панелямиСама метрики не собирает и не хранит
AlertmanagerПолучает сработавшие оповещения от Prometheus, группирует их и отправляет в почту или мессенджерУсловия оповещений не вычисляет
OpenTelemetryСоздаёт телеметрию в коде и передаёт её через Collector в хранилищаДанные не хранит и графики не строит

Дальше пройдём по пути одного числа: от строки кода, которая увеличивает счётчик, до цифры на панели Grafana.

§2Приложение отдаёт текущие значения

Ответ /metrics по строкам разобран в главе 1.4. Здесь посмотрим, как этот ответ формируется в коде.

ФрагментЧто делает
totalsСловарь с двумя счётчиками: {"200": ..., "500": ...}. Обработчик /products увеличивает нужный в конце каждого запроса
{{route=...}}Двойные фигурные скобки в f-строке выводят одинарные: так в тексте появляется {route="/products",status="200"}
include_in_schema=FalseПрячет адрес из Swagger: он нужен Prometheus, а не людям
Response(...)Возвращает строки обычным текстом в формате, который понимает Prometheus

Этот адрес возвращает только текущее состояние счётчиков. Два запроса к /metrics подряд покажут два значения, но хранить их по времени приложение не будет. Историю создаёт тот, кто регулярно читает адрес.

На стенде формат собран вручную, чтобы механизм был виден целиком. В рабочих приложениях используют библиотеку prometheus_client: она ведёт счётчики и гистограммы, правильно экранирует значения меток и работает, когда приложение запущено в нескольких процессах.

§3Prometheus сам опрашивает приложение

Опрос (scrape) — HTTP-запрос, которым Prometheus читает метрики с адреса приложения. Опросы повторяются с заданным интервалом, и каждое прочитанное значение сохраняется с отметкой времени.

Такую схему называют сбором по запросу (pull): запрос отправляет система мониторинга, а приложение только отвечает. Пройдите по шагам схемы и посмотрите, в какую сторону идёт HTTP-запрос и в какую — данные.

Стрелки на схемах мониторинга часто рисуют от приложения к Prometheus, по направлению движения данных, а сетевой запрос при этом идёт в обратную сторону. Это нужно помнить при настройке сети: Prometheus должен иметь доступ к адресу приложения, а приложению адрес Prometheus знать не нужно.

Какие адреса опрашивать, Prometheus берёт из файла конфигурации. На стенде он короткий.

СтрокаЧто означает
scrape_interval: 5sОпрашивать каждые 5 секунд. По умолчанию Prometheus опрашивает раз в минуту; на стенде интервал короткий, чтобы изменения появлялись быстро
job_name: telemetry-labИмя группы целей. Оно попадёт в каждый ряд меткой job
targetsСписок адресов. Путь /metrics не указан: он используется по умолчанию
host.docker.internalИмя, по которому контейнер обращается к компьютеру, на котором он запущен. API работает не в контейнере, поэтому Prometheus ищет его на хост-машине

Бывает и обратная схема: приложение само отправляет метрики. Её используют для коротких задач, которые завершаются раньше, чем их успеют опросить, например для ночного скрипта резервного копирования. Для них у Prometheus есть отдельный компонент Pushgateway. Долго работающий веб-сервис удобнее опрашивать напрямую.

§4Проверка цели на странице Target health

После запуска Prometheus первым делом открывают страницу состояния целей. Она показывает, получается ли вообще опрашивать приложение. Если здесь ошибка, все остальные запросы и панели будут пустыми.

КолонкаЗначение на снимкеЧто означает
Endpointhttp://host.docker.internal:8015/metricsАдрес из targets и путь по умолчанию
Labelsinstance="host.docker.internal:8015", job="telemetry-lab"Метки, которые Prometheus добавит к каждому ряду этой цели
Last scrape3.194s ago · 2msПоследний опрос был 3,2 секунды назад и занял 2 мс
StateUPПоследний опрос завершился успешно

Метки instance и job приложение не отдавало, их добавляет сам Prometheus. Благодаря им ряды разных экземпляров одного сервиса не смешиваются, даже если метрики называются одинаково.

По колонке Last scrape проверяют интервал: при scrape_interval: 5s значение «сколько секунд назад» не должно превышать пяти. Если цель недоступна, в колонке State появится DOWN и текст ошибки, например connection refused — по указанному адресу никто не слушает.

Метрика up

Для каждой цели Prometheus сам записывает ряд up: 1, если опрос успешен, и 0, если нет. Правило оповещения на up == 0 сообщит о пропаже цели. Без него сломанный сбор выглядит так же, как сервис без запросов.

§5Текущие значения в таблице

На вкладке Query в поле выражения вводят запрос на языке PromQL и нажимают Execute. Самый простой запрос — имя метрики. Он возвращает последние значения всех её рядов.

Каждая строка таблицы — один временной ряд: слева имя и полный набор меток, справа значение. Из четырёх меток route и status пришли из ответа приложения, а instance и job добавил Prometheus при опросе.

Значения 363 и 38 — счётчики с момента запуска API: 363 успешных запроса и 38 ошибочных. Поле Evaluation time позволяет посмотреть значения на любой момент в прошлом.

Для вопроса «как работает сервис» эти числа мало что дают: 38 ошибок могли накопиться за сутки или за минуту. Нужна скорость, и её даёт следующий запрос.

§6Скорость на графике

Переключимся на вкладку Graph и введём выражение, которое переводит счётчик в скорость и делит её по кодам ответа.

Выражение читают изнутри наружу.

  1. lab_http_requests_total[1m]

    Все значения каждого ряда за последнюю минуту. При опросе раз в 5 секунд это около двенадцати точек.

  2. rate(...)

    Средний прирост в секунду за эту минуту. Функция учитывает сбросы счётчика при перезапуске, о которых шла речь в главе 1.4.

  3. sum by (status) (...)

    Сложить ряды с одинаковой меткой status и убрать остальные метки. Будь экземпляров три, их скорости сложились бы в одну линию на каждый код.

Снимок сделан сразу после специального прогона. Две минуты скрипт tools/traffic.py отправлял только быстрые запросы, затем полторы минуты — смесь, где каждый четвёртый запрос завершается ошибкой, а каждый двадцать пятый выполняется медленно.

Участок графикаЧто видноПочему так
Слева, до начала нагрузкиНулевая линияЗапросов к API не было
Подъём ступенькамиСкорость 200 растёт около минутыОкно [1m] заполняется постепенно; ступенька — каждый новый опрос раз в 5 секунд
Ровный участок около 2,0Два успешных запроса в секундуСкрипт ждёт 0,4 с между запросами, а запрос длится около 85 мс
Появление нижней линииСкорость 500 растёт до 0,4Каждый четвёртый запрос стал ошибкой
Верхняя линия снижается до 1,3Успешных ответов стало меньшеЧетверть запросов ушла в ошибки, а медленные запросы по 3 с уменьшили общий темп
Спад справаОбе линии падаютНагрузка закончилась, и окно [1m] постепенно освобождается

Нагрузка поменялась мгновенно, а линии меняются около минуты, потому что скорость усредняется по последней минуте окна [1m]. Короткое окно быстрее реагирует, но сильнее скачет. Длинное сглаживает шум, но позже показывает изменения.

Пример

Почему окно rate не берут короче четырёх интервалов опроса

Функция rate считает прирост по точкам, попавшим в окно, а точек в окне столько, сколько опросов туда поместилось. Возьмём обычную рабочую настройку scrape_interval: 15s.

ОкноТочек в окнеЧто получится на графике
[20s]1 или 2Прирост посчитать не из чего: при одной точке значения нет, линия рвётся
[30s]2 или 3Линия есть, но один пропущенный опрос снова разрывает её
[1m]4 или 5Линия непрерывна и переживает один пропущенный опрос
[5m]20 или 21Линия гладкая, но изменение нагрузки видно с задержкой в несколько минут

Поэтому окно берут не меньше четырёх интервалов опроса. При scrape_interval: 15s это [1m], при 5 секундах на стенде хватило бы и [20s], но мы берём [1m], чтобы линия была спокойнее.

§7Дашборд Grafana

В интерфейсе Prometheus удобно проверять отдельные запросы, а для постоянного наблюдения используют Grafana. Она хранит набор панелей, каждая выполняет свой запрос к источнику данных и показывает результат.

Дашборд — страница Grafana с набором панелей. У каждой панели есть источник данных, запрос, диапазон времени и способ отображения.

Источник данных на стенде настраивается файлом, поэтому после запуска контейнера ничего не нужно указывать вручную.

СтрокаЧто означает
url: http://prometheus:9090Адрес работает внутри Docker Compose: контейнеры одного проекта находят друг друга по имени сервиса
access: proxyЗапросы к Prometheus отправляет сервер Grafana, а не браузер пользователя
editable: falseИсточник нельзя изменить через интерфейс, поэтому стенд у всех одинаковый
ПанельЗапрос PromQLЧто показывает
Завершённые запросы · с запускаsum(lab_http_requests_total)Сумма обоих рядов счётчика
Ошибки HTTP 500 · с запускаsum(lab_http_requests_total{status="500"})Только ряд с кодом 500
Поток запросов · запросов/сsum(rate(lab_http_requests_total[1m]))Скорость всех запросов
Средняя длительность · обработчикrate(..._sum[1m]) / rate(..._count[1m])Прирост суммы длительностей, делённый на прирост числа запросов

Сверим панели с Prometheus. Верхняя левая показывает 401 — ровно 363 + 38 из таблицы выше. Верхняя правая показывает 38. Числа совпадают, потому что Grafana выполнила запросы к тому же Prometheus.

На мини-графиках под крупными цифрами видно, как сбрасывается счётчик. Слева линия держится на ровном уровне, затем резко падает к нулю и снова растёт: ровный уровень — счётчик предыдущего запуска API, падение — перезапуск процесса перед прогоном, рост — новый счёт с нуля.

Нижняя правая панель показывает среднюю длительность. На первом участке она держится около 83 мс: все запросы быстрые. На втором поднимается до 185 мс из-за медленных запросов: каждый двадцать пятый длится 3 секунды и добавляет к среднему около 3000 / 25 = 120 мс. Быстрые ошибки немного тянут среднее вниз. Та же картина была в главе 1.4: пара долгих запросов сильно сдвигает среднее.

Анонимный просмотр

В правом верхнем углу Grafana стоит кнопка Sign in. На стенде включён анонимный просмотр с ролью Viewer: дашборд можно смотреть без входа, но нельзя менять. Для стенда на своём компьютере это удобно, для рабочей Grafana недопустимо.

§8Как запущен стенд

Prometheus и Grafana запускаются одной командой через Docker Compose. Файл описывает оба контейнера и их настройки.

СтрокаЧто означает
imageОбраз с точной версией. Без версии Docker возьмёт последнюю, и через полгода стенд может выглядеть иначе, чем на снимках
ports: 127.0.0.1:9095:9090Порт 9090 контейнера доступен на порту 9095 компьютера, и только с локального адреса. С других машин стенд недоступен
volumesПодключает файлы конфигурации внутрь контейнера. Суффикс :ro — только для чтения
extra_hosts: host-gatewayДобавляет имя host.docker.internal на Linux. В Docker Desktop для macOS и Windows это имя есть и без настройки
GF_AUTH_*Включают анонимный просмотр и скрывают форму входа
  1. docker compose up -d

    Скачивает образы при первом запуске и запускает контейнеры в фоне. API к этому моменту уже запущен с --host 0.0.0.0.

  2. docker compose ps

    Показывает состояние контейнеров.

  3. docker compose down

    Останавливает и удаляет контейнеры этого проекта, не затрагивая другие.

Адрес 0.0.0.0

API для стенда запускают с --host 0.0.0.0, иначе контейнер Prometheus до него не достучится. Такой адрес открывает API на всех сетевых интерфейсах компьютера, поэтому стенд запускают только в доверенной сети. Для практики без Prometheus достаточно адреса 127.0.0.1.

§10Проверьте себя

Кто отправляет HTTP-запрос при сборе метрик по схеме pull?

Prometheus. Он отправляет GET к адресу /metrics приложения, а приложение возвращает текущие значения в ответе.

На странице Target health цель в состоянии DOWN с ошибкой connection refused. Что проверить?

Запущен ли API, совпадает ли порт, слушает ли API адрес, доступный из контейнера (0.0.0.0, а не только 127.0.0.1), и разрешается ли имя host.docker.internal.

Откуда в рядах метрики появились метки instance и job, если приложение их не отдаёт?

Их добавляет Prometheus при опросе: job — из job_name конфигурации, instance — из адреса цели.

Что вычисляет выражение sum by (status) (rate(lab_http_requests_total[1m]))?

Среднюю скорость запросов в секунду за последнюю минуту, сложенную по всем рядам с одинаковым кодом ответа. Получается по одной линии на каждый код.

Нагрузка изменилась мгновенно, а линия rate(...[1m]) меняется около минуты. Почему?

Скорость усредняется по окну в одну минуту. Новые значения вытесняют старые из окна постепенно, поэтому линия меняется плавно.

§11Шпаргалка

  • Приложение отдаёт текущие значения, Prometheus хранит историю, Grafana показывает.
  • Сбор по запросу (pull): Prometheus опрашивает /metrics с интервалом scrape_interval.
  • Target health: UP — опрос успешен; метрика up = 1 или 0.
  • Метки instance и job добавляет Prometheus.
  • Имя метрики в запросе — последние значения всех её рядов.
  • rate(x[1m]) — средний прирост в секунду за минуту с учётом сбросов.
  • sum by (метка) — сложить ряды, оставив только указанную метку.
  • Панель Grafana = источник + запрос + диапазон + отображение.
  • Средняя длительность из гистограммы: rate(_sum) / rate(_count).
