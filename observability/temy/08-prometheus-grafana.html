Prometheus и Grafana: как метрики попадают на график

Проходим путь метрики учебного сервиса от строки в /metrics до панели Grafana. Разбираем по снимкам стенда, как Prometheus опрашивает приложение, как читать таблицу и график запроса и из чего состоит дашборд.

Приложение отдаёт текущее значение; историю создаёт тот, кто его регулярно читает.

§1Кто за что отвечает

В предыдущих главах мы разбирали, какие данные нужны для расследования. Теперь посмотрим на инструменты, которые эти данные собирают, хранят и показывают. Путаница обычно начинается с того, что всё вместе называют «Grafana» или «мониторинг». На деле за каждый участок пути отвечает свой компонент.

КомпонентЧто делаетЧего не делает
Приложение с инструментациейСчитает события и длительности, отдаёт текущие значения по адресу /metricsНе хранит историю: после перезапуска счётчики начинаются с нуля
PrometheusРегулярно опрашивает приложения, хранит временные ряды, выполняет запросы PromQL и проверяет правила оповещенияНе хранит логи и трассы; не рисует полноценные дашборды
GrafanaОтправляет запросы к источникам данных и показывает результаты панелямиСама метрики не собирает и не хранит
AlertmanagerПолучает сработавшие оповещения от Prometheus, группирует их и отправляет в почту или мессенджерНе вычисляет условия оповещений
OpenTelemetryСоздаёт телеметрию в коде и передаёт её через Collector в хранилищаНе хранит данные и не строит графики

На учебном стенде работают первые три компонента. API запущен как обычный Python-процесс, а Prometheus и Grafana — в контейнерах Docker. Ниже мы пройдём по пути одного числа: от строки кода, которая увеличивает счётчик, до цифры на панели Grafana.

§2Приложение отдаёт текущие значения

Разбор ответа /metrics по строкам есть в главе 1.4. Здесь посмотрим, как этот ответ формируется в коде учебного сервиса.

Обработчик собирает список строк и возвращает его обычным текстом. Словарь totals хранит два счётчика: {"200": ..., "500": ...}. Обработчик /products увеличивает нужный из них в конце каждого запроса. Двойные фигурные скобки в f-строке выводят одинарные: так в тексте появляется {route="/products",status="200"}. Параметр include_in_schema=False прячет адрес из Swagger, потому что он предназначен для Prometheus, а не для людей.

Главное свойство этого адреса: он возвращает только текущее состояние счётчиков. Два запроса к /metrics подряд покажут два значения, но где-то хранить их по времени приложение не будет. Историю создаёт тот, кто регулярно читает этот адрес.

В учебном сервисе формат собран вручную, чтобы механизм был виден целиком. В рабочих приложениях используют библиотеку prometheus_client: она ведёт счётчики и гистограммы, правильно экранирует значения меток и корректно работает, когда приложение запущено в нескольких процессах.

§3Prometheus сам опрашивает приложение

Опрос (scrape) — HTTP-запрос, которым Prometheus читает метрики с адреса приложения. Опросы повторяются с заданным интервалом, и каждое прочитанное значение сохраняется с отметкой времени.

Такую схему называют сбором по запросу (pull): инициатор — система мониторинга, а приложение только отвечает. Пройдите по шагам схемы и обратите внимание, в какую сторону идёт HTTP-запрос и в какую — данные.

Сбор по запросу · кто кого вызывает

← запрос
Grafanaпанель

1. Приложение обновляет свои измерения при обработке запросов.

Стрелки на схемах мониторинга часто рисуют от приложения к Prometheus, по направлению движения данных. Сетевой запрос при этом идёт в обратную сторону. Это различие важно при настройке сети: Prometheus должен иметь доступ к адресу приложения, а приложению не нужно знать адрес Prometheus.

Какие адреса опрашивать, Prometheus читает из файла конфигурации. На учебном стенде он короткий.

  • scrape_interval: 5s — опрашивать каждые 5 секунд. По умолчанию Prometheus опрашивает раз в минуту; короткий интервал выбран, чтобы на стенде изменения появлялись быстро.
  • job_name: telemetry-lab — имя группы целей. Оно попадёт в каждый ряд меткой job.
  • targets — список адресов. Путь /metrics не указан, потому что он используется по умолчанию.
  • host.docker.internal — имя, по которому контейнер обращается к компьютеру, на котором он запущен. API работает не в контейнере, поэтому Prometheus ищет его на хост-машине.

У сбора по запросу есть альтернатива: приложение само отправляет метрики. Её используют для коротких задач, которые завершаются раньше, чем их успеют опросить, например для ночного скрипта резервного копирования. Для таких случаев у Prometheus есть отдельный компонент Pushgateway. Долгоживущий веб-сервис удобнее опрашивать напрямую.

§4Проверка цели на странице Target health

Первое, что стоит открыть после запуска Prometheus, — страницу состояния целей. Она отвечает на вопрос, получается ли вообще опрашивать приложение. Если здесь ошибка, все остальные запросы и панели будут пустыми.

Разберём строку цели по колонкам.

КолонкаЗначение на снимкеЧто означает
Endpointhttp://host.docker.internal:8015/metricsПолный адрес опроса: адрес из targets и путь по умолчанию
Labelsinstance="host.docker.internal:8015", job="telemetry-lab"Метки, которые Prometheus добавит к каждому ряду этой цели
Last scrape3.194s ago · 2msПоследний опрос был 3,2 секунды назад и занял 2 мс
StateUPПоследний опрос завершился успешно

Метки instance и job приложение не отдавало: их добавляет сам Prometheus. Так ряды разных экземпляров одного сервиса не смешиваются, даже если метрики называются одинаково.

Колонка Last scrape помогает проверить интервал. При scrape_interval: 5s значение «сколько секунд назад» не должно превышать пяти. Если цель недоступна, в колонке State появится DOWN, а рядом текст ошибки, например connection refused — по указанному адресу никто не слушает.

Метрика up

Для каждой цели Prometheus сам записывает ряд up: 1, если опрос успешен, и 0, если нет. Правило оповещения на up == 0 сообщит о пропаже цели. Без него сломанный сбор выглядит так же, как сервис без запросов.

§5Текущие значения в таблице

На вкладке Query в поле выражения вводят запрос на языке PromQL и нажимают Execute. Самый простой запрос — имя метрики. Он возвращает последние значения всех её рядов.

Каждая строка таблицы — один временной ряд. Слева имя и полный набор меток, справа значение. В фигурных скобках четыре метки. route и status пришли из ответа приложения, instance и job добавил Prometheus при опросе.

Значения 363 и 38 — счётчики с момента запуска API: 363 успешных запроса и 38 ошибочных. Справа над таблицей Result series: 2 — число найденных рядов, Load time: 24ms — время выполнения запроса. Поле Evaluation time позволяет посмотреть значения на любой момент в прошлом, а не только сейчас.

Для ответа на вопрос «как работает сервис» эти числа мало что дают. 38 ошибок могли накопиться за сутки или за минуту. Нужна скорость, и её показывает следующий запрос.

§6Скорость на графике

Переключимся на вкладку Graph и введём выражение, которое переводит счётчик в скорость и разделяет её по кодам ответа.

Читать выражение удобно изнутри наружу.

  1. lab_http_requests_total[1m] — все значения каждого ряда за последнюю минуту. При опросе раз в 5 секунд это около двенадцати точек.
  2. rate(...) — средний прирост в секунду за эту минуту. Функция учитывает сбросы счётчика при перезапуске, о которых шла речь в главе 1.4.
  3. sum by (status) (...) — сложить ряды, у которых совпадает метка status, и убрать остальные метки. Если бы экземпляров было три, их скорости сложились бы в одну линию на каждый код.

Снимок сделан сразу после специального прогона. Две минуты скрипт tools/traffic.py отправлял только быстрые запросы, затем полторы минуты — смесь, где каждый четвёртый запрос завершается ошибкой, а каждый двадцать пятый выполняется медленно. Прочитаем график по участкам.

Участок графикаЧто видноПочему так
Слева, до начала нагрузкиНулевая линияЗапросов к API не было
Подъём ступенькамиСкорость 200 растёт около минутыОкно [1m] заполняется постепенно; ступенька — каждый новый опрос раз в 5 секунд
Ровный участок около 2,0Два успешных запроса в секундуСкрипт ждёт 0,4 с между запросами, а запрос длится около 85 мс
Появление нижней линииСкорость 500 растёт до 0,4Каждый четвёртый запрос стал ошибкой
Верхняя линия снижается до 1,3Успешных ответов стало меньшеЧетверть запросов ушла в ошибки, а медленные запросы по 3 с уменьшили общий темп
Спад справаОбе линии падаютНагрузка закончилась, и окно [1m] постепенно освобождается

Посмотрим внимательнее на плавность линий. Нагрузка поменялась мгновенно, а линии меняются около минуты. Это прямое следствие окна [1m]: скорость усредняется по последней минуте. Короткое окно быстрее реагирует, но сильнее скачет. Длинное окно сглаживает шум, но позже показывает изменения.

Пример

Почему окно rate не берут короче четырёх интервалов опроса

Функция rate считает прирост по точкам, попавшим в окно. Точек в окне столько, сколько опросов туда поместилось. Возьмём рабочую настройку scrape_interval: 15s и посмотрим, что даёт разное окно.

ОкноТочек в окнеЧто получится на графике
[20s]1 или 2Прирост посчитать не из чего: при одной точке значения нет, линия рвётся
[30s]2 или 3Линия есть, но один пропущенный опрос снова разрывает её
[1m]4 или 5Линия непрерывна и переживает один пропущенный опрос
[5m]20 или 21Линия гладкая, но изменение нагрузки видно с задержкой в несколько минут

Отсюда правило: окно берут не меньше четырёх интервалов опроса. При scrape_interval: 15s это [1m], при интервале 5 секунд учебного стенда хватило бы и [20s] — мы всё равно берём [1m], чтобы линия была спокойнее.

Отдельно отметим, что окно и интервал опроса — разные настройки. Интервал задаётся в prometheus.yml и определяет, как часто появляются точки. Окно пишется в самом запросе и определяет, по скольким точкам считается скорость. Менять интервал ради красивой линии не нужно: достаточно подобрать окно.

Доля ошибок на втором участке: 0,43 / (1,3 + 0,43) ≈ 25%, то есть как раз каждый четвёртый запрос. Такой расчёт по графику совпал с тем, как была задана нагрузка. Это хорошая проверка, что метрика и запрос устроены правильно.

§7Дашборд Grafana

Интерфейс Prometheus удобен для проверки отдельных запросов. Для постоянного наблюдения используют Grafana. Она хранит набор панелей, каждая из которых выполняет свой запрос к источнику данных и показывает результат.

Дашборд — страница Grafana с набором панелей. У каждой панели есть источник данных, запрос, временной диапазон и способ отображения.

Источник данных Grafana на стенде настраивается файлом, поэтому после запуска контейнера ничего не нужно указывать вручную.

Адрес http://prometheus:9090 работает внутри Docker Compose: контейнеры одного проекта находят друг друга по имени сервиса. access: proxy означает, что запросы к Prometheus отправляет сервер Grafana, а не браузер пользователя. editable: false запрещает менять источник через интерфейс, чтобы стенд у всех был одинаковым.

ПанельЗапрос PromQLЧто показывает
Завершённые запросы · с запускаsum(lab_http_requests_total)Сумма обоих рядов счётчика
Ошибки HTTP 500 · с запускаsum(lab_http_requests_total{status="500"})Только ряд с кодом 500
Поток запросов · запросов/сsum(rate(lab_http_requests_total[1m]))Скорость всех запросов
Средняя длительность · обработчикrate(..._sum[1m]) / rate(..._count[1m])Прирост суммы длительностей, делённый на прирост числа запросов

Сверим панели с Prometheus. Верхняя левая показывает 401, и это ровно 363 + 38 из таблицы выше. Верхняя правая показывает 38. Числа совпадают, потому что Grafana выполнила запросы к тому же Prometheus.

На мини-графиках под крупными цифрами есть деталь, которая хорошо иллюстрирует сбросы счётчика. Слева линия держится на ровном уровне, затем резко падает к нулю и снова растёт. Ровный уровень — счётчик предыдущего запуска API, падение — перезапуск процесса перед прогоном, рост — новый счёт с нуля.

Нижняя правая панель показывает среднюю длительность. На первом участке она держится около 83 мс: все запросы быстрые. На втором поднимается до 185 мс. Причина — медленные запросы: каждый двадцать пятый длится 3 секунды и добавляет к среднему около 3000 / 25 = 120 мс. Быстрые ошибки немного тянут среднее вниз. Это та же картина, что в главе 1.4: пара долгих запросов сильно сдвигает среднее.

В правом верхнем углу Grafana стоит кнопка Sign in. На стенде включён анонимный просмотр с ролью Viewer: смотреть дашборд можно без входа, менять нельзя. Для локального учебного стенда это удобно, для рабочей Grafana — недопустимо.

§8Как запущен стенд

Prometheus и Grafana на стенде запускаются одной командой через Docker Compose. Файл описывает оба контейнера и их настройки.

  • image указывает образ с точной версией. Без версии Docker возьмёт последнюю, и через полгода стенд может выглядеть иначе, чем на снимках.
  • ports: 127.0.0.1:9095:9090 публикует порт 9090 контейнера на порт 9095 компьютера, причём только для локального адреса. С других машин стенд недоступен.
  • volumes подключает файлы конфигурации внутрь контейнера. Суффикс :ro — только для чтения.
  • extra_hosts: host-gateway добавляет имя host.docker.internal на Linux. В Docker Desktop для macOS и Windows это имя есть и без настройки.
  • Переменные GF_AUTH_* включают анонимный просмотр и скрывают форму входа.

docker compose up -d скачивает образы при первом запуске и запускает контейнеры в фоне. docker compose ps показывает их состояние. docker compose down останавливает и удаляет контейнеры этого проекта, не затрагивая другие.

API для стенда запускают с --host 0.0.0.0, иначе контейнер Prometheus не достучится до него. Такой адрес открывает API на всех сетевых интерфейсах компьютера, поэтому стенд запускают только в доверенной сети. Для практики без Prometheus достаточно адреса 127.0.0.1.

§10Проверьте себя

Кто инициирует HTTP-запрос при сборе метрик по схеме pull?

Prometheus. Он отправляет GET к адресу /metrics приложения, а приложение возвращает текущие значения в ответе.

На странице Target health цель в состоянии DOWN с ошибкой connection refused. Что проверить?

Запущен ли API, совпадает ли порт, слушает ли API адрес, доступный из контейнера (0.0.0.0, а не только 127.0.0.1), и разрешается ли имя host.docker.internal.

Откуда в рядах метрики появились метки instance и job, если приложение их не отдаёт?

Их добавляет Prometheus при опросе: job — из job_name конфигурации, instance — из адреса цели.

Что вычисляет выражение sum by (status) (rate(lab_http_requests_total[1m]))?

Среднюю скорость запросов в секунду за последнюю минуту, сложенную по всем рядам с одинаковым кодом ответа. Получается по одной линии на каждый код.

Нагрузка изменилась мгновенно, а линия rate(...[1m]) меняется около минуты. Почему?

Скорость усредняется по окну в одну минуту. Новые значения вытесняют старые из окна постепенно, поэтому линия меняется плавно.

§11Шпаргалка

  • Приложение отдаёт текущие значения, Prometheus хранит историю, Grafana показывает.
  • Сбор по запросу (pull): Prometheus опрашивает /metrics с интервалом scrape_interval.
  • Target health: UP — опрос успешен; метрика up = 1 или 0.
  • Метки instance и job добавляет Prometheus.
  • Имя метрики в запросе — последние значения всех её рядов.
  • rate(x[1m]) — средний прирост в секунду за минуту с учётом сбросов.
  • sum by (метка) — сложить ряды, оставив только указанную метку.
  • Панель Grafana = источник + запрос + диапазон + отображение.
  • Средняя длительность из гистограммы: rate(_sum) / rate(_count).
