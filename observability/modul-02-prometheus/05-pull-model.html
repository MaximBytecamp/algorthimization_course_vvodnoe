Pull-модель:
Prometheus приходит сам

В предыдущих главах запрос всегда шёл от Prometheus к приложению. В этой главе у этого порядка появляется название — pull-модель — и сравнение с противоположным способом, push. Разобрано, куда направлен запрос и куда идут данные, почему Prometheus построен на pull и что было до него, какие ограничения у такого сбора и как экосистема Prometheus обходит их, когда без push не обойтись.

§1Два способа доставки метрик

Значения метрик возникают в приложении, а хранятся на сервере мониторинга. Доставить их можно двумя способами, и они различаются тем, кто начинает обмен.

Для наглядности
Показания счётчика воды

Жилец сам передаёт показания в управляющую компанию раз в месяц — это push. Контролёр обходит квартиры по списку и снимает показания сам — это pull. Если жилец забыл или уехал, в первом случае компания видит только отсутствие письма. Контролёр же знает, в какую квартиру не смог попасть.

Что это в мониторинге

Жилец — приложение, компания — сервер мониторинга, список квартир — список target в prometheus.yml. «Не смог попасть» — неуспешный scrape и up = 0.

Push-модельприложение → мониторинг

Приложение само отправляет значения на сервер мониторинга: знает его адрес, решает, когда отправлять, и отвечает за повтор при ошибке. Так работают StatsD, Graphite, InfluxDB в обычной настройке, протокол OTLP в OpenTelemetry.

Pull-модельPrometheus → приложение

Сервер мониторинга сам запрашивает значения у приложений по списку target и по своему расписанию. Приложение только держит текущие значения и отвечает на запрос. Так устроен сбор в Prometheus: scrape из главы 2.4 и есть pull.

§2Push и pull по шагам

Две диаграммы показывают одну и ту же ситуацию: два обмена данными, затем приложение падает. Различие видно на последнем шаге: что знает сервер мониторинга после падения.

Pushприложение отправляет само
  1. Приложение знает адрес сервера мониторинга: он записан в его конфигурации.
  2. Приложение отправляет значения, когда решит само: по таймеру или после события.
  3. Сервер записывает то, что пришло. О приложении, которое ничего не отправило, сервер не знает.
  4. Следующая отправка.
  5. Процесс упал; отправок больше нет.
  6. Для сервера это выглядит как тишина. Отличить упавшее приложение от приложения, которому нечего сообщить, по одному отсутствию данных нельзя.
PullPrometheus запрашивает сам
  1. Prometheus знает список target: из файла или из service discovery.
  2. По расписанию Prometheus отправляет GET /metrics.
  3. Приложение отвечает текущими значениями.
  4. Prometheus записывает отсчёты и up = 1.
  5. Следующий scrape по расписанию.
  6. Процесс упал, порт закрыт.
  7. Запрос завершается ошибкой соединения.
  8. Prometheus записывает up = 0: известно, какой target и с какого момента недоступен.

§3Направление запроса и данных

В pull-модели легко спутать два направления. HTTP-запрос идёт от Prometheus к приложению. Данные идут обратно — в теле ответа на этот запрос. Когда говорят «Prometheus собирает метрики с приложения», имеют в виду оба направления сразу.

ЗапросGET /metrics от Prometheus к api:8000
→
Сетевое правилоВходящие соединения на порт приложения должны быть разрешены с адреса Prometheus
ДанныеТело ответа 200 OK от приложения к Prometheus
→
Отдельного соединения нетОтвет идёт по тому же TCP-соединению, которое открыл Prometheus

Отсюда практическое следствие: при pull порт /metrics открыт для входящих соединений. На нём видны внутренние числа сервиса, поэтому его не публикуют в интернет. В Kubernetes и Compose метрики отдают на внутреннем адресе, а при необходимости закрывают TLS и авторизацией; в задании Prometheus для этого есть параметры scheme: https, tls_config, basic_auth, authorization.

§4Откуда взялась pull-модель

Pull-модель Prometheus повторяет устройство внутренней системы мониторинга Google — Borgmon. Её подробно описывает глава 10 книги Google «Site Reliability Engineering» (2016). Приложения Google отдавали внутренние переменные по HTTP-пути /varz, простым текстом — пары «ключ значение» по одной в строке. В книге приведён пример ручного просмотра:

По описанию в книге, Borgmon через заданные интервалы запрашивает /varz у каждого target, разбирает ответ и хранит значения в памяти; список target он получает через службы разрешения имён; сбор с разных target распределяется по интервалу; для каждого target записываются «синтетические» переменные о том, удался ли сбор. Все эти черты есть в Prometheus: /metrics, scrape_interval, service discovery, смещения scrape и up. В той же главе книги Prometheus назван среди открытых систем, очень похожих на Borgmon.

§5Что даёт pull

В FAQ Prometheus на вопрос, почему сбор идёт через pull, дан короткий ответ:

«Pulling over HTTP offers a number of advantages: You can start extra monitoring instances as needed, e.g. on your laptop when developing changes. You can more easily and reliably tell if a target is down. You can manually go to a target and inspect its health with a web browser.»

Prometheus FAQ, «Why do you pull rather than push?» · prometheus.io/docs/introduction/faq

Перевод: pull по HTTP даёт ряд преимуществ. Можно запускать дополнительные экземпляры мониторинга по мере надобности, например на своём ноутбуке при разработке. Проще и надёжнее определить, что target не работает. Можно вручную открыть target в браузере и посмотреть его состояние. Каждое из этих преимуществ видно на стенде модуля, и к ним добавляются ещё два.

ПреимуществоКак это выглядит на практике
Доступность видна сразуup = 0 и текст ошибки в Target health (глава 2.4, §7). В push нужно отдельно решать, через сколько минут тишины считать отправителя упавшим
Второй Prometheus без изменений в приложенииДля отказоустойчивости два одинаковых сервера собирают одни и те же target. Для отладки — Prometheus на ноутбуке. Приложение не знает, сколько серверов его опрашивает

Список target — описание того, что должно работатьTarget из конфигурации или service discovery, который не ответил, виден как DOWN. В push-модели сервис, который ни разу не отправил данные, серверу неизвестен

Приложению при pull тоже проще: не нужно знать адрес мониторинга, буферизовать данные при недоступности сервера и повторять отправку. Библиотека держит числа в памяти и отдаёт их по запросу.

§6Ограничения pull

У pull-модели три ограничения, и каждое следует из того, что инициатор — сервер.

Сервер должен достать до targetПриложение за NAT или файрволом, который не пропускает входящие соединения, собрать нельзя.

РешенияДокументация советует ставить Prometheus в ту же сеть, что и target. Если это невозможно — PushProx: клиент за файрволом сам держит соединение с прокси, и Prometheus собирает через него.

Короткая задача завершается раньше scrapeСкрипт резервного копирования работает 40 секунд и выходит. При интервале 60 с его /metrics никто не увидит.

РешенияЗадача перед выходом отправляет результат в Pushgateway, а Prometheus собирает Pushgateway как обычный target. Для задач, привязанных к машине (cron, обновления), — файл для textfile collector в node exporter.

Нужно знать список targetВ облаке экземпляры появляются и исчезают, и файл с адресами устаревает за минуты.

РешенияService discovery из главы 2.2: Kubernetes, Consul, облачные API, DNS.

Документация Prometheus рекомендует Pushgateway только в ограниченных случаях и перечисляет, что теряется при его использовании вместо pull:

  • Единая точка отказа. Когда много экземпляров отправляют данные через один Pushgateway, он становится и единой точкой отказа, и узким местом.
  • Нет up для источника. Автоматическая проверка доступности по up относится к самому Pushgateway; для задач, которые в него пишут, её нет.
  • Данные не забываются. Pushgateway хранит последние отправленные ряды и отдаёт их Prometheus вечно, пока их не удалят через его API. Ряды удалённого экземпляра остаются, хотя в pull-модели они исчезли бы вместе с экземпляром.

По документации, обычно единственный обоснованный случай для Pushgateway — результат пакетной задачи уровня сервиса, не привязанной к конкретной машине или экземпляру. У её метрик не должно быть метки instance. Так как Pushgateway передаёт чужие метки job и instance, в его задании включают honor_labels: true (глава 2.2, §6).

§7Push в экосистеме Prometheus

Pull остаётся основным способом сбора, но передача данных в push-направлении в экосистеме тоже есть. Флаги ниже проверены в prometheus --help версии 3.5.0.

МеханизмКто кому отправляетДля чего
PushgatewayЗадача → Pushgateway; Prometheus собирает Pushgateway через pullРезультаты коротких пакетных задач
remote_write в конфигурацииPrometheus → другое хранилищеДолгое хранение и объединение нескольких серверов (Thanos, Mimir, VictoriaMetrics)
--web.enable-remote-write-receiverДругой Prometheus или агент → этот PrometheusПриём данных от серверов в режиме агента, которые сами собирают target через pull
--web.enable-otlp-receiverПриложение с OpenTelemetry SDK или OpenTelemetry Collector → PrometheusПриём метрик по протоколу OTLP без /metrics

Оба приёмника по умолчанию выключены. Данные, которые пришли через них, не проходят scrape: для их источников нет up и рядов scrape_*, и доступность отправителя приходится отслеживать отдельно. Это та же цена push-модели, что в §2.

§8Проверьте себя

Вопрос 1Между Prometheus и приложением стоит файрвол. Какое соединение он должен разрешить для pull?

  • Так было бы при push. В pull приложение соединений не открывает.

  • Верно. Prometheus открывает соединение, а данные приходят в ответе по нему же.

  • Ответ идёт по уже открытому TCP-соединению; второго соединения нет.

Вопрос 2Какое преимущество pull приведено в FAQ Prometheus?

  • Объём одинаковый — те же значения. FAQ этого не утверждает.

  • Верно, это одно из трёх преимуществ в FAQ, вместе с дополнительными экземплярами мониторинга и проверкой в браузере.

  • NAT и файрвол, закрывающие входящие соединения, — одно из ограничений pull (§6).

Вопрос 3Скрипт очистки базы запускается раз в сутки и работает 20 секунд. Как передать в Prometheus время его последнего успешного запуска?

  • Scrape может не попасть в 20 секунд работы, а после выхода target будет DOWN до следующих суток.

  • Верно. Это пакетная задача уровня сервиса — случай, для которого документация рекомендует Pushgateway.

  • Prometheus не читает логи; для логов нужны другие системы.

Вопрос 4Экземпляр сервиса удалён. Что станет с его рядами в Pushgateway?

  • Pushgateway не связан с жизнью экземпляра и сам ничего не удаляет.

  • Верно. Документация называет это одной из проблем Pushgateway.

  • up относится к scrape самого Pushgateway. Для экземпляров, которые в него писали, отдельного up нет.
