§1Два способа доставки метрик

Числа появляются в приложении, а хранятся на сервере мониторинга. Доставить их можно двумя способами. Способы различаются тем, кто начинает обмен.

Сравнение из жизни
Показания счётчика воды

Первый способ. Жилец раз в месяц передаёт показания в управляющую компанию.

Второй способ. Контролёр обходит квартиры по списку и записывает показания.

Когда жилец уехал, в первом случае компания не получает письма, и причина ей неизвестна. Во втором случае у контролёра записано, в какую квартиру он не попал.

Метрики

Push. Приложение отправляет числа на сервер мониторинга.

Pull. Сервер обходит приложения по списку target и забирает числа.

Когда приложение остановилось, при push сервер не получает данных, и причина ему неизвестна. При pull на сервере записано, какой target не ответил: ряд up равен 0.

По способу push работают StatsD, Graphite, InfluxDB в обычной настройке и протокол OTLP из OpenTelemetry. По способу pull работает Prometheus: scrape из главы 2.4 — это pull.

§2Push и pull по шагам

Две схемы показывают одну ситуацию: два обмена данными, затем приложение аварийно завершается. Сравните последний шаг каждой схемы: какие сведения есть у сервера после остановки приложения.

Pushприложение отправляет само
  1. Адрес сервера мониторинга записан в настройках приложения.
  2. Приложение отправляет числа по своему расписанию: по таймеру или после события.
  3. Сервер записывает то, что пришло.
  4. Следующая отправка.
  5. Приложение аварийно завершилось. Отправок больше нет.
  6. Данные на сервер не приходят. По одному отсутствию данных причину определить нельзя: приложение остановилось или у него нет новых чисел.
PullPrometheus запрашивает сам
  1. У Prometheus есть список target.
  2. По расписанию Prometheus отправляет запрос GET /metrics.
  3. Приложение отвечает текущими числами.
  4. Prometheus записывает числа и up = 1.
  5. Следующий scrape по расписанию.
  6. Приложение аварийно завершилось. Его порт закрыт.
  7. Запрос завершается ошибкой соединения.
  8. Prometheus записывает up = 0. Известно, какой target недоступен и с какого момента.

§3Направление запроса и данных

Сравнение из жизни
Звонок в справочную

Человек звонит в справочную и задаёт вопрос. Ответ он слышит в том же разговоре. Справочная ему не перезванивает.

Запрос и ответ в pull

Prometheus открывает соединение и отправляет запрос. Числа приходят в ответе по тому же соединению. Приложение соединений не открывает.

В pull-модели есть два направления. Запрос идёт от Prometheus к приложению. Данные идут обратно, от приложения к Prometheus.

Запрос и ответ в одном соединенииодин scrape
открывает соединениеPrometheus
принимает соединениеapi:8000
получает числаPrometheus
отвечает по тому же соединениюapi:8000

Сетевой экран между ними должен разрешать одно соединение: от Prometheus на порт приложения.

Что из этого следует для безопасности

При pull порт приложения принимает входящие соединения. На странице /metrics видны внутренние числа сервиса. Поэтому этот порт не открывают в интернет. Метрики отдают на внутреннем адресе сети.

Подробнее: защита страницы /metrics

Страницу можно закрыть шифрованием и проверкой доступа. В задании Prometheus для этого есть параметры scheme: https, tls_config, basic_auth и authorization.

§4Откуда взялась pull-модель

Программы Google отдавали свои числа по адресу /varz. Ответ — обычный текст: в каждой строке название и значение. Пример из книги:

§5Что даёт pull

В разделе вопросов и ответов документации Prometheus объяснено, почему выбран pull:

«Pulling over HTTP offers a number of advantages: You can start extra monitoring instances as needed, e.g. on your laptop when developing changes. You can more easily and reliably tell if a target is down. You can manually go to a target and inspect its health with a web browser.»

Prometheus FAQ, «Why do you pull rather than push?» · prometheus.io/docs/introduction/faq

В ответе названы три преимущества. На стенде модуля видны они и ещё два.

Пять преимуществ pullпервые три — из документации
1 · из документацииВторой сервер без правок в приложенииМожно запустить ещё один Prometheus, например на своём ноутбуке. В приложении для этого ничего не меняют.
2 · из документацииВидно, что target не работаетРяд up равен 0, на странице Target health записан текст ошибки.
3 · из документацииПроверка вручнуюБраузер и curl показывают тот же текст, который получает Prometheus.
4Нагрузкой управляет серверСервер распределяет опросы по интервалу. Тысяча приложений не отправляет ему данные одновременно.
5Список target показывает, что должно работатьTarget из списка, который не ответил, виден как DOWN. При push приложение, которое ни разу не отправило данные, серверу неизвестно.

Что pull упрощает в приложении

Приложению не нужен адрес сервера мониторинга. Ему не нужно хранить неотправленные данные и повторять отправку, когда сервер недоступен. Библиотека хранит числа в памяти и отдаёт их по запросу.

§6Ограничения pull

У pull три ограничения. Все три следуют из того, что обмен начинает сервер.

1. Сервер должен иметь доступ к targetПриложение находится в закрытой сети. Входящие соединения к нему запрещены, и Prometheus его опросить не может.

Как поступаютСтавят Prometheus в ту же сеть, что и приложение. Так советует документация.

2. Короткая задача завершается раньше scrapeСкрипт резервного копирования работает 40 секунд и завершается. При интервале 60 секунд scrape может не попасть в эти 40 секунд.

Как поступаютЗадача перед завершением отправляет результат в программу Pushgateway. Prometheus опрашивает Pushgateway как обычный target.

3. Нужно знать список targetВ облаке копии сервиса появляются и исчезают. Файл с адресами устаревает за минуты.

Как поступаютБерут список из внешней системы: service discovery из главы 2.2.

Как работает Pushgateway

Сравнение из жизни
Почтовый ящик в подъезде

Жилец уезжает до прихода контролёра. Он оставляет записку с показаниями в ящике. Контролёр забирает записку при обходе.

Pushgateway

Задача завершается до scrape. Она отправляет числа в Pushgateway. Prometheus забирает их оттуда при очередном scrape.

Короткая задача и Pushgatewaypush и pull вместе

Три недостатка Pushgateway

Документация Prometheus советует Pushgateway только в ограниченных случаях. Она называет три недостатка.

  • Одна точка отказа. Много задач отправляют данные через один Pushgateway. Если он остановится, пропадут данные всех задач.
  • Нет up для задачи. Ряд up показывает доступность самого Pushgateway. Состояние задач, которые в него пишут, по этому ряду определить нельзя.
  • Данные не удаляются сами. Pushgateway хранит последние полученные числа и отдаёт их при каждом scrape, пока их не удалят вручную. Числа удалённой копии сервиса остаются. При pull они исчезли бы вместе с копией.

По документации, Pushgateway обычно оправдан в одном случае: результат пакетной задачи, которая относится ко всему сервису и не привязана к одной машине. Пример — ночная очистка базы данных.

Подробнее: настройки для Pushgateway и другие решения

У метрик такой задачи не должно быть метки instance. Pushgateway передаёт метки job и instance других программ, поэтому в его задании включают honor_labels: true (глава 2.2, §6).

Для задач, привязанных к одной машине (cron, обновления), числа записывают в файл. Этот файл читает программа node exporter через свой textfile collector.

Для приложений в закрытой сети есть PushProx. Его клиент внутри закрытой сети держит соединение с посредником, и Prometheus опрашивает приложение через посредника.

§7Push в экосистеме Prometheus

Основной способ сбора в Prometheus — pull. Передача данных способом push тоже используется, в четырёх случаях. Флаги запуска из таблицы проверены командой prometheus --help версии 3.5.0.

МеханизмКто кому отправляетДля чего
PushgatewayЗадача → Pushgateway. Prometheus опрашивает Pushgateway способом pullРезультаты коротких задач
remote_write в конфигурацииPrometheus → другое хранилищеДолгое хранение и объединение данных нескольких серверов
Флаг --web.enable-remote-write-receiverДругой Prometheus → этот PrometheusПриём данных от серверов, которые опрашивают свои target
Флаг --web.enable-otlp-receiverПриложение с OpenTelemetry → PrometheusПриём метрик по протоколу OTLP без страницы /metrics

Оба флага по умолчанию выключены. Данные, принятые через них, не проходят scrape. Для их источников нет ряда up, и доступность отправителя проверяют отдельно. Это тот же недостаток push, что в §2.

§8Проверьте себя

Вопрос 1Между Prometheus и приложением стоит сетевой экран. Какое соединение он должен разрешить для pull?

  • Так было бы при push. В pull приложение соединений не открывает.

  • Верно. Prometheus открывает соединение, а данные приходят в ответе по нему же.

  • Ответ идёт по уже открытому соединению. Второго соединения нет.

Вопрос 2Какое преимущество pull названо в документации Prometheus?

  • Объём одинаковый: передаются те же значения. Документация этого не утверждает.

  • Верно. Это одно из трёх преимуществ из документации, вместе со вторым сервером мониторинга и проверкой в браузере.

  • Закрытая сеть — одно из ограничений pull (§6).

Вопрос 3Скрипт очистки базы запускается раз в сутки и работает 20 секунд. Как передать в Prometheus время его последнего успешного запуска?

  • Scrape может не попасть в 20 секунд работы. После завершения скрипта target будет DOWN до следующих суток.

  • Верно. Это пакетная задача всего сервиса — случай, для которого документация советует Pushgateway.

  • Prometheus логи не читает. Для логов нужны другие системы.

Вопрос 4Копия сервиса удалена. Что станет с её числами в Pushgateway?

  • Pushgateway не связан с работой копий и полученные числа не удаляет.

  • Верно. Документация называет это одним из недостатков Pushgateway.

  • Ряд up относится к самому Pushgateway. Для копий, которые в него писали, отдельного up нет.
