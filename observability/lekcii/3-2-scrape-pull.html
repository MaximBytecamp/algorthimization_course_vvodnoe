§1Один scrape

Три действия, из которых состоит один плановый опрос.

В прошлой лекции target описан как адрес для опроса. Scrape — одна завершённая попытка получить метрики с этого адреса. После HTTP-ответа Prometheus разбирает текст и записывает отсчёты в свою базу.

GET /metricsPrometheus обращается к endpoint target. В стенде это API на порту 8015.
text expositionAPI возвращает строки с именем метрики, метками и числом.
TSDBУспешно разобранные строки становятся точками временных рядов.

Один scrape — законченный рабочий цикл. Чтобы понять, почему этот цикл устроен именно так, сначала определим, какая сторона посылает первый запрос.

§2Направление HTTP-запроса

Направление запроса отличает pull от push.

У двух программ есть два возможных способа обменяться данными. В push-модели приложение само посылает данные получателю. В pull-модели получатель приходит за данными сам. Prometheus использует второй вариант: запрос всегда начинает его планировщик.

Pull-модель описывает направление первого обращения. В стенде API не открывает соединение к Prometheus и не получает его адрес. API отвечает, когда к /metrics приходит запрос.

Направление запроса определено. Теперь разберём, какие практические свойства даёт pull-модель именно Prometheus.

§3Зачем Prometheus pull-модель

Почему расписание и проверка связи находятся у системы сбора.

В конфигурации Prometheus находится список target. Расписание определяет время опроса, результат попытки отражается в up, а к данным добавляются метки задания и адреса. Приложение поддерживает endpoint и формирует корректный ответ.

ЗадачаВ pull-модели
Когда опрашиватьрешает расписание Prometheus
Куда обращатьсяопределяют target в конфигурации
Проверить связьрезультат последнего scrape виден в up
Отдать измерениеделает endpoint /metrics

Такое разделение не освобождает приложение от ответственности за смысл метрик. Оно лишь определяет границу: Prometheus забирает уже подготовленные измерения и хранит историю попыток это сделать.

Чтобы история получилась равномерной, планировщик повторяет scrape. Следующий вопрос — с какой частотой.

§4Расписание опросов

Как интервал из YAML превращается в регулярные точки на временной шкале.

В файле стенда задано global.scrape_interval: 5s. Значит, Prometheus планирует новый scrape этого target примерно каждые пять секунд. Каждый успешный цикл добавляет новую точку для рядов из ответа, включая lab_http_requests_total и служебный up.

Пять секунд выбраны для стенда, чтобы несколько отсчётов появлялись быстро. Интервал задаёт частоту снимков состояния. Он не меняет скорость работы приложения.

У расписания есть соседняя настройка. Она отвечает не за паузу, а за максимальное ожидание одного ответа.

§5Интервал и timeout

Два времени, которые нельзя путать.

scrape_interval отвечает на вопрос «когда начать следующую попытку». scrape_timeout отвечает на другой вопрос: «сколько ждать завершения уже начатого scrape». Timeout ограничивает один запрос, а не паузу между всеми запросами.

5sПланировщик готовит новый scrape с таким интервалом.
4sЕсли ответ текущего scrape не завершился за это время, попытка считается неудачной.
не один параметрВ примере timeout короче интервала: ожидание одной попытки не перекрывает следующий плановый момент.
scrape_timeoutпредел ожидания одного scrape
Что это
Максимальная длительность запроса и получения ответа для одной попытки сбора.
Не означает
Timeout не задаёт частоту новых scrape и не описывает скорость прикладного запроса /products.
Связь с up
Превышение timeout делает scrape неудачным; последующий служебный ряд up отражает этот результат.

Даже успешный scrape не превращает промежуток до следующего опроса в наблюдаемый. Посмотрим, что именно известно Prometheus между двумя точками.

§6Что происходит между опросами

Почему временной ряд состоит из снимков, а не из непрерывной записи.

В 10:00:00 counter равен 7, а в 10:00:05 — 10. В базе сохранены две точки. Отдельные события между этими моментами не записываются. Эту детализацию дают трасса или лог конкретного запроса; scrape counter хранит периодические отсчёты.

Периодический опрос создаёт ряд снимков состояния. Меньший интервал даёт больше точек и чаще нагружает target. Больший интервал снижает число запросов и увеличивает промежуток между снимками.

Значит, один ручной запрос тоже даёт лишь снимок. Сравним его с регулярным scrape.

§7Один запрос и история

Почему curl /metrics нужен для проверки endpoint, но не заменяет Prometheus.

Ручной curl полезен: он показывает, отвечает ли endpoint и как выглядит text exposition сейчас. Но вывод терминала исчезает после команды, Prometheus не добавляет к нему время, метки target и следующий отсчёт. Поэтому такой запрос проверяет источник, а регулярный scrape строит историю.

curl /metricsрегулярный scrape
Кто запускаетчеловек в терминалепланировщик Prometheus
Сколько точекодин снимок выводановая точка по расписанию
Где результаттерминалTSDB Prometheus
Что ещё появляетсятолько ответ endpointслужебный ряд up и метки target

После такой проверки нужно оставить Prometheus работать несколько интервалов. Тогда выражение в его интерфейсе сможет показать ряд не только в один момент, но и за выбранный диапазон времени.

Закрепим эту цепочку на counter стенда: сначала создадим изменение, затем увидим несколько отсчётов.

§8Несколько отсчётов одного ряда

Как соединить действие в API, scrape и точки в Prometheus.

Endpoint стенда увеличивает lab_http_requests_total после завершения запроса к /products. Если выполнить два успешных запроса, counter вырастет. Следующий scrape заберёт новое значение. Предыдущая точка в базе останется прежней: Prometheus не переписывает историю counter задним числом.

В интерфейсе Prometheus переключите вкладку с мгновенного значения на график и выберите диапазон, который охватывает несколько интервалов. Результат — последовательность точек одного ряда. Если значение не изменялось, соседние точки могут иметь одно и то же число: это всё равно разные отсчёты в разные моменты.

Теперь повторите опыт на стенде и проверьте, что время scrape действительно отделяет действие приложения от появления точки.

§9Практика

Наблюдаем изменение counter и несколько сохранённых отсчётов.

Задача 1. Проверьте расписание

Запустите API и Prometheus из папки observability/lab, как в лекции 3.1. Откройте http://127.0.0.1:9095/targets и найдите строку telemetry-lab. Сравните время Last scrape дважды с паузой немного больше пяти секунд.

Что нужно получить

Время последнего scrape изменится. Это подтверждает, что Prometheus сам повторяет опрос target по расписанию.

Проверка

Если строка остаётся DOWN, сначала откройте http://127.0.0.1:8015/metrics. Endpoint должен отвечать, а target стенда должен оставаться host.docker.internal:8015.

Задача 2. Увидьте новую точку counter

Выполните два запроса, затем подождите немного больше одного интервала и постройте график запроса из §8 за последние несколько минут.

Что нужно получить

После ближайшего успешного scrape ряд lab_http_requests_total со статусом 200 будет содержать значение не меньше предыдущего и новую точку на графике.

Почему значение появилось не мгновенно?

Counter меняется в процессе API сразу после запроса. Prometheus узнаёт новое значение только при следующем плановом scrape, затем записывает отсчёт в TSDB.

§10Проверьте себя

Вопросы по циклу сбора. Ответ раскрывается щелчком.

Что такое scrape?

Один запрос Prometheus к target, получение и разбор ответа с метриками, затем запись отсчётов. Один scrape может создать точки для многих рядов.

Кто начинает запрос в pull-модели Prometheus?

Prometheus. Приложение предоставляет endpoint /metrics и отвечает на запрос, но не отправляет метрики Prometheus по собственной инициативе.

Чем scrape_interval отличается от scrape_timeout?

Интервал задаёт частоту плановых попыток. Timeout ограничивает максимальное ожидание одного уже начатого scrape.

Почему один curl не заменяет сбор Prometheus?

Он показывает один ответ endpoint в терминале. Регулярный scrape создаёт временной ряд: сохраняет последовательность отсчётов с временем, метками target и служебным состоянием связи.
