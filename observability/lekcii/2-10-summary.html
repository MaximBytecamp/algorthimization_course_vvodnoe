§1Summary в Python

Что отдаёт Summary в prometheus-client и чего в нём нет.

Четвёртый основной тип метрик — Summary («сводка»). В описании Prometheus это тип, который считает перцентили прямо в приложении. Проверим, что он делает в библиотеке для Python. Отдадим ему те же 20 отчётов, что гистограмме в лекции 2.8:

Summary("report_duration_seconds", …)Аргументы те же, что у Histogram, но без границ корзин.
duration.observe(seconds)Наблюдение передают так же, есть и time().

В ответе всего две строки значений: _count — 20 и _sum — 8,87. Корзин и перцентилей нет. Опыт поставлен правильно: Summary в Python-библиотеке хранит только количество и сумму. Сравним с гистограммой из лекции 2.8:

Слева — корзины, по которым видно распределение и оценивается перцентиль. Справа — только сумма и количество. Из них получается одно среднее: 8,87 / 20 = 0,44 с. Это то самое число из лекции 2.8, §1, которое не похоже ни на один отчёт.

Вывод

В prometheus-client для Python Summary хранит только _count и _sum. Перцентилей и корзин в нём нет.

§2Метка quantile занята

Как Summary с перцентилями выглядит в других библиотеках и почему метку quantile нельзя взять себе.

В библиотеках для некоторых других языков, например для Go, у Summary есть ещё одна часть. Приложение само считает заданные перцентили по последним наблюдениям и отдаёт их строками с меткой quantile, например report_duration_seconds{quantile="0.95"} 1.4. В Python этой части нет, но метка quantile всё равно зарезервирована. Проверим:

Библиотека не дала создать Summary с меткой quantile: имя занято под перцентили, даже если Python их не отдаёт. Текст ошибки напечатан с опечаткой — methe fric вместо metric. Это не искажение при копировании: так написано в самой библиотеке 0.26.0, в файле validation.py, строка 112. Найти её можно командой grep -n "Reserved label" .venv/lib/python3.12/site-packages/prometheus_client/validation.py. Опечатки встречаются и в популярных библиотеках, поэтому текст ошибки ищут по ключевым словам.

Вывод

Метка quantile у Summary зарезервирована под перцентили. В Python их нет, но и своей такой метки завести нельзя.

Даже там, где Summary отдаёт перцентили, у них есть ограничение, знакомое по лекции 2.8.

§3Перцентили из приложения не складываются

Почему готовые перцентили экземпляров нельзя объединить.

Summary с перцентилями отдаёт уже посчитанный p95 каждого экземпляра. Распределения в ответе нет — только итоговое число. Возьмём три экземпляра из лекции 2.8, §7 и посмотрим, что можно сделать с их готовыми p95:

reported = {…}Так получает данные Prometheus при Summary с перцентилями: по одному готовому числу от каждого.
sum(…) / 3, max(…)Две попытки получить общий p95 из готовых чисел.
exact(0.95, fast + slow + fast)Настоящий общий p95 — для сравнения. Prometheus его посчитать не может: отдельных значений у него нет.

Среднее готовых p95 — 0,689, максимум — 1,9, а на самом деле 1,7. Ни одна операция над готовыми перцентилями не даёт правильного ответа. Пересчитать тоже нельзя: отдельных значений нет. Гистограмма в той же ситуации отдавала корзины, и сложение корзин дало 2,05 — грубо, но из общего распределения. Поэтому длительность в сервисах из нескольких экземпляров хранят гистограммой.

Вывод

Готовые перцентили экземпляров не объединяются: среднее и максимум дают неверный ответ. Если экземпляров несколько, длительность хранят гистограммой.

Зачем тогда Summary в Python? У него есть одно достоинство — цена.

§4Когда Summary в Python полезен

Сколько рядов стоят Summary и Histogram и когда хватает среднего.

Посчитаем ряды обоих типов с одной меткой route на трёх адресах, как в лекции 2.8, §8:

Summary — 6 рядов: _count и _sum на адрес. Гистограмма с границами по умолчанию — 51, в восемь с половиной раз больше. Если нужно только среднее за окно, Summary даёт его теми же приростами, что гистограмма в лекции 2.8, §4: Δ_sum / Δ_count. И обходится в 8,5 раза дешевле. Так бывает для величин, где распределение не важно: средний размер ответа в байтах, среднее число строк в отчёте.

Вывод

Summary в Python — дешёвый способ знать среднее за окно. Для длительности, где важны медленные запросы, его не хватает: нужна гистограмма.

Кроме четырёх основных, в библиотеке есть ещё два типа для особых случаев.

§5Info и Enum

Как отдать версию приложения и текущее состояние из списка.

Иногда нужно отдать текст: версию приложения, номер коммита. Или состояние, одно из нескольких: «ждёт», «выполняется», «упала». Для этого в библиотеке есть Info и Enum. Оба в ответе превращаются в gauge:

Info("app_build", …).info({…})Текст передают метками; значение всегда 1. К имени добавляется _info.
Enum(…, states=[…])Список возможных состояний задают при создании.
state.state("running")Текущее состояние получает 1, остальные — 0.

app_build_info — одна строка, в метках версия и коммит, значение 1. По ней видно, какая версия работает на каждом экземпляре: в лекции 1.6 как раз версия 2.15.0 оказалась подсказкой к сбою. export_state — три строки, по одной на состояние: у running 1, у остальных 0. Так состояние можно показывать на графике и проверять условием «failed равно 1».

Вывод

Info отдаёт текст метками со значением 1, Enum — одно текущее состояние из заданного списка. В ответе оба — gauge.

Типов шесть. Соберём правило выбора.

Пять вопросов, которые приводят к нужному типу.

Тип выбирают по вопросу, на который метрика должна отвечать. На схеме — порядок вопросов:

Вопросы идут сверху вниз. Текст и состояние отсеиваются первыми, потому что у них нет числа в обычном смысле. §8Практика

Три задачи. Решение спрятано под задачей.

Задача 1. Выберите тип

Ситуация: в сервисе рассылки нужно измерять:

  • сколько писем отправлено;
  • сколько писем ждёт в очереди;
  • сколько времени занимает отправка, с вниманием к медленным;
  • средний размер письма в байтах;
  • версию сервиса;
  • состояние соединения с почтовым сервером: «нет», «подключается», «есть».
Что нужно сделать

Назвать тип для каждой величины по вопросам §6.

Решение

Отправлено — Counter. Ждёт — Gauge. Время отправки — Histogram: важны медленные. Средний размер — Summary: хватит среднего. Версия — Info. Состояние соединения — Enum.

Задача 2. Среднее из Summary за окно

Ситуация: в 12:00 у Summary _count 400 и _sum 20,0; в 12:05 — 520 и 50,0.

Что нужно сделать

Найти среднее за всё время и за эти 5 минут.

Решение

За всё время: 50 / 520 ≈ 0,096. За окно: (50 − 20) / (520 − 400) = 30 / 120 = 0,25. Прежнее среднее было 20 / 400 = 0,05, новые наблюдения в 5 раз больше, а общее среднее выросло только до 0,096.

Задача 3. Смена состояния

Ситуация: Enum export_state из §5 в состоянии running. Выгрузка упала, вызвали state.state("failed").

Что нужно сделать

Записать три строки значений после вызова.

Решение

export_state{export_state="idle"} 0.0, …="running"} 0.0, …="failed"} 1.0: единица переходит к новому состоянию, прежнее становится 0.

§9Проверьте себя

Вопросы по лекции. Ответ раскрывается щелчком.

Что отдаёт Summary в prometheus-client для Python?

Только _count и _sum, и ещё _created.

Почему готовые p95 экземпляров нельзя объединить?

В них нет распределения. Среднее (0,689) и максимум (1,9) не дают настоящего общего p95 (1,7).

Зачем Summary, если есть Histogram?

Он дешевле: 2 ряда на сочетание меток против 17 у гистограммы по умолчанию. Хватает, когда нужно только среднее.

Какое значение у строки Info?

Всегда 1. Сведения записаны в метках.

Какой тип для длительности в сервисе из трёх экземпляров?

Histogram: корзины экземпляров складываются, и по сумме оценивается общий перцентиль.

§11Глоссарий

Термины лекции, включая понятия прежних лекций: формулировка, пример и рисунок.

Counter

Примерhttp_requests_total.

Gauge

Метрика с числом, которое растёт и уменьшается: состояние сейчас.

Примерorders_queue_length.

Гделекция 2.7

Histogram

Метрика, которая раскладывает наблюдения по корзинам и хранит _sum и _count.

Примерreport_duration_seconds_bucket{le="0.5"} 16.

Гделекции 2.8–2.9

Summary

Метрика наблюдений с _sum и _count. В некоторых библиотеках ещё и перцентили, посчитанные в приложении; в Python — нет.

Пример20 отчётов: _count 20, _sum 8,87.

Гделекция 2.10, §1

Info

Метрика с текстовыми сведениями в метках и значением 1.

Примерapp_build_info{version="2.15.0"} 1.0.

Гделекция 2.10, §5

Enum

Метрика текущего состояния из заданного списка: у текущего 1, у остальных 0.

Примерexport_state{export_state="running"} 1.0.

Гделекция 2.10, §5

Итог лекции

Summary в prometheus-client для Python хранит только _count и _sum: перцентилей в нём нет, а метка quantile зарезервирована. В других библиотеках Summary считает перцентили в приложении, но такие перцентили экземпляров не объединяются: среднее и максимум трёх p95 дают 0,689 и 1,9 при настоящих 1,7. Поэтому для длительности берут Histogram, а Summary в Python — дешёвый способ знать среднее за окно, 2 ряда вместо 17. Для текста о приложении есть Info, для одного состояния из списка — Enum. Тип выбирают вопросами сверху вниз: текст, состояние, события, значение сейчас, распределение или среднее.
