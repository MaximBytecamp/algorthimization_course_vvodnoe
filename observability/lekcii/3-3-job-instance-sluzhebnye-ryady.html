§1Ряд и его подпись

Почему одного имени метрики недостаточно для поиска нужного измерения.

В стенде endpoint отдаёт counter lab_http_requests_total. В его строке уже есть метки route и status. После scrape Prometheus сохраняет это число вместе с ещё двумя метками: job и instance.

Имя метрики сообщает, что измеряется. Метки уточняют, к какому маршруту, статусу, заданию и адресу относится значение. Следующие два раздела разбирают метки, которые добавляет Prometheus.

§2Метка job

Как имя задания из YAML становится частью каждого собранного ряда.

В prometheus.yml target стенда находится внутри задания telemetry-lab. Поэтому при scrape Prometheus добавляет к собранным отсчётам job="telemetry-lab". Job объединяет ряды target, которые относятся к одному заданию сбора.

job_nameИмя группы target в конфигурации.
job="telemetry-lab"Метка, которую получают ряды успешного scrape этого задания.

Job полезен, когда один Prometheus собирает несколько групп сервисов. Чтобы различить адреса внутри одной группы, нужна отдельная метка.

§3Метка instance

Как сохранить адрес конкретного target.

instance хранит адрес target, к которому обращался scrape. В стенде это host.docker.internal:8015. Если в том же job появятся два адреса, их прикладные метрики будут разделены значением instance.

На стенде target один, поэтому у всех его рядов instance одинаковый. Метка остаётся необходимой: она связывает ряд с конкретным адресом и позволяет отличить результат одного endpoint от другого.

§4Метки из endpoint и scrape

Два источника меток в одной строке результата.

API формирует прикладные метки. В app.py counter получает route="/products" и status="200" или status="500". Prometheus добавляет job и instance по конфигурации и target.

МеткаИсточникЗначение стенда
routeответ API/products
statusответ API200 или 500
jobконфигурация Prometheustelemetry-lab
instanceадрес targethost.docker.internal:8015

Обе группы меток остаются в одном ряду. Прикладные метки отвечают на вопрос о работе API. Метки scrape отвечают на вопрос, откуда Prometheus получил измерение. Теперь рассмотрим ряды, которые Prometheus создаёт сам.

§5Служебные ряды

Какие измерения создаёт сам процесс сбора.

После scrape Prometheus публикует ряд up. Значение 1 означает успешную последнюю попытку, 0 — неуспешную. У него есть те же job и instance, поэтому состояние можно отнести к конкретному target.

Также Prometheus записывает показатели scrape: длительность, число полученных образцов и число добавленных рядов. Эти ряды начинаются с scrape_ и помогают отделить неполадку endpoint от неполадки самого сбора.

Служебные ряды не заменяют прикладные метрики. Они описывают доступность и работу пути Prometheus → target. Чтобы читать их без смешения target, нужно записать условия выбора полностью.

§6Выбор ряда

Как фильтр по job и instance делает запрос однозначным.

Выражение up без условий может вернуть target других заданий. Фильтр по job ограничивает выбор группой стенда. Фильтр по instance оставляет конкретный endpoint внутри этой группы.

Служебный рядизмерение процесса сбора

Ряд, который Prometheus создаёт при scrape. Endpoint не содержит эту строку в своём ответе.
Пример

Метки
job и instance указывают задание и адрес этой попытки.

Эти фильтры опираются на уже известный список target. В следующей лекции появятся правила, которые меняют метки до сохранения и после обнаружения адресов.

§8Проверьте себя

Ответы раскрываются щелчком.

Откуда берётся job?

Из job_name задания scrape в конфигурации Prometheus.

Что хранит instance?

Адрес конкретного target, к которому выполнялся scrape.

Чем up отличается от counter API?

up создаёт Prometheus и он описывает последний scrape. Counter API отдаёт endpoint и он описывает запросы /products.
