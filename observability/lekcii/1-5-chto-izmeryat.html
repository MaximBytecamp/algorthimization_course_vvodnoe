Что измерять: золотые сигналы, RED, USE

Лекции 1.2–1.4 разобрали, как измерять и хранить. Остался вопрос, что измерять у сервиса, чтобы не пропустить проблему. §1Стандартный осмотр

Почему у показателей сервиса есть стандартный набор.

На медосмотре врач не измеряет всё, что можно измерить. У него стандартный набор: пульс, давление, температура. Набор небольшой, но по нему видно большинство проблем, и после него ясно, какие анализы назначать дальше. У сервиса тоже есть стандартные наборы показателей. Их составили инженеры, которые разбирали сбои многих систем и заметили, что почти каждый сбой виден на нескольких одних и тех же числах.

Наборы опираются на то, что сервис обещает пользователю. В лекции 1.1 таких обещаний было четыре: доступность, производительность, надёжность и корректность. Показатель нужен там, где обещание может нарушиться незаметно. Разберём три набора:

Первые два набора, голубые, описывают работу сервиса со стороны запросов: сколько их, сколько ошибок, сколько ждать. Третий, белый, описывает её со стороны ресурсов: процессора, памяти, обработчиков, соединений с базой. Названия RED и USE составлены из первых букв английских слов.

Чтобы сравнить наборы, нужен сервис, у которого есть и запросы, и ресурсы, способные кончиться. Опишем стенд.

§2Стенд заказов

Как устроен сервис заказов и где в нём могут возникнуть проблемы.

Стенд lab-orders принимает заказы. API на FastAPI не оплачивает заказ сам: он записывает заказ, ставит задание в очередь — список заданий, которые ждут обработки, — и сразу отвечает кодом 202 Accepted («принято»). Оплату выполняет отдельный процесс — обработчик очереди (воркер) Celery. Он берёт задания из очереди и обращается к платёжному шлюзу. Путь заказа:

Слева клиент получает ответ 202 за пару миллисекунд: API только записал заказ и положил задание в очередь. Дальше заказ ждёт в очереди, пока освободится один из двух слотов обработчика — мест, где задание выполняется. Одно задание занимает слот около 0,4 секунды: проверка заказа 0,05 с, обращение к шлюзу 0,25 с, запись результата 0,1 с. Шлюз смоделирован: долю его отказов можно задать, и обработчик повторяет неудачное обращение до трёх раз. Вот как API принимает заказ:

store.hset(...)Записать заказ в Redis со статусом accepted — «принят».
process_order.apply_async(...)Поставить задание оплаты в очередь. Последний аргумент time.time() — момент постановки: по нему обработчик потом посчитает, сколько задание ждало.
orders_created...inc()Прибавить единицу к числу принятых заказов.
status_code=202Ответ «принято»: заказ записан, но ещё не оплачен.

Код ответа 202 не говорит, оплачен ли заказ. Он говорит только, что заказ попал в очередь. Поэтому на этом стенде видно, где одни показатели молчат, а другие нет. Стенд запускается так (Redis уже работает на порту 6389, зависимости из requirements.txt установлены):

--concurrency 2 задаёт два слота, --pool threads — выполнять задания в потоках одного процесса, чтобы его /metrics на порту 8026 видел, сколько слотов занято. У API свой /metrics на порту 8025.

Стенд описан. Начнём с самого общего набора показателей.

§3Четыре золотых сигнала

Какие четыре показателя нужны почти любому сервису.

Четыре золотых сигналаfour golden signals
Что это
Набор из четырёх показателей, который инженеры Google предложили в книге о надёжности сервисов (Site Reliability Engineering, 2016): задержка, трафик, ошибки, насыщение.
Что даёт
Если можно измерить только четыре числа, по ним видно большинство проблем сервиса, который отвечает пользователям.
Пример
Для API стенда: длительность ответа, запросов в секунду, доля ответов 5xx, длина очереди.

Разберём каждый сигнал и найдём его на стенде заказов:

СигналВопросНа стенде
задержка (latency)сколько ждать ответадлительность POST /orders; время ожидания задания в очереди
трафик (traffic)сколько работы поступаетзапросов в секунду; принятых заказов в секунду
ошибки (errors)какая доля работы не удаласьдоля ответов 5xx; отказы шлюза и отклонённые заказы
насыщение (saturation)насколько заняты ограниченные ресурсызанятые слоты обработчика; длина очереди

Первые три сигнала описывают поток работы, четвёртый — запас. Насыщение отвечает на вопрос «сколько ещё выдержит сервис». Пока ресурс занят наполовину, лишняя нагрузка поместится. Когда он занят полностью, новая работа встаёт в очередь, и задержка растёт. Поэтому насыщение часто предупреждает о проблеме раньше, чем растёт задержка. На схеме — как насыщение связано с остальными тремя сигналами:

Трафик слева приходит в ресурс. Если у ресурса есть запас, верхняя стрелка: работа выполняется сразу, задержка мала. Если ресурс занят полностью, нижняя стрелка: работа ждёт, задержка растёт, а когда клиенты перестают ждать, появляются ошибки. Отсюда правило: задержку и ошибки смотрят вместе с насыщением, иначе не понять, почему они выросли.

Вывод

Задержка, трафик и ошибки описывают поток работы, насыщение — запас ресурсов. Насыщение растёт раньше, чем задержка.

Золотые сигналы — общий набор. Для частей сервиса, которые принимают запросы, есть более узкий набор — RED.

§4RED: показатели запросов

Три показателя для всего, что принимает запросы.

REDRate, Errors, Duration
Что это
Три показателя для каждой части сервиса, которая принимает запросы: частота запросов (rate), ошибки (errors), длительность (duration). Набор предложил Том Уилки в 2015 году.
Что даёт
Одинаковый набор для каждого маршрута, сервиса и обработчика заданий: панели всех сервисов устроены одинаково.
Пример
У POST /orders: запросов в секунду, ответов 5xx, миллисекунд на запрос.

RED — это первые три золотых сигнала, сформулированные для одного вида работы: запроса. Насыщения в нём нет, потому что запрос — не ресурс. Посчитаем RED для API стенда. Программа watch.py каждые 5 секунд читает /metrics API и обработчика и печатает разницу с прошлым измерением — как collect.py и window.py в лекции 1.2:

read(url)Читает текст /metrics и возвращает словарь «строка ряда → число».
total(values, prefix, part)Складывает все ряды, имя которых начинается с prefix и содержит part. Так из рядов по кодам ответа получается общее число запросов к /orders.
d = {k: now[k] - before[k] ...}Разница двух измерений — сколько прибавилось за 5 секунд. Это окно из лекции 1.2.
rate, d["http_5xx"], msТри буквы RED: запросов в секунду, ошибок за окно, средняя длительность — сумма секунд, делённая на число запросов.

Нагрузку подаёт программа phases.py из той же папки: четыре фазы с разным числом заказов в секунду. Во время первой фазы на стенд шло 3 заказа в секунду. Колонки RED из вывода watch.py:

Частота — 3 запроса в секунду, как и задано. Ошибок 0. Средняя длительность ответа — 2–3 мс. По RED API в полном порядке.

Вывод

RED — частота, ошибки и длительность — одинаково считается для любого маршрута и любого обработчика. Его берут из счётчика запросов и суммы длительностей за окно.

Разберём расчёт RED по шагам на одном окне.

§4.1Пример по шагам: RED из двух снимков

Как три буквы RED получаются из трёх строк /metrics.

В watch.py расчёт RED спрятан в нескольких строках. Разберём его вручную на одном окне. Программа сняла /metrics API дважды, с разницей 5 секунд. Нужны три числа: сколько всего запросов, сколько с кодом 5xx и сумма их длительностей в секундах. Числа придуманы для примера, но близки к фазе наплыва на стенде:

Счётчики в снимках растут с запуска процесса, поэтому сами по себе ничего не говорят об окне. Справа — разница: за 5 секунд пришло 55 запросов, одна ошибка, и вместе они шли 0,110 секунды. Из этих трёх разностей получаются три буквы:

rateR — частота: разница числа запросов, делённая на длину окна. 55 / 5 = 11.
errorsE — ошибки: разница счётчика 5xx. Долю считают от числа запросов за то же окно, как в лекции 1.2.
duration_msD — длительность: сколько секунд прибавилось к сумме, делённое на число запросов. 0,110 / 55 = 0,002 с = 2 мс. Это средняя длительность за окно.

Все три буквы получились из разностей. Если вместо разности взять само значение счётчика — 1055 запросов, — выйдет «211 в секунду». Это число за всё время работы, делённое на 5 секунд. Поэтому RED всегда считают за окно.

Вывод

RED за окно — три разности двух снимков: число запросов, число ошибок, сумма длительностей. Частота — первая разность, делённая на окно; длительность — третья, делённая на первую.

Посмотрим, что покажет RED, когда заказов станет больше, чем обработчик успевает оплатить.

§5Наплыв заказов: RED молчит

Что происходит с очередью, пока API отвечает за 2 мс.

Во второй фазе опыта на стенд 30 секунд шло 11 заказов в секунду. Два слота по 0,4 секунды на задание теоретически оплачивают 5 заказов в секунду; на стенде вышло 4. Затем 50 секунд шёл 1 заказ в секунду, и очередь разбиралась. Выведем RED API вместе с очередью и временем ожидания в ней:

Колонки RED — частота, ошибки, длительность — в порядке: 11 запросов в секунду, 0 ошибок, 2 мс. А правее всё иначе. Принято 11 заказов в секунду, оплачено 4. Разница копится в очереди: за 30 секунд наплыва она выросла до 201 задания. Время ожидания в очереди дошло до 49 секунд. Покажем это двумя рисунками на общей шкале времени. Сначала то, что показывает RED:

Синяя ступенька — частота запросов по фазам: 3, 11, 1 и 2,5 в секунду. Длительность ответа всё время около 2 мс, ошибок ноль. По этому рисунку сбоя нет. Теперь на той же шкале — очередь:

Во время наплыва оранжевая линия очереди поднимается почти прямо: каждые 5 секунд в очередь прибавляется около 35 заданий — 11 пришло в секунду, 4 ушло. На пике 201 задание. Когда наплыв кончился, линия идёт вниз со скоростью около 3 заданий в секунду — обработчик оплачивает 4, приходит 1. Ожидание продолжает расти: задания, попавшие в конец очереди на пике, стоят дольше всех, и последние из них ждали 49 секунд. Пользователь, который оформил заказ в этот момент, ответ 202 получил за 2 мс, а оплату — почти через минуту.

Вывод

RED у API показывает только приём заказов. Проблема оказалась за очередью: обработчик был занят полностью, задания копились, ожидание дошло до 49 секунд. Чтобы её увидеть, нужны показатели ресурса — обработчика и его очереди.

Посчитаем рост очереди по секундам.

§5.1Пример по шагам: как растёт очередь

Очередь и ожидание по секундам.

Почему за 30 секунд наплыва очередь выросла до двухсот заданий? Посчитаем по секундам. Каждую секунду приходит 11 заказов, обработчик оплачивает 4 — как на стенде. Всё, что не оплачено, остаётся в очереди. Последнее задание очереди ждёт, пока обработчик пройдёт всех перед ним: длина очереди, делённая на 4 в секунду.

queue += arrive - served — главная строка: каждую секунду очередь прибавляет разницу между тем, что пришло, и тем, что ушло. Та же арифметика столбиками:

Столбики растут ступеньками по 7 заданий. Оранжевая верхушка последнего — те 7 заказов, что не успели оплатить в шестую секунду. За 5 секунд очередь выросла на 35 — ровно столько прибавлялось на стенде между строками watch.py в §5. За 30 секунд по расчёту набралось бы 210, на стенде — 201: близко к расчёту.

Ожидание растёт вместе с очередью: к шестой секунде последнее задание ждёт 10,5 секунды, хотя каждый заказ оплачивается за 0,4 секунды. Время работы у заказа прежнее — выросло только время в очереди. Его RED у API не показывает.

Вывод

Если приходит больше, чем уходит, очередь растёт на разницу каждую секунду, а ожидание — пропорционально очереди. Пока поток не упадёт ниже мощности обработчика, очередь сама не уменьшится.

Показатели ресурсов собирает третий набор — USE.

§6USE: показатели ресурсов

Три вопроса к каждому ресурсу.

У кассы в магазине три состояния, о которых стоит знать управляющему. Как часто кассир занят. Сколько людей стоит в очереди. Сколько раз за день касса ломалась. Если кассир занят всё время и очередь растёт, нужна вторая касса, даже если каждый покупатель обслуживается быстро. То же спрашивают о любом ресурсе сервиса.

USEUtilization, Saturation, Errors
Что это
Три вопроса к каждому ресурсу: загрузка (utilization) — какую долю времени ресурс занят; насыщение (saturation) — сколько работы ждёт, потому что ресурс занят; ошибки (errors) — сколько раз ресурс отказал. Метод описал Брендан Грегг в 2012 году.
Что даёт
Ресурс, который кончился, находят перебором: для каждого ресурса — три числа.
Пример
Обработчик стенда: занято 2 слота из 2, в очереди 201 задание, отказов шлюза 0.

Применим USE к обработчику стенда в момент пика наплыва, на 70-й секунде:

Слева оба слота оранжевые: загрузка 100%. Сама по себе полная загрузка — ещё не беда: значит, обработчик работает без простоя. Беду показывает средний блок: 201 задание ждёт, потому что свободных слотов нет. Это насыщение. Справа ошибок ноль: ресурс не ломался, его не хватило. Вывод из трёх чисел: обработчику нужно больше слотов или больше экземпляров. RED API к этому выводу не вёл.

USE применяют к каждому ресурсу, который может кончиться. Для типичного сервиса:

РесурсЗагрузкаНасыщениеОшибки
обработчик очередизанятые слоты из всехдлина очереди, время ожидания в нейотказы заданий
процессордоля времени занятпроцессы, ждущие процессораредки; чаще не смотрят
памятьзанятая долявытеснение на дискпроцесс убит из-за нехватки памяти
соединения с базойзанятые из пулазапросы, ждущие свободного соединенияошибки подключения
Вывод

USE задаёт три вопроса каждому ресурсу. Полная загрузка без очереди — нормальная работа; загрузка вместе с растущей очередью — нехватка ресурса.

В третьей фазе опыта ресурс в порядке, но отказывает внешняя система. Посмотрим, что видно на этот раз.

§7Отказ платёжного шлюза

Где видны ошибки, которые не доходят до HTTP.

В последней фазе опыта 60 секунд шло 2,5 заказа в секунду, а платёжный шлюз отказывал в половине обращений. Обработчик повторяет неудачное обращение до трёх раз, и только после четвёртой неудачи отклоняет заказ. Колонки вывода:

RED у API опять в порядке: 0 ошибок, 2 мс. Клиент на каждый заказ получил 202. Но за минуту набралось 122 повтора обращения к шлюзу, и 4 заказа отклонены окончательно. Очередь не уходит ниже 46: каждый повтор снова занимает слот, и обработчику не хватает мощности даже на 2,5 заказа в секунду. Посмотрим, на каком уровне видна каждая проблема:

На верхнем уровне — HTTP — проблемы нет: API только принимает заказы и к шлюзу не обращается. На среднем уровне — задание оплаты — она видна по повторам и насыщению. На нижнем — бизнес — виден результат: 4 заказа не оплачены. Отсюда два правила. Первое: RED считают не только для HTTP, но и для каждого вида заданий — частота заданий, отказы и повторы, длительность выполнения. Второе: кроме технических показателей, нужны бизнес-метрики — числа о том, ради чего сервис существует: принятые, оплаченные и отклонённые заказы.

Вывод

Ошибка внутри фоновой обработки не попадает в HTTP-код. Её видно по RED заданий и по бизнес-метрикам: повторы, отказы, разница между принятыми и оплаченными заказами.

Остался один подвох внутри самого RED: как считать длительность, если часть запросов падает.

§8Задержка успешных и ошибочных запросов

Почему длительность успешных и неуспешных запросов меряют отдельно.

Ошибка часто возвращается быстро. Если база не принимает подключения, запрос падает за 5 мс вместо обычных 300. В книге Google поэтому советуют считать задержку успешных и ошибочных запросов отдельно. Посчитаем на примере: 90 успешных запросов по 300 мс и 10 ошибок по 5 мс. Числа придуманы для примера:

Верхняя и нижняя полосы одинаковые: для успешных запросов ничего не изменилось. Средняя полоса короче — общая средняя «улучшилась» как раз во время сбоя. Поэтому длительность в RED делят по результату: отдельно для успешных запросов, отдельно для ошибочных, а ошибки считают отдельным показателем.

Вывод

Быстрые ошибки снижают общую длительность. Длительность успешных и ошибочных запросов показывают раздельно.

Все три набора разобраны. Соберём из них карту показателей стенда.

§9Карта показателей сервиса

Какой набор к какой части сервиса применять.

Наборы не соревнуются: каждый применяют к своей части сервиса. На схеме стенд из §2 с подписями — какой набор где:

Над каждым блоком — набор, который к нему применяют. API принимает запросы — для него RED. Очередь — это насыщение обработчика, её длину и время ожидания относят к USE. Обработчик и принимает работу, и сам является ресурсом, поэтому у него оба набора: RED заданий и USE слотов. Обращения к шлюзу — тоже запросы, только исходящие: для них RED вызовов — сколько, сколько неудачных, как долго. Снизу во всю ширину — бизнес-метрики: они не привязаны к одному блоку и показывают результат всего пути. Вот эти показатели в виде таблицы, с именами метрик стенда:

§11Практика

Три задачи на то, что разобрано в лекции. Решение спрятано под задачей.

Задача 1. Разложите показатели по наборам

Ситуация: у сервиса рассылки писем есть показатели:

  • писем отправлено в секунду;
  • доля писем, которые почтовый сервер не принял;
  • занятые соединения с почтовым сервером из 10;
  • сколько писем ждёт отправки;
  • время от постановки письма до отправки.
Что нужно сделать

Для каждого показателя назвать набор (RED или USE) и букву.

Решение

Писем в секунду — RED, R (частота). Доля непринятых — RED, E (ошибки). Занятые соединения — USE, U (загрузка). Ждущие письма — USE, S (насыщение). Время до отправки — задержка письма, RED, D. Если она растёт вместе с числом ждущих писем, это признак насыщения.

Задача 2. Сколько ждать

Ситуация: обработчик стенда оплачивает 4 заказа в секунду. В очереди 120 заданий, новые заказы не поступают.

Что нужно сделать

Посчитать, сколько секунд будет ждать последнее задание очереди, и сколько — если число слотов увеличить вдвое.

Решение

120 / 4 = 30 секунд. Если удвоить слоты, обработчик будет оплачивать около 8 заказов в секунду: 120 / 8 = 15 секунд. Это оценка: на стенде два слота дали 4 заказа в секунду вместо расчётных 5, и при большем числе слотов узким местом может стать сам шлюз.

Задача 3. Всё зелёное

Ситуация: на панели сервиса заказов — только RED API. Все три показателя в норме. Поддержка получает жалобы, что заказы висят в статусе «принят».

Что нужно сделать

Назвать три показателя, которые нужно посмотреть первыми, и что каждый может показать.

Решение

Длину очереди и время ожидания в ней — насыщение обработчика, как в §5. Занятые слоты обработчика — если 0 из 2, обработчик остановлен; если 2 из 2, ему не хватает мощности. Разницу между принятыми и оплаченными заказами и число отклонённых — бизнес-результат, как в §7.

§12Проверьте себя

Вопросы по лекции. Ответ раскрывается щелчком.

Назовите четыре золотых сигнала.

Задержка, трафик, ошибки, насыщение.

Почему во время наплыва RED у API был в норме?

API только записывает заказ и ставит задание в очередь — это занимает 2 мс при любой нагрузке. Нехватка мощности была у обработчика, за очередью.

Обработчик занят на 100%, очередь пуста. Это проблема?

Нет. Обработчик работает без простоя и успевает. Проблема — когда к полной загрузке добавляется растущая очередь.

Почему 122 повтора не означают 122 потерянных заказа?

Повтор — это новая попытка обращения к шлюзу. Заказ отклоняется только после четырёх неудачных попыток; таких на стенде было 4.

Почему средняя длительность может упасть во время сбоя?

Ошибки часто возвращаются быстрее успешных запросов. В общей средней они тянут её вниз.

§14Глоссарий

Термины лекции, включая понятия из лекций 1.1–1.4: формулировка, пример и рисунок.

Метрикаmetric

Число, которое описывает много событий сразу и хранится как временной ряд.

Примерorders_queue_depth — заданий в очереди.

Гделекция 1.4, §2

Окно времениtime window

Промежуток, за который складывают измерения. Количество за окно — разница двух измерений растущего числа.

Примерwatch.py считает запросы за 5 секунд.

Гделекция 1.2, §7

Четыре золотых сигналаfour golden signals

Задержка, трафик, ошибки и насыщение — общий набор показателей для сервиса, который отвечает пользователям.

Пример2 мс, 11 запросов/с, 0 ошибок, 201 задание в очереди.

Гделекция 1.5, §3

REDRate, Errors, Duration

Частота, ошибки и длительность — набор для каждой части сервиса, которая принимает или отправляет запросы.

ПримерPOST /orders: 11 запросов/с, 0 ошибок, 2 мс.

Гделекция 1.5, §4

USEUtilization, Saturation, Errors

Загрузка, насыщение и ошибки — три вопроса к каждому ресурсу, который может кончиться.

Примеробработчик: 2 из 2 слотов, 201 задание ждёт, 0 ошибок.

Гделекция 1.5, §6

Насыщениеsaturation

Сколько работы ждёт, потому что ресурс занят полностью. Обычно видно по длине очереди и времени ожидания.

Примерна пике наплыва 201 задание ждало до 49 секунд.

Гделекция 1.5, §3, §6

Очередь и обработчикqueue, worker

Очередь — список заданий, которые ждут обработки. Обработчик — процесс, который берёт задания из очереди и выполняет их в слотах.

ПримерRedis-очередь orders и обработчик Celery с двумя слотами.

Гделекция 1.5, §2

Бизнес-метрикаbusiness metric

Число о том, ради чего сервис существует: заказы, оплаты, выручка. Показывает результат всего пути от заказа до оплаты.

Примерorders_rejected_total: 4 заказа отклонены при 0 ошибок HTTP.

Гделекция 1.5, §7

Длительностьlatency, duration

Время от начала до конца операции. У успешных и ошибочных запросов её показывают раздельно.

Примерс быстрыми ошибками общая средняя 270,5 мс, у успешных — 300 мс.

Гделекция 1.1, §7; лекция 1.5, §8

Итог лекции

Что измерять, подсказывают три набора. Четыре золотых сигнала — задержка, трафик, ошибки, насыщение — общий набор для любого сервиса. RED — частота, ошибки, длительность — для всего, что принимает или отправляет запросы. USE — загрузка, насыщение, ошибки — для каждого ресурса. На стенде заказов RED у API весь опыт был в норме: 0 ошибок, около 2 мс. Во время наплыва обработчик был занят полностью, очередь выросла до 201 задания, а ожидание — до 49 секунд; это показал USE. При отказах шлюза набралось 122 повтора и 4 отклонённых заказа; это показали RED заданий и бизнес-метрики. Длительность успешных и ошибочных запросов показывают раздельно, иначе быстрые ошибки выглядят как ускорение.
