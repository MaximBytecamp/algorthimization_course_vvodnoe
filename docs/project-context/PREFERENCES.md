## Git

- Коммит — без строки `Co-Authored-By: Claude`, почта автора
  `-c user.email=bytecampmm@gmail.com` (no-claude-coauthor-trailer).
- После каждого коммита сразу `git push`, не спрашивая; в ответе — хеш и где смотреть
  результат. Отклонённый push не перезаписывать силой (always-push-after-commit).
- Архивы `*.zip.enc` и готовый код (`tools/code*`, `tools/proekt*`, `tools/proto*`) не
  отправлять в открытые репозитории; новые папки с кодом сразу в `.gitignore`; перед
  `git add` смотреть `git status` (no-ready-code-in-public-repos).

## Учебный текст

- Взрослая лекция для новичка: связное объяснение, термин вводится и сразу объясняется,
  без ссылок вперёд, сквозных загадок, вопросов «ответьте сами» и придуманных названий
  блоков. В трудном месте — аналогия и пример после термина (clear-text-for-beginners).
- Одна линия мысли на главу, без служебных блоков и повторов условия (op04-book-less-text).
- Не писать «вслух» и «устная защита решения» (avoid-vsluh-in-slide-text).
- Инструкции — прямое указание с причиной вместо запрета; повторяющееся действие —
  кадром в каждом разделе (instructions-no-prohibitions).
- Каждое действие — шаг `ol.steps` с кадром; части «Делаем» / «Разбираемся»; F5 перед
  проверкой (do-and-read-phases).
- Код разбирать подробно, по конструкциям, с примером «что пришло → что получилось»
  (code-walkthrough-detail).
- Страницы-инструкции верстать компонентами справочника по Git, не самодельными рамками
  (pages-use-book-components).
- Визуализаций — много, не бояться их количества: людям проще воспринять блок зрительно, чем прочитать.
  Показывать картинкой, схемой, таблицей, кодом с выводом, кадром — что угодно, что подходит к мысли.
  Отдельно рисовать системные истории — путь данных: как запрос доходит до сервера, как запись попадает в
  базу или таблицу, как данные переносятся между серверами и процессами. Большой процесс — серией из
  нескольких рисунков по шагам, а не одной перегруженной схемой (2026-11-06).
- Текст ведёт рисунки: перед каждой схемой — абзац, что сейчас покажем и зачем; после — разбор: что на
  рисунке видно (по элементам, цветам, стрелкам, числам), как его читать и что из этого следует для темы.
  Следующий абзац продолжает мысль рисунка. Рисунок без подводки и разбора или подпись вместо разбора — дефект;
  в сериях шагов — короткая связка между шагами (2026-11-06).
- Каждый разбор строк кода (`.walk`) сопровождается прогоном на живых данных стенда: команда или программа
  с печатью промежуточных значений, настоящий вывод и таблица «строка → что получилось на прогоне»; для кода
  сервиса — состояние до и после (Redis, `/metrics`, `/events`). Блок начинается словами «Прогон на живых данных»
  (2026-11-10).
- Каждый механизм лекции — ещё и «пример по шагам» на маленьком наборе демонстрационных данных (6–20 записей):
  данные кодом → шаг 1, 2, 3 с выводом программы и рисунком на каждом шаге → вывод; числа пересчитываются в уме,
  помечены как придуманные, связаны с числами стенда. Оформление — раздел `§N.1` после основного (2026-11-10,
  «не хватает показать на явных примерах, как будет работать»).
- В конце каждой лекции (темы) — глоссарий со всеми терминами лекции, включая изученные ранее (повторы
  из главы в главу нужны). У каждого термина: чёткая формулировка, пример и визуальная демонстрация работы —
  схема, рисунок, диаграмма или кадр; только текст — недостаточно (2026-11-06, наблюдаемость: `.glossary`/`.gl`
  в `observability/lekcii/styles.css`).
- ДЗ в колоде: зачин «не хочет, но очень хочет», мем, слайд порядка сдачи, PDF
  (homework-slide-convention).

## Тесты

- Условие: ситуация списком + отдельный блок «Что нужно сделать»; без «слева/справа»
  (test-task-clarity).
- Верный вариант не выделяется длиной и формой; разное число верных; условие не
  подсказывает ответ; «найти ошибку» — только реальная ошибка (test-options-no-giveaways).
