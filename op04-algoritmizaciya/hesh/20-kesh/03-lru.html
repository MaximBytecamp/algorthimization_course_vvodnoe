LRU-кэш
на OrderedDict

Задача КТП занятия 20 — упрощённый LRU-кэш, LeetCode 146. Словарь находит ключ за O(1), но LRU нужен ещё порядок обращений, и менять его тоже нужно за O(1). В главе этот порядок хранит OrderedDict. Разобрано, как устроен OrderedDict внутри и как то же сделать словарём и двусвязным списком, — это продвинутый уровень контроля КТП. Замер сравнивает три реализации.

§1Порядок обращений за O(1)

На полке у кассира помещаются пять коробок. Коробку, которую только что брали, он ставит с правого края. Когда приносят шестую, он убирает коробку с левого края — к ней дольше всех не обращались. Чтобы найти коробку, он смотрит на подписи и полку не перебирает.

LRU-кэш требует трёх операций за O(1): найти ключ, перенести ключ в конец порядка, убрать ключ из начала. Словарь даёт первую. Порядок в списке ключей не годится: order.remove(key) ищет ключ перебором, это O(n). Обычный словарь хранит порядок вставки, но перенести ключ в конец можно только удалив и вставив заново. OrderedDict из модуля collections умеет все три операции напрямую.

move_to_end(key) переносит ключ в конец. popitem(last=False) удаляет и возвращает первую пару — это и есть вытеснение. Вторая запись в выводе показывает подвох: присваивание существующему ключу меняет значение, но не двигает ключ. Гайка обновилась до 55 и осталась первой. Поэтому put существующего ключа должен сам вызвать move_to_end, иначе обновлённый ключ вытеснят первым. Как это складывается в класс, видно в коде.

§2Код и пошаговый прогон

Напишите класс сами. Тесты проверяют пример LeetCode с ответом None вместо −1, обновление существующего ключа, промах, ёмкость 1 и ошибку при ёмкости 0. Ещё один тест сравнивает класс с простой моделью на трёхстах случайных сценариях.

Пошаговый прогон идёт по одной функции, поэтому ниже те же действия записаны сценарием. Это цикл по операциям: ветка get повторяет метод get, ветка put — метод put. Ёмкость 2, значение товара — load(key) из главы 20.2.

После get 'болт' порядок — гайка, болт. Шайба переполняет кэш, и вытесняется гайка: к ней дольше всех не обращались. Поэтому get 'гайка' — промах, а последний get 'болт' — попадание. Проверка размера стоит после записи: так обновление существующего ключа никого не вытесняет. Каждая операция — несколько действий над OrderedDict, каждое за O(1). Почему они O(1), видно по устройству OrderedDict.

§3Что внутри OrderedDict

Продвинутый уровень контроля КТП — объяснить, откуда O(1) у get и put. OrderedDict — это словарь и двусвязный список: цепочка узлов, где каждый узел хранит ссылки на соседа слева и соседа справа. Словарь по ключу находит узел. Через ссылки узел вынимается из цепочки и ставится в конец, не трогая остальные узлы.

ОперацияЧто делает словарьЧто делает цепочкаВремя
найти ключячейка по хешу—O(1) в среднем
перенести в конецячейка по хешу → узелсоседи узла связываются друг с другом, узел ставится перед хвостомO(1)
вытеснить первыйудалить ключузел после головы вынимаетсяO(1)

Список Python так не может: удалить элемент из середины списка — значит сдвинуть все элементы правее, O(n). В цепочке узлов сдвигать нечего: меняются только четыре ссылки. Ниже — та же схема, написанная вручную. По КТП это углубление: на собеседовании её просят, когда готовый OrderedDict брать нельзя. Подробно связный список разбирается на занятии 21.

Углубление: LRU на словаре и двусвязном списке

Голова и хвост — пустые узлы-ограничители. С ними у каждого настоящего узла всегда есть оба соседа, и проверки на край не нужны. _unlink вынимает узел, связывая его соседей. _append ставит узел перед хвостом. Код проверен на трёх тысячах случайных сценариев: ответы и порядок ключей совпадают с версией на OrderedDict.

class Node:
    def __init__(self, key=None, value=None):
        self.key, self.value = key, value
        self.prev = self.next = None

class LRUCacheLinked:
    def __init__(self, capacity):
        self.capacity = capacity
        self.nodes = {}                              # ключ → узел
        self.head, self.tail = Node(), Node()
        self.head.next, self.tail.prev = self.tail, self.head

    def _unlink(self, node):
        node.prev.next, node.next.prev = node.next, node.prev

    def _append(self, node):
        node.prev, node.next = self.tail.prev, self.tail
        self.tail.prev.next = node
        self.tail.prev = node

    def get(self, key):
        node = self.nodes.get(key)
        if node is None:
            return None
        self._unlink(node)
        self._append(node)
        return node.value

    def put(self, key, value):
        node = self.nodes.get(key)
        if node is not None:
            node.value = value
            self._unlink(node)
        else:
            node = Node(key, value)
            self.nodes[key] = node
        self._append(node)
        if len(self.nodes) > self.capacity:
            oldest = self.head.next
            self._unlink(oldest)
            del self.nodes[oldest.key]

    def __len__(self):
        return len(self.nodes)

Узел хранит свой ключ, и это не лишнее: при вытеснении берут узел после головы, а удалить его из словаря можно только по ключу. Обе реализации — O(1) на операцию. Какая быстрее на практике, вместе с двумя более простыми, показывает замер.

§4Три реализации: замер

В замере 200 000 операций над 5000 ключей: 70% — get, 30% — put. Сравниваются OrderedDict, обычный словарь с переносом через удаление и вставку и словарь со списком порядка, где перенос — order.remove(key).

ЁмкостьOrderedDict, мссловарь, мссловарь и список, мс
10013,214,413,1
1 00014,721,9124,3

Замер выполнен на ноутбуке автора, Python 3.12.12, Apple M4, медиана трёх запусков. При ёмкости 100 разницы нет: список из ста ключей remove проходит быстро. При ёмкости 1000 список медленнее в 8,5 раза — проявляется его O(n). Обычный словарь медленнее OrderedDict в 1,5 раза. Причина — вытеснение через next(iter(self.data)): после многих удалений из начала словаря поиск первого живого ключа проходит через места удалённых, пока таблица не перестроится. OrderedDict берёт первый узел цепочки сразу.

Отсюда защита выбора, которой требует контроль КТП. OrderedDict — короткий код, O(1) на операцию и лучшее время из трёх. Словарь со связным списком — то же O(1), но втрое больше кода, и он медленнее. В замере стартового набора на ёмкости 1000 он занял 25,2 мс против 14,9 мс у OrderedDict, у которого цепочка написана на C. Его пишут, когда готовой структуры нет. Список порядка годится только для очень маленьких кэшей. Самая частая ошибка в LRU — забыть перенос ключа при чтении.

Проверьте себяПочему порядок обращений в LRU не хранят в обычном списке ключей?

  • Хранит. Проблема — в цене переноса ключа из середины в конец.

  • Верно. На ёмкости 1000 это в 8,5 раза медленнее OrderedDict, где перенос — O(1).

  • В список можно класть что угодно. Ограничение — во времени операций.

  • Наоборот, OrderedDict тяжелее: у каждого ключа узел со ссылками. Выбор делают ради времени.

Проверьте себяЧто останется в OrderedDict после d = OrderedDict(a=1, b=2), d['a'] = 10, d.popitem(last=False)?

  • Присваивание не переносит a в конец, поэтому первым вытесняется a.

  • Верно. a обновился, но остался первым, и popitem(last=False) удалил его. Поэтому put вызывает move_to_end.

  • popitem на непустом словаре не бросает ошибку.

  • popitem удаляет одну пару, а присваивание уже заменило 1 на 10.
