20.2

Индекс по ключу
и кэш с подсчётом

Два словаря из главы 20.1 в коде. Индекс строится один раз по всем записям и отвечает на поиск по полю за O(1); замер показывает, во сколько раз это быстрее перебора. Кэш заполняется по ходу работы и считает попадания и промахи. В главе — оба, контракт индекса при повторе ключа и причина, по которой кэшу без ограничения нужна ёмкость.

§1Индекс по полю

Записи из базы приходят списком словарей: у каждого товара код и цена. Найти товар по коду в списке — значит перебрать список, O(n) на каждый поиск. Индекс по полю code — словарь «код → запись». Его строят одним проходом, и дальше каждый поиск стоит в среднем O(1).

Первое решение при построении — что делать, если два товара получили один код. Простое присваивание index[key] = rec молча оставит последний, и первый товар пропадёт из индекса. Ошибку в данных никто не заметит. Контракт из главы 20.1 требует бросить ValueError: повтор ключа в индексе — повод разбираться с данными, и выбирать одну запись за пользователя нельзя. Напишите функцию сами.

Прогоны выполнены настоящим запуском. В первом три товара с разными кодами, во втором к ним добавлена вторая гайка. На ленте — коды записей.

В индексе лежат сами записи, копий нет: тест test_same_record проверяет это через is. Индекс занимает O(n) памяти только на словарь ссылок, сами товары не дублируются. Бывает, что ключ по смыслу не уникален: в индексе по цене у двух товаров может быть цена 5. Тогда строят словарь «ключ → список записей», как группировку из модуля 18. Насколько индекс ускоряет поиск, видно на замере.

§2Индекс или перебор: замер

В замере n товаров в случайном порядке и 1000 поисков по коду. Перебор проходит список до нужной записи, индекс строится один раз, затем 1000 раз читается.

Записей1000 поисков перебором, мспостроение индекса, мс1000 поисков по индексу, мс
10 00092,60,520,017
100 0003 050,726,20,024

Замер выполнен на ноутбуке автора, Python 3.12.12, Apple M4, медиана трёх запусков. На 100 000 записей перебор занял три секунды, индекс — 26 мс на построение и 0,024 мс на все поиски. Построение — это O(n), как один проход перебора, поэтому индекс окупается уже со второго-третьего поиска. В индексе ответ на любой запрос готов заранее. В кэше ответы появляются по одному.

§3Кэш над медленной функцией

Теперь цены приходят по одной из медленной функции load(code) — запроса к базе. Кэш оборачивает эту функцию. При запросе он сначала смотрит в словарь. Если ответ есть — попадание, база не нужна. Если нет — промах: кэш вызывает load, запоминает ответ и возвращает его. Счётчики показывают, сколько раз кэш помог. Ниже — сценарий из шести запросов, записанный одним циклом.

Шесть запросов дали три промаха — по одному на каждый товар — и три попадания. База вызвалась три раза вместо шести. Чем чаще повторяются запросы, тем выше доля попаданий. В классе те же действия разложены по методу get, а счётчики хранятся в полях объекта. Напишите класс сами.

Тест test_none_value ловит частую ошибку: проверку попадания через if self.data.get(key):. Для значений None, 0 или пустой строки она даёт ложный промах, и load вызывается снова. Попадание проверяют через key in self.data — так спрашивают о ключе, значение не участвует.

§4Кэш, который только растёт

У CountingCache нет ёмкости: каждый промах добавляет запись, и ни одна не удаляется. Если запросов миллионы и ключи разные, кэш займёт память, сравнимую со всей базой. Тот же кэш даёт functools.lru_cache(maxsize=None): при maxsize=None он тоже не ограничен.

Ограничение ёмкости требует решить, кого вытеснить, и в главе 20.1 замер показал, что LRU попадает чаще FIFO. Для LRU словаря мало: нужен ещё порядок обращений, и он должен меняться за O(1) при каждом get. Как это сделать, разобрано в главе 20.3.

Проверьте себяПочему в build_index повтор ключа — ошибка, а не замена записи?

  • Умеет: присваивание по существующему ключу заменяет значение. Решение — в контракте, а не в возможностях словаря.

  • Верно. Индекс обещает, что по ключу находится единственная запись. Если записей две, лучше сообщить, чем выбрать одну за пользователя.

  • Замена — та же операция O(1). Время не меняется.

  • Скорость здесь ни при чём: выбор — что делать с плохими данными.
