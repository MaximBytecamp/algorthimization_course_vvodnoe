У теста есть ожидаемый результат

Тестовый случай — это конкретный вход и результат, который функция должна вернуть по контракту. Ожидаемый результат записывают до запуска. Если сначала запустить код и только потом посмотреть на ответ, неверный ответ легко принять за правильный. Запуск показывает фактический ответ, а верный он или нет, видно только при сравнении с ожидаемым.

Типичный вход без особенностей называют happy path: например, максимум для [3, 8, 2] равен 8. На таких входах ошибки проявляются редко. Граничный случай проверяет край допустимых данных: пустой список, список из одного элемента, наибольшее допустимое значение. Ошибки чаще всего обнаруживаются на таких входах.

Вход для find_maxОжидаемЗачем проверяем
[3, 8, 2]8Максимум внутри
[8, 3, 2]8Максимум в начале
[2, 3, 8]8Максимум в конце
[-7]−7Один элемент
[-8, -3, -10]−3Все числа отрицательные
[5, 5, 5]5Все значения равны
[]ValueErrorОтказ на пустом входе по контракту
Здесь find_max требует непустой список и выбрасывает ValueError при нарушении требования. У second_max другой контракт: пустой вход допустим и даёт None.

Таблица тестов в программе

Таблицу можно перенести в программу: для каждой пары «вход — ожидаемый ответ» вызвать функцию и сравнить её результат с ожидаемым. Проверим так версию find_max, в которой поиск начинается с best = 0.

Перед кодом · кейсМаксимум списка

Ситуация«Найдите максимальный элемент списка». Условие короткое, и кажется, что уточнять нечего.

Что спросить и что изменится от ответа
  1. Бывают ли отрицательные числа?Если бывают, начинать с best = 0 нельзя: для [-7] ответ станет 0. Поэтому в таблицу тестов добавляют список из отрицательных чисел.
  2. Может ли список быть пустым?У пустого списка нет максимума. Договариваются заранее: исключение, None или такой вход запрещён.
  3. Вернуть значение или индекс?Если нужен индекс, сразу появляется второй вопрос: какой индекс вернуть, когда максимум встречается несколько раз.
  4. Отсортирован ли список?Если да, максимум стоит последним: его берут по индексу, без цикла. Это O(1).

ДоговорилисьВход — непустой список целых чисел, отрицательные допустимы, возвращаем значение. В коде ниже поиск нарочно начинается с best = 0. Таблица тестов покажет, соблюдает ли такой код этот контракт.

Три проверки из пяти прошли, и по ним ошибку не заметить. Две оставшиеся, на отрицательных числах, показывают, что функция нарушает контракт.

Открыть разбор

[-1]: ожидаем −1, получаем 0. Условие -1 > 0 ложно, поэтому best остаётся равным нулю. Значит, функция находит максимум не для любого непустого списка целых чисел, как обещает контракт.

Контрпример — допустимый по контракту вход, на котором функция возвращает неверный ответ. Чтобы показать, что в коде есть ошибка, хватает одного контрпримера. В обратную сторону это не работает: сколько бы тестов ни прошло, корректность для всех входов они не доказывают, ведь проверить все входы невозможно.

Та же проверка короче записывается через assert. Если условие ложно, программа останавливается и печатает сообщение:

Первая проверка ничего не вывела, вторая остановила программу на строке 10. Текст после запятой в assert выводится в сообщении об ошибке, поэтому в нём пишут, что именно ожидали.

Возьмём три версии find_max с разными ошибками и семь тестов из таблицы выше. В каждой клетке — результат запуска: «ловит» значит, что версия вернула неверный ответ и тест это заметит.

Три теста из семи не ловят ни одной ошибки: [3, 8, 2], [8, 3, 2] и [5, 5, 5]. Три других — [2, 3, 8], [-7] и [3, 8, 5] — вместе ловят все три версии. Поэтому к каждому тесту полезно назвать ошибку, которую он поймает. Тест, который не ловит ни одной, можно заменить.
