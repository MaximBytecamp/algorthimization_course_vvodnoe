## 2. Границы темы

Вглубь идём сколько нужно, вширь — нет. За границей занятия остаются:

- **замеры настоящего времени** — занятие 4. Здесь операции считаются, а не измеряются;
- **амортизированная стоимость** — занятие 7, вместе с ростом динамического массива;
- **рекуррентные соотношения и мастер-теорема** — не в этом курсе вообще;
  `O(n log n)` для сортировки слиянием показывается счётчиком, а не выводится формулой;
- **Θ и Ω** — называются один раз словами: O — это верхняя граница, «не хуже чем».
  Разбирать три обозначения на первом занятии по теме означает потерять само содержание;
- **сложность по памяти для рекурсии** — упоминается только в связи с call stack на занятии 4.

Занятие должно жить и вне курса: студент, открывший колоду через полгода перед
собеседованием, находит в ней таблицу роста, шесть заблуждений и фразу, которой
называют сложность на секции.

## 3. Ведущий приём: живой прогон алгоритма

Занятие построено как последовательная демонстрация. Каждый класс сложности показывается
прогоном: на экране полоса ячеек — список, по которому идёт алгоритм. Ячейка вспыхивает
в момент обращения к ней, счётчик увеличивается. Числа под анимацией получены прогоном:
`demos.js` строит план шагов тем же алгоритмом, что записан в `fragments.py`.

| Экран | Что выполняется | Результат прогона |
|---|---|---|
| 2 | перебор против половинного деления, n = 64 | 64 обращения против 6 |
| 9 | обращение по индексу | 1 операция при любом n |
| 11 | бинарный поиск; исключённые ячейки оседают | 6 шагов, три четверти списка не тронуты |
| 13 | линейный проход | 64 сравнения, полоса закрашена целиком |
| 15 | сортировка слиянием, n = 32 | 160 просмотров: 5 уровней по 32 |
| 17 | перебор всех пар, n = 24 | 276 сравнений, заполняется треугольник |
| 20 | те же данные двумя решениями | 24 против 276 на одном экране |
| 22 | график роста, кривые рисуются | `O(n²)` покидает область, остальные различимы |

Каждый класс занимает два экрана: **определение с прогоном** и **три примера** — алгоритм,
код, оценка T(n) и S(n). Всего 18 примеров плюс два для экспоненциального класса.

Второй слой демонстрации — числа, которые студент получает сам. `opcount.py` считает те же
операции без анимации:

```
     n         O(1)     O(log n)         O(n)   O(n log n)        O(n²)
     8            1            6            8           12           28
  1024            1           20         1024         5120       523776

ВО СКОЛЬКО РАЗ БОЛЬШЕ, КОГДА n УДВАИВАЕТСЯ
   128        1.00x        1.17x        2.00x        2.33x        4.03x
```

**Единицы счёта.** В анимации бинарного поиска считаются шаги деления (6 при n = 64),
в `opcount.py` — сравнения, их вдвое больше: на шаг приходится проверка на равенство
и на «меньше». Это названо прямо на экране 11, иначе экраны противоречат друг другу.

## 4. Тема с восьми сторон

Каждая сторона — свой экран или пара экранов, своя форма показа, свой материал.

### 4.1. Считать, а не измерять

Что становится видно: одно и то же решение на входах 8, 16, 32 даёт числа, по которым
предсказывается следующее. Форма — таблица счётчика с закрытой последней строкой:
студент называет число до того, как его покажут.

Материал: `opcount.py`, столбцы `O(n)` и `O(n²)` на n = 64 → 128.

### 4.2. Форма кода говорит о числе операций

Три правила чтения, каждое на своём фрагменте:

| Что в коде | Что со стоимостью | Фрагмент |
|---|---|---|
| два цикла подряд | складываются: n + n, это по-прежнему `O(n)` | 07 `average_and_spikes` |
| цикл внутри цикла | умножаются: n · n | 08 `closest_pair_distance` |
| на каждом шаге отрезок делится пополам | `log n` шагов | 06 `find_receipt`, 11 `halving_steps` |

Форма показа — листинг с подсветкой той строки, которая выполняется чаще всего,
и счётчиком рядом. Не «вход → ответ»: здесь важен не ответ функции, а сколько раз
дошло дело до подсвеченной строки.

### 4.3. Почему константы отбрасываются

`3n + 7` записывается как `O(n)`. Показывается на числах: при n = 1000 слагаемое 7
не видно вообще, а тройка не меняет того, что при удвоении n время удваивается.

Здесь же — честная цена этого упрощения: **на маленьких входах отброшенное решает всё.**
При n = 8 «плохой» `O(n²)` даёт 28 сравнений против 12 у `O(n log n)` — в два с половиной
раза, а не в тысячу. При n = 1024 это уже 523 776 против 5120 — разница в 102 раза.
O-нотация говорит о поведении при росте, и на восьми элементах она не советник.

### 4.4. Худший, лучший и средний случай

`find_pass` возвращает индекс сразу, как только нашёл. Если номер стоит первым — одно
сравнение. Если последним или его нет — n сравнений. Оценка `O(n)` берётся по худшему,
потому что на секции спрашивают про гарантию, а не про удачу.

Форма показа — три прогона одного фрагмента на трёх входах, счётчик у каждого:
1, 4 и 8 сравнений на списке из восьми номеров. Экран сразу закрывает вопрос
«а если повезёт»: повезти может, а оценка описывает то, на что можно рассчитывать.

Отдельная строка про средний случай: он считается по всем возможным входам и совпадает
с худшим по классу для линейного поиска — n/2 это тот же `O(n)`.

### 4.5. Память считается отдельно от времени

`S(n)` — это то, что решение создаёт **сверх** полученного входа. Список, пришедший
в аргументах, в оценку не входит: он уже был.

Пара фрагментов на одном экране, две колонки:

- 03 `has_duplicate_badges` — `O(n²)` время, `O(1)` память;
- 04 `has_duplicate_badges_fast` — `O(n)` время, `O(n)` память.

Отсюда первый в курсе разговор про размен: быстрее — за счёт памяти. Правильного
ответа нет, есть ограничение задачи. Это же формулировка, которую студент потом
пишет в complexity note.

### 4.6. Строки, которые выглядят дешёвыми

Самый практичный угол темы. Отсутствие цикла в коде не означает `O(1)`:

| Строка | Настоящая стоимость | Почему |
|---|---|---|
| `if x in data` для списка | `O(n)` | перебор до совпадения |
| `if x in seen` для множества | `O(1)` в среднем | адрес считается по значению |
| `sorted(prices)` | `O(n log n)` | сортировка сравнениями |
| `data[1:]` | `O(n)` время и память | срез копирует |
| `result.insert(0, x)` | `O(n)` | остальные элементы сдвигаются |
| `sum(data)`, `max(data)` | `O(n)` | полный проход, просто внутри библиотеки |

Ловится фрагментом 10 `unique_keep_order`: один цикл, а внутри `row not in result` —
и всё решение `O(n²)`. Это тот случай, когда студент уверенно пишет `O(n)`,
и автопроверка ловит его на этом.

### 4.7. Ограничение из условия — обратный ход

До сих пор шли от кода к оценке. Здесь наоборот: в условии стоит `n ≤ 200 000`,
и это уже сообщение о том, какое решение имеется в виду. Материал — `limits.md`,
шесть ситуаций и таблица ориентиров.

Ориентир «около 10⁷ операций в секунду» называется именно ориентиром: это не константа
из стандарта, а способ за десять секунд прикинуть, укладывается решение или нет.

### 4.8. Как назвать сложность на секции

Тема закрывается формулировкой, которую студент произносит интервьюеру и пишет
в заметку. Три части, одна фраза:

> Время `O(n)` — один проход по списку; память `O(1)` — храню только счётчик;
> худший случай — искомого номера нет, проход идёт до конца.

Это же связывает занятие с 2-м: в interview canvas поле «сложность» перестаёт быть
пустым. И задаёт форму заметки для `templates/complexity.md`.

## 5. Шесть заблуждений, которые ловим

Не «типичные ошибки» списком в конце, а разложенные по колоде: каждое ловится
на своём фрагменте и опровергается счётчиком, а не утверждением преподавателя.

| Заблуждение | Чем ловится |
|---|---|
| «два цикла подряд — это `O(n²)`» | фрагмент 07: счётчик показывает 2n, а не n² |
| «половина пар — значит другой класс» | фрагмент 08: `n(n−1)/2`, а при удвоении n всё равно 4.03x |
| «нет цикла — значит `O(1)`» | фрагменты 05 и 10: `sorted()` и `in` по списку |
| «`O(n²)` всегда хуже `O(n log n)`» | n = 8: 28 против 12, разница в два с половиной раза |
| «сложность зависит от языка и компьютера» | счётчик не вызывает `perf_counter`, числа у всех одинаковые |
| «`O(n)` — это ровно n операций» | бинарный поиск: 2·log n сравнений, а записывается `O(log n)` |

### Два норматива КТП, которые этот формат не выдерживает

Оба отклонения — прямое следствие выбранного формата, и оба названы здесь, а не спрятаны.

1. **Доля практики 27% при норме 30%.** Причина — подробный разбор шести классов
   с примерами: демонстрационная часть заняла 79 минут из 139.
2. **58 минут подряд без работы руками** (экраны 1–20) при норме 25 минут.

Способ выдержать оба норматива, не ломая последовательность: две короткие вставки
по 5 минут **внутри** блока классов — после экрана 14 (линейная сложность) и после
экрана 18 (квадратичная). В обеих студент дописывает счётчик к фрагменту из `fragments.py`
и называет число операций при n = 8 и n = 16. Это даёт 48 минут практики из 149 — 32% —
и разбивает демонстрацию на куски по 28 и 26 минут. Вставки не написаны: решение о том,
нужны ли они, принимает преподаватель.

## 8. Контроль и Git

Приёмка: студент получает незнакомое решение на 25–30 строк и называет три вещи —
время, память, худший случай. Ответ засчитывается, если названо, **какие операции
считались**: «`O(n)`, потому что каждый элемент проверяется один раз».

Git по КТП: issue `complexity-baseline`, ветка `lesson-03`, коммит с заполненным
`answers.py` и заметками, Pull Request с описанием того, какие два фрагмента
оказались спорными и почему. Взаимное review — один комментарий по чужой оценке
с контраргументом, а не «согласен».
