Модуль, пакет и точки в импорте

Два слова, которые дальше встречаются постоянно. Модуль — это один файл .py, например calculator.py. Пакет — это папка с модулями, которую тоже можно импортировать, например app. Точки в записи app.services.calculator — не «части имени», а вложенность: папка app → папка services → файл calculator.py. Читая импорт, вы читаете путь по дереву проекта.

Что делает сам файл __init__.py

Он играет две роли сразу.

  • Объявляет папку обычным пакетом. Для Python наличие этого файла — явный признак: «это не просто папка с файлами, это пакет».
  • Является телом пакета. Код внутри __init__.py выполняется в момент первого импорта пакета — так же, как код верхнего уровня обычного модуля из главы 2.4. Пустой файл просто ничего не делает.

Причём выполняется он не только при import app. Импортируя что-то в глубине, Python проходит весь путь по дереву и выполняет __init__.py каждого пакета по дороге — сверху вниз.

Почему в учебном проекте он пустой

В __init__.py обычно складывают то, что относится к пакету целиком: короткие псевдонимы для импортов, версию, общие настройки. Но помните предыдущий пункт: этот код выполнится при любом импорте из пакета, даже если нужна одна маленькая функция. Тяжёлый или «делающий что-то» __init__.py — частая причина медленных и непредсказуемых импортов, поэтому по умолчанию его оставляют пустым. Так делаем и мы.

Почему иногда пакет работает и без него

Вы можете удалить __init__.py, и импорт всё равно сработает. Начиная с Python 3.3 папка без этого файла тоже импортируется — как namespace package. Разница видна, если посмотреть на сам объект пакета.

Вывод для вашей работы: в своих проектах создавайте __init__.py явно. Пакет получает тело, поведение импорта становится предсказуемым, а инструменты и старые версии библиотек надёжнее видят вашу папку как пакет. При этом отсутствие файла в чужом проекте само по себе не является ошибкой.

Две разные вещи с одинаковым именем

Файл __init__.py — тело пакета. Метод __init__ внутри класса — подготовка объекта при его создании; к пакетам он отношения не имеет. Общее у них только соглашение об именах: такие имена с двойными подчёркиваниями называют dunder (от double underscore) и придумывать свои не нужно — их набор задан языком.

Файл, пакет и путь импорта

Три слова, которые дальше встречаются постоянно. Файл — одна единица текста, calculator.go. Пакет — папка целиком: все файлы в ней с одинаковой строкой package services образуют один пакет и видят имена друг друга без импортов. Путь импорта — адрес папки от имени модуля: example.com/student-tools/internal/services.

Отсюда вывод, непривычный после Python: разбить пакет на несколько файлов — бесплатно. Можно держать calculator.go и average.go в одной папке, и это по-прежнему один пакет services с общим набором имён. Новая граница возникает только вместе с новой папкой.

Все файлы одной папки — один пакет

Из этого следует жёсткое правило: в одной папке не может быть двух разных значений package. Попытка положить рядом файл с package services и файл с package calculator закончится ошибкой сборки found packages services and calculator in .... Компилятор не выбирает — он останавливается.

Имя пакета при этом не обязано совпадать с именем папки: язык этого не требует. Но в путях импорта видно именно имя папки, а в вызовах — имя пакета, поэтому расхождение сбивает читателя. Договорённость такая: называйте пакет так же, как папку, и делайте это исключением, а не привычкой.

Зачем нужна папка internal

Имя internal Go понимает особым образом. Пакеты внутри неё доступны только коду того же модуля — точнее, коду, лежащему рядом с папкой internal или ниже. Чужой модуль, подключивший ваш как библиотеку, получит на импорте ошибку use of internal package not allowed.

Это единственный способ в Go ограничить видимость на уровне пакетов, и работает он на компиляции, а не по договорённости. Заглавная буква решает, что видно за пределами пакета; internal решает, что видно за пределами модуля.

Две разные вещи с похожими именами

Функция init() в Go выполняется один раз при подключении пакета — это отдалённый родственник питоновского __init__.py. Метод-конструктор она не заменяет: в Go объекты создают обычными функциями вида NewConsole(). Пользоваться init() в учебном проекте не нужно.

Частая ошибка

При python app/main.py стартовый путь поиска отличается: Python может не найти пакет app. Не исправляйте это добавлением случайных путей в sys.path. Вернитесь в student-tools и используйте python -m app.main.

Почему один и тот же код запускается по-разному

Запуская программу, Python первым делом решает, откуда искать импортируемые пакеты. Стартовая папка поиска зависит от способа запуска — и именно она решает, будет ли виден пакет app.

Разберём по частям. go build компилирует код и сообщает об ошибках; ./... означает «текущая папка и все вложенные», то есть все пакеты модуля сразу. Молчание здесь — хороший результат: собралось всё. go vet ищет подозрительные места, которые формально компилируются: например неверное число аргументов в Printf. go run . собирает и тут же запускает пакет из текущей папки.

Обратите внимание: проверяются все пакеты, включая те, которые никто не импортирует. Ошибка в internal/utils обнаружится сразу, даже если main.go до него не добирается. В Python аналогичная опечатка дождалась бы первого импорта во время работы программы.

Частая ошибка

Команда go run main.go собирает не пакет, а перечисленные файлы. Пока в пакете main один файл, разницы нет. Как только рядом появится второй файл того же пакета, запуск сломается с undefined, хотя go run . работает. Привыкайте к точке: она означает пакет целиком.

Почему нет ошибки «пакет не найден»

В Python стартовая папка решала, будет ли виден пакет app, — отсюда разница между python -m app.main и python app/main.py. В Go этого класса проблем нет: пути импорта абсолютны и отсчитываются от имени модуля в go.mod, а не от текущего каталога. Поэтому команду можно выполнять из любой папки проекта:

Структура и архитектура

Структура отвечает на вопрос «где лежит файл?». Архитектура — «какая у части ответственность и от кого она зависит?». Папка services сама не делает программу правильно устроенной: важно, чтобы вычисления не зависели от интерфейса вывода.

Имена app, src, core зависят от команды и проекта. Здесь services хранит прикладной расчёт, utils — небольшую функцию оформления. Создавать пустые папки «на будущее» не требуется.

Имена internal, cmd, pkg — распространённые соглашения сообщества, а не требования языка: обязательное значение есть только у internal. Здесь services хранит прикладной расчёт, utils — небольшую функцию оформления. Создавать пустые папки «на будущее» не требуется: пакет без файлов для Go не существует.

Куда смотрят стрелки

Главное правило этой структуры — направление зависимостей. Точка запуска знает про расчёт и оформление, а они про неё — нет. Расчёт вообще ни от чего не зависит: ему всё равно, кто его вызвал и куда пойдёт результат.

Интерактивная схема · кто от кого зависит
app/main.pymain.go · package mainточка запуска
↓ импортирует↑ импортирует обратно
services/calculator.pyinternal/servicesтолько вычисления
utils/formatter.pyinternal/utilsтолько оформление строки

Стрелка одна и вниз: точка запуска импортирует расчёт и оформление. Калькулятор можно вызвать из тестов, из другой программы, из будущего веб-интерфейса — он ничего не знает о том, кто его использует.

Если стрелка появляется в обратную сторону — расчёт импортирует точку запуска, — получается цикл: два модуля ждут друг друга, и Python сообщает об этом ошибкой partially initialized module. Данные передают вниз аргументами, а результат возвращают вверх через return; обратный импорт для этого не нужен.

Если стрелка появляется в обратную сторону — расчёт импортирует точку запуска, — получается цикл. Go в этом месте строже Python: такой проект вообще не собирается, компилятор отвечает import cycle not allowed и перечисляет участников цикла. Данные передают вниз аргументами, а результат возвращают вверх через return; обратный импорт для этого не нужен.

Проверьте себя · Чем go build ./... отличается от go run .?

Первая команда проверяет и собирает все пакеты модуля, включая те, которые сейчас никто не импортирует, и ничего не запускает. Вторая собирает только пакет из текущей папки и сразу его выполняет.
