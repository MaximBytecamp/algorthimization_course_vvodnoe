Зачем начинать с .venv

Представьте два проекта на одном компьютере: одному нужна одна версия библиотеки, другому — другая. Установка в общее место связывает их между собой. Обновление ради первой программы может сломать вторую.

Виртуальное окружение отделяет установленные библиотеки проекта от остальных. Каталог .venv создаётся на основе уже установленного Python: внутри будет исполняемый файл Python или ссылка на него, служебные файлы и собственные пакеты. Это не отдельная операционная система.

Проект — все файлы и папки, из которых складывается программа: исходный код, проверки, документация, настройки и список зависимостей. Наш общий проект — Student Tools. Он посчитает среднюю оценку, сначала обычным текстом, а затем с помощью Rich. В каждой главе мы изменяем эту же папку.

Схема · два независимых окружения
student-tools/.venv → свои пакеты
другой-проект/.venv → другие пакеты

Одинаковое имя папки не делает окружения общими.

02 / Создайте окружение

Выполните в своём проекте
Где
Терминал VS Code, корень student-tools.
Действие
Выберите ОС выше. Выполните проверку версии, затем команду создания ниже.
Результат
В Explorer появился каталог .venv; внутри есть pyvenv.cfg.
Проверка
Дождитесь возврата приглашения терминала. Если видна ошибка, не переходите к активации.

Нужен установленный Python 3.10 или новее. Выберите вашу систему в переключателе сверху. Первая команда проверяет Python, вторая создаёт папку окружения. Если Windows не находит py, но команда python --version работает, используйте python -m venv .venv.

-m означает «выполни модуль», venv — встроенный модуль создания окружений, последнее .venv — имя создаваемой папки. Успешная команда может ничего не напечатать: проверьте появление каталога в Explorer.

Создать ≠ активировать

Появление папки не меняет команды в уже открытом терминале. Следующий шаг выбирает её инструменты для этой сессии.

Содержимое окружения создаёт Python. Свой код туда не переносим и служебные файлы руками не редактируем. .venv — принятое имя папки; .env обычно является файлом переменных окружения. Это разные вещи.

Что именно делает активация

Когда вы набираете python, терминал не угадывает, какую программу запустить: он идёт по списку папок из переменной PATH — сверху вниз — и берёт первый подходящий файл. Активация не создаёт и не перемещает ничего на диске. Она делает ровно одно: ставит папку .venv в начало этого списка для текущего терминала. С этого момента первым найденным python оказывается python из вашего окружения, а вместе с ним — и его собственный pip с его набором библиотек.

Отсюда три следствия, которые обычно и вызывают путаницу. Активация действует только в том терминале, где вы её выполнили: соседняя вкладка продолжит работать с базовым Python. Команда deactivate возвращает прежний порядок поиска, но не удаляет окружение — папка остаётся на диске со всеми пакетами. И наконец, активация вообще не обязательна: можно ничего не активировать и каждый раз вызывать интерпретатор по полному пути, как в блоке для PowerShell ниже — результат будет тот же.

Зачем начинать с go.mod

Представьте два проекта на одном компьютере: одному нужна одна версия библиотеки, другому — другая. Если версия выбирается «глобально», один проект придётся ломать ради другого. Go решает это иначе, чем Python: изоляцию даёт не отдельная папка внутри проекта, а файл, который лежит в его корне.

Модуль — это набор пакетов с общим именем, у которого в корне есть файл go.mod. В go.mod записано имя модуля, минимальная версия Go и точные версии всех зависимостей. Скачанный код библиотек хранится в общем кэше на вашем компьютере, но при сборке каждый проект берёт ровно те версии, которые названы в его собственном go.mod. Поэтому проекты не мешают друг другу и активировать ничего не нужно.

Проект — все файлы и папки, из которых складывается программа: исходный код, проверки, документация, настройки и список зависимостей. Наш общий проект — Student Tools. Он посчитает среднюю оценку, сначала обычным текстом, а затем цветным выводом через стороннюю библиотеку. В каждой главе мы изменяем эту же папку.

Схема · два независимых модуля
student-tools/go.mod → свои версии
другой-проект/go.mod → другие версии

Скачанный код общий, выбор версий — у каждого свой.

Если вы уже прошли ветку Python

Привычки переносятся почти один в один, только имена другие. Слева — то, что вы делали в Python, справа — как это выглядит в Go.

Одно важное отличие

В Python зависимости лежат внутри проекта, поэтому .venv нельзя ни копировать, ни отправлять в Git. В Go в проекте лежит только описание зависимостей — его как раз и нужно отправить в Git, а код библиотек Go скачает сам.

02 / Объявите модуль

Выполните в своём проекте
Где
Терминал VS Code, корень student-tools.
Действие
Проверьте версию Go, затем выполните go mod init с именем модуля.
Результат
В корне появился файл go.mod из двух строк.
Проверка
Откройте go.mod в редакторе. Первая строка начинается со слова module.

Нужен установленный Go 1.21 или новее. Команды одинаковы во всех операционных системах — отдельный переключатель терминала здесь не нужен.

go mod init создаёт файл go.mod, а его аргумент — имя модуля. С этого имени будут начинаться все внутренние импорты проекта, поэтому оно должно быть уникальным. Обычно берут адрес будущего репозитория: github.com/ваш-логин/student-tools. Учебное example.com/student-tools тоже работает: Go не обращается по этому адресу, пока вы сами не попросите скачать такой модуль.

Пока в файле только две строки: имя модуля и версия Go, на которую рассчитан код. Раздела require нет — зависимостей ещё нет. Он появится сам в главе 2.3, когда мы подключим первую библиотеку.

Объявить ≠ скачать

Появление go.mod ничего не загружает на диск. Файл только фиксирует имя модуля и версии. Код зависимостей Go скачает при первой сборке или по команде go mod download.

Где тогда лежат библиотеки

Скачанные версии Go складывает в общий кэш модулей — одну папку на весь компьютер. Посмотреть её путь можно так:

Внутри кэша каждая библиотека лежит вместе с номером версии в имени папки, поэтому две версии одной библиотеки спокойно существуют рядом. Проекту не нужна своя копия: ему достаточно назвать нужную версию в go.mod. Править файлы в кэше вручную нельзя — Go проверяет их контрольные суммы.

Что происходит вместо активации

Когда вы набираете go build или go run, команда не угадывает, какой проект вы имеете в виду. Она берёт текущую папку и идёт вверх по дереву каталогов, пока не найдёт go.mod. Найденный файл и задаёт границы модуля: его имя, набор пакетов и версии зависимостей. Никакой предварительной команды для этого не требуется.

Отсюда три следствия, которые обычно и вызывают путаницу. Работает это в любом терминале — вкладки и новые окна ничего не теряют, потому что состояние хранится в файле, а не в сессии. Дальше: вложенные папки — часть того же модуля, отдельный go.mod внутри проекта создавать не нужно, и именно поэтому важно открыть в редакторе правильную папку. И наконец, место установки самого Go роли не играет: один и тот же go обслуживает все ваши проекты, а различает их по go.mod.

Интерактивная схема · не настоящий терминал
go build → student-tools/go.mod

Команда выполнена в корне: go.mod найден сразу, модуль определён.

Если go не находится вовсе

Сообщение command not found: go или «go» не является внутренней или внешней командой означает, что Go не установлен либо не попал в PATH. Переустановите Go с go.dev/dl, закройте и заново откройте терминал VS Code — переменные окружения читаются при его запуске.

Проверьте себя · Почему нельзя просто скопировать .venv одногруппнику?

В окружении есть локальные пути и платформенные файлы. На другом компьютере его создают заново из установленного Python; список библиотек передают отдельно. В главе 2.6 подготовим такой список.

Проверьте себя · Почему в Go нет команды «активировать окружение»?

Потому что окружения как папки в проекте нет. Версии зависимостей записаны в go.mod рядом с кодом, а сам код библиотек лежит в общем кэше. Команде go из любого терминала достаточно найти go.mod выше по дереву папок — выбор версий уже сделан, активировать нечего.
