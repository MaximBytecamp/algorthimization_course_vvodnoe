Передаём рецепт окружения

Выполните в своём проекте
Где
Активная .venv; корень student-tools.
Действие
Выполните python -m pip freeze > requirements.txt. Откройте созданный файл.
Результат
В файле записаны строки с именами пакетов и версиями.
Проверка
Найдите rich; убедитесь, что файл не пуст. Если там посторонние библиотеки, проверьте выбранное окружение.

Ваша .venv зависит от компьютера и содержит локальные пути. Её не отправляют в Git или архив проекта. Другому разработчику нужны исходники, установленный Python и список зависимостей, по которому он создаст собственное окружение.

Выполняйте команду в активном окружении этого проекта. freeze записывает установленные пакеты с версиями, в том числе транзитивные зависимости Rich. Символ > сохраняет вывод в файл и перезаписывает прежнее содержимое.

Снимок пакетов, а не полная гарантия

pip freeze не создаёт полноценный lock-файл и не фиксирует версию Python или операционную систему. Чистое окружение и явно указанная версия Python делают такой учебный рецепт понятнее. Лишние пакеты из общей .venv попадут в снимок тоже.

Это зафиксированный набор для скачиваемого примера, а не обещание самых новых версий. Ваш freeze после pip install rich может дать другие версии. В своей работе проверяйте именно свой файл зависимостей.

Что такое тест и зачем он в этой теме

Тест — это обычный код, который вызывает вашу функцию с известными данными и проверяет, что она вернула ожидаемое. Проверяет не человек глазами, а сама программа: вы один раз описываете «на списке [5, 4, 5, 3, 5] среднее равно 4.4» — и дальше эта проверка повторяется по команде за доли секунды.

В теме про структуру проекта тесты появляются не случайно. Они — первый посторонний потребитель вашего кода: тестовый файл лежит в другой папке и добирается до функций теми же импортами, что и main.py. Если структура собрана правильно, тесты запускаются сразу. Если нет — вы увидите ровно те ошибки, которые разбирали в главах 2.4 и 2.5.

Важная деталь оттуда же: тесты ваши модули импортируют, а не запускают. Поэтому main() и должен вызываться только под условием __name__ == "__main__" — иначе при каждом прогоне тестов программа будет печатать свой отчёт.

Мы используем unittest — он входит в стандартную библиотеку Python, ставить ничего не нужно. Существуют и сторонние инструменты (например, pytest), но для трёх проверок хватает встроенного.

Как читается файл теста

  • import unittest и два импорта из app — тест берёт функции из вашего пакета, как это делал бы любой другой код.
  • class AverageTests(unittest.TestCase) — группа проверок. Наследование от TestCase даёт классу готовые методы сравнения, которые сами сообщают о расхождении.
  • def test_average(self) — один тест. Имя обязано начинаться с test: по этому признаку Python и находит, что запускать. Метод без такого имени просто не выполнится.
  • self.assertAlmostEqual(a, b) — «должны быть равны с точностью до округления», self.assertEqual(a, b) — «должны совпадать точно», with self.assertRaises(ValueError): — «внутри этого блока обязана возникнуть такая ошибка». Последняя конструкция проверяет не результат, а поведение при неверных данных: пустой список должен приводить к ValueError, и если функция промолчит, тест упадёт.

Почему для среднего — assertAlmostEqual

Компьютер хранит дробные числа приближённо, и привычные равенства иногда не выполняются. Это не ошибка Python, а свойство двоичного представления дробей — с ним живут все языки.

Команда запуска по частям

-m unittest — запускаем встроенный модуль тестирования тем же Python, что и программу. discover — «найди тесты сам». -s tests — начни поиск с папки tests. -v — печатай каждый тест отдельной строкой, а не точками. Команда выполняется из корня проекта: оттуда виден пакет app, который тесты импортируют.

Создайте папку tests в корне и сохраните туда файл выше. Ожидаются три успешных теста и OK: средняя обычного списка, ошибка для пустого списка и формат строки.

Действие
Выполните go mod tidy, затем go mod verify. Откройте go.mod.
Результат
tidy молчит или правит файл, verify печатает all modules verified.
Проверка
В go.mod есть строка с github.com/fatih/color и номером версии; рядом лежит go.sum.

В Python список зависимостей нужно было создать отдельной командой — и о ней легко забыть. В Go отдельного шага нет: go.mod и go.sum заполнялись сами, пока вы работали. Передать проект другому человеку — значит передать исходники вместе с этими двумя файлами.

go mod tidy приводит файлы в соответствие с импортами в коде. go mod verify пересчитывает контрольные суммы всех скачанных зависимостей и сравнивает их с go.sum: ответ all modules verified означает, что содержимое версий не менялось с момента загрузки. Обе команды выполняют перед отправкой работы.

Насколько это надёжнее requirements.txt

pip freeze делает снимок: он перечисляет версии, но не проверяет содержимое пакетов и не фиксирует версию Python. В Go go.mod задаёт минимальную версию языка, go.sum хранит контрольные суммы, а сборка останавливается при любом расхождении. Ближайший аналог в Python — не requirements.txt, а полноценный lock-файл (poetry.lock, uv.lock).

Это зафиксированный набор для скачиваемого примера, а не обещание самых новых версий. У вас версии будут другими — так и должно быть. В своей работе проверяйте именно свой go.mod.

Обновление версий — отдельное решение

go mod tidy версии не поднимает: она меняется только по вашей команде go get имя@версия или go get -u ./.... Это сделано намеренно — сборка проекта не должна менять результат сама по себе.

Что такое тест и зачем он в этой теме

Тест — это обычный код, который вызывает вашу функцию с известными данными и проверяет, что она вернула ожидаемое. Проверяет не человек глазами, а сама программа: вы один раз описываете «на срезе [5, 4, 5, 3, 5] среднее равно 4.4» — и дальше эта проверка повторяется по команде за доли секунды.

В Go тестирование встроено в язык и в команду go: ставить ничего не нужно, сторонние библиотеки для трёх проверок не требуются. Правила всего три, и все они про имена. Файл обязан заканчиваться на _test.go. Функция обязана начинаться с Test и принимать один аргумент *testing.T. И такой файл не попадает в обычную сборку: go build его игнорирует, поэтому тесты не увеличивают программу.

Ещё одно отличие от Python: тест лежит в той же папке, что и проверяемый код, и объявляет тот же пакет. Отдельной папки tests в Go не делают. Зато тесту становятся доступны и неэкспортированные имена пакета — то, до чего внешний код не добрался бы.

Как читается файл теста

  • package services — тот же пакет, что и у проверяемого файла. Поэтому CalculateAverage вызывается напрямую, без импорта: имена внутри пакета видны без квалификации.
  • func TestCalculateAverage(t *testing.T) — один тест. Имя обязано начинаться с Test: по этому признаку Go и находит, что запускать. Функция без такого имени просто не выполнится.
  • t.Errorf(...) — «запиши расхождение и продолжай»; t.Fatalf(...) — «запиши и прекрати этот тест немедленно». Второе нужно там, где дальше проверять нечего: если функция вернула ошибку, сравнивать её результат бессмысленно.
  • Готовых assertEqual в Go нет. Сравнение пишется обычным if, и это осознанное решение: тест — такой же код, как остальной, без отдельного языка проверок.

Почему сравнение через math.Abs

Компьютер хранит дробные числа приближённо, и привычные равенства иногда не выполняются: 0.1 + 0.2 даёт 0.30000000000000004. Это не особенность Go, а свойство двоичного представления дробей — с ним живут все языки. Поэтому дробные результаты сравнивают с допуском: math.Abs(got-4.4) > 1e-9 читается как «отличается больше, чем на миллиардную». Точное сравнение == оставляют строкам и целым числам.

Команда запуска по частям

go test собирает и запускает тесты; ./... — «все пакеты модуля»; -v печатает каждый тест отдельной строкой, а не сводку. Третья команда показывает, как запустить один тест: -run принимает шаблон имени. Команды работают из любой папки внутри модуля.

Ожидается две строки --- PASS и итог ok example.com/student-tools/internal/services. Пакеты без тестов Go отметит как no test files — это не ошибка, а сообщение, что проверять там нечего.

Как выглядит непройденный тест

Зелёный прогон полезен, но учит мало. Разберите три вида вывода — с ними вы столкнётесь в практике 2.7 и в домашней работе.

FAIL — код отработал, но посчитал не то

Здесь в формулу внесена ошибка — деление на len(values) - 1. Go называет тест, файл и строку, где сработала проверка, а текст расхождения вы написали сами в t.Errorf. Отсюда практический вывод: пишите в сообщении и полученное, и ожидаемое значение — иначе через месяц вывод FAIL вам ничего не скажет.

Ошибка сборки — до тестов дело не дошло

Аналог питоновского ERROR, только раньше: в Go такие ошибки находит компилятор, а не выполнение теста. Пометка [build failed] означает, что ни один тест пакета не запускался. Разница важна: FAIL — «проверка не сошлась», build failed — «код не собрался», и чинить нужно разные места.

Ноль тестов — не победа

Так выглядит прогон, в котором проверять оказалось нечего: файл назван calculatortest.go вместо calculator_test.go, или функция — CheckAverage вместо TestAverage. Ошибки нет, красного цвета нет, но и проверок не было. Смотрите не на отсутствие слова FAIL, а на наличие строк ok и PASS.

Проверка с чистого листа

Скопируйте только передаваемые файлы в отдельную папку или скачайте свой репозиторий заново. Откройте папку, содержащую main.go и go.mod. Кэш модулей можно даже очистить командой go clean -modcache, чтобы зависимости скачались заново.

Если видны Средний результат: 4.40 и строки PASS, вы проверили, что проект собирается не только у вас. В README укажите также вывод go version: он показывает, на какой версии работа проверялась.

Что именно доказывает такая проверка

Что в репозитории нет забытых файлов и что версии зависимостей записаны. Полной независимости от операционной системы это не даёт: программу, использующую специфику Windows, Linux всё равно не запустит. Зато собранный бинарник переносится без установки Go — достаточно собрать его под нужную систему.

Проверьте себя · Почему go.sum нужно отправлять в репозиторий?

В нём записаны контрольные суммы тех версий, на которых работа проверялась. Без go.sum Go скачает зависимости заново и запишет суммы с нуля — подмену содержимого версии в этом случае никто не заметит. Файл служебный, править его руками не нужно, но и удалять из репозитория нельзя.

Проверьте себя · Почему requirements.txt нужно получать в окружении проекта?

freeze перечисляет установленные пакеты выбранного Python. В общем окружении он захватит библиотеки других программ, а в неверно выбранном — может не содержать Rich.
