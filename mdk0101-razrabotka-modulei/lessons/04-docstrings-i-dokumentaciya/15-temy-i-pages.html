Часть 1 · Внешний вид

§1Тема оформления

Тема оформления Sphinx — набор шаблонов страниц, стилей и скриптов. Содержимое страницы — заголовки, описания функций, оглавление — Sphinx строит одинаково, тема задаёт только то, как его показать: шрифты, цвета, где стоит навигация, как выглядит подпись функции. Поэтому тему меняют одной строкой в conf.py, и ни один файл .rst или докстринг при этом не правят.

Так устроены и обложки одной книги в разных изданиях: текст глав тот же, меняются шрифт, поля и обложка. Три темы, которые встречаются чаще других:

alabasterВстроена в SphinxПростая, с узкой колонкой навигации слева; подписи функций без выделенияТема по умолчанию после мастера

§2Смена темы по шагам

Установите тему в окружение

.venv/bin/pip install furo.venv\Scripts\pip install furo. Тема — пакет Python, как расширение. Без установки сборка остановится с отчётом Theme error! и строкой no theme named 'furo' found.

Укажите тему и заголовок сайта

Без html_title Furo составляет заголовок из названия и номера выпуска: «документация Отчёт кафе 1.0». Своя строка короче и читается в колонке навигации целиком.

Соберите и откройте главную

sphinx-build -M html docs/source docs/build -E. Ключ -E здесь не обязателен — смена conf.py и так пересобирает всё, — но он гарантирует, что от прежней темы не осталось страниц.

§3Зависимости документации

Программе «Отчёт кафе» для работы Sphinx и Furo не нужны, поэтому в requirements.txt проекта их не добавляют. Для документации заводят отдельный список рядом с её исходниками:

Версии записаны точно, через ==, как в requirements.txt проекта. Сборка на другом компьютере и в GitHub Actions пойдёт на тех же версиях, что у вас, и даст ту же страницу. Номера своих версий показывает .venv/bin/pip show sphinx furo.venv\Scripts\pip show sphinx furo, строки Version.

Чтобы собрать документацию на новом компьютере, ставят оба списка одной командой: pip install -r requirements.txt -r docs/requirements.txt. Первый нужен потому, что autodoc импортирует модули проекта (глава 4.13), второй — сам Sphinx с темой.

Сайт по-прежнему открывается только с вашего диска. Во второй части его собирает и выкладывает GitHub.

Часть 2 · Публикация

§4GitHub Pages и откуда берётся сайт

GitHub Pages — служба GitHub, которая раздаёт готовые HTML-страницы из репозитория по адресу вида https://логин.github.io/имя-репозитория/. Сервер, база данных и своя программа для этого не нужны: Pages отдаёт файлы как есть. Сайт Sphinx как раз состоит из таких файлов. В бесплатном плане GitHub Pages включается у публичного репозитория.

Файлы для Pages можно взять из ветки репозитория или получить от GitHub Actions. В главе 4.12 папка docs/build исключена из Git, поэтому в ветке готовых страниц нет. Их собирает GitHub Actions — служба, которая по событию в репозитории запускает команды на своей виртуальной машине. Событие — отправка коммита в main; команды — те же, что вы выполняли в терминале.

Путь от коммита до сайта

1 · git push Коммит с правкой докстринга уходит в main. на вашем компьютере
2 · build Виртуальная машина ставит зависимости и выполняет sphinx-build. GitHub Actions
3 · deploy Папка docs/build/html передаётся в Pages. GitHub Actions
4 · сайт Новая версия открывается по прежнему адресу. около минуты после push

Если на шаге 2 сборка находит предупреждение, шаги 3 и 4 не выполняются: на сайте остаётся прошлая исправная версия.

§5Файл сборки docs.yml по строкам

Что и когда запускать, GitHub Actions читает из файлов в папке .github/workflows репозитория. Такой файл называется workflow и записывается в формате YAML: отступы задают вложенность, как в Python, дефис начинает элемент списка. Создайте файл .github/workflows/docs.yml в корне проекта — точка в начале имени папки обязательна.

Файл читается сверху вниз блоками.

СтрокиЧто задают
name: ДокументацияНазвание, которое видно на вкладке Actions репозитория
on: → push: branches: [main]Когда запускать: при каждой отправке коммитов в ветку main
workflow_dispatch:Добавляет кнопку Run workflow для запуска вручную, без коммита
permissions:Права на время запуска: читать код (contents: read), публиковать в Pages (pages: write), подтвердить GitHub, что публикация идёт из этого репозитория (id-token: write)
concurrency:Если два коммита отправлены подряд, первый запуск отменяется и публикуется только последний
jobs: → build:Первое задание — сборка. runs-on: ubuntu-latest — машина с Linux
actions/checkout@v5Готовое действие: скачивает код репозитория на машину
actions/setup-python@v6Ставит Python указанной версии
run: pip install …Команда в терминале машины: зависимости проекта и документации
run: sphinx-build … -W --keep-goingСборка в строгом режиме из главы 4.13: предупреждение останавливает публикацию
actions/upload-pages-artifact@v4Упаковывает папку docs/build/html для передачи в Pages
deploy: → needs: buildВторое задание — публикация; начинается, только если сборка прошла
environment: github-pagesОкружение публикации; в нём GitHub запоминает адрес сайта и показывает его на странице запуска
actions/deploy-pages@v4Выкладывает упакованную папку на Pages. Через id: deployment адрес передаётся в строку url

Строка uses: подключает готовое действие из другого репозитория GitHub: actions/checkout — репозиторий checkout организации actions, которую ведёт сам GitHub. После @ — номер основной версии действия. Строка run: выполняет команду в терминале машины.

На полях: команды без .venv

На машине Actions окружение .venv не создаётся: она запускается заново для каждого запуска и после него удаляется, поэтому пакеты ставятся прямо в её Python. Отсюда короткая запись sphinx-build без пути — так, как в терминале с активированным окружением.

§6Включение Pages и первая публикация

Проект должен лежать в собственном репозитории на GitHub, в корне — app, docs, requirements.txt и .github. Как создать репозиторий и отправить в него проект, разобрано в справочнике по Git и GitHub.

Проверьте сборку на своём компьютере в строгом режиме

sphinx-build -M html docs/source docs/build -E -W --keep-going должна закончиться строкой сборка успешна.. На машине Actions выполняется та же команда, и предупреждение, пропущенное здесь, остановит публикацию там.

Проверьте, что в docs/source/_static лежит файл .gitkeep (глава 4.12, §7). Без него папки не будет в репозитории, и сборка на машине Actions остановится на предупреждении элемент html_static_path '_static' не существует.

Выберите GitHub Actions источником Pages

На странице репозитория откройте вкладку Settings, в левой колонке — раздел Pages. В блоке Build and deployment в списке Source выберите GitHub Actions. Сохранять отдельно не нужно: выбор применяется сразу.

Вариант Deploy from a branch в том же списке публикует файлы, которые лежат в ветке. Для сайта Sphinx он не подходит без сборки на своём компьютере и коммита папки build, от которых курс отказался в главе 4.12.

Отправьте коммит с docs и workflow

Закоммитьте docs/ (без docs/build — он в .gitignore), docs/requirements.txt и .github/workflows/docs.yml, отправьте в main кнопкой Sync Changes в VS Code или командой git push.

Найдите запуск на вкладке Actions

Откройте вкладку Actions репозитория. В списке слева — workflow «Документация», справа — запуск с текстом последнего коммита. Жёлтый кружок означает, что запуск идёт, зелёная галочка — прошёл, красный крестик — ошибка. Откройте запуск: на схеме два прямоугольника, build и deploy, соединённые стрелкой. Под deploy после завершения появляется адрес сайта.

Откройте сайт

Адрес — https://логин.github.io/имя-репозитория/; он же показан в Settings → Pages строкой Your site is live at. Откройте его и пройдите по страницам: главная, «Запуск и проверки», пакеты, поиск. Сайт тот же, что на вашем диске, но открыт по адресу https:// и доступен любому, у кого есть ссылка.

Дальше сайт обновляется сам: исправьте докстринг, отправьте коммит, и через минуту-две на сайте новая версия.

§8Соберите сами

Первые три задания выполняются на своём компьютере, четвёртое — в репозитории на GitHub. Команды записаны коротко, для терминала с активированным окружением.

Соберите сами · тема и публикация

Четыре опыта: три темы на одной странице, тема без установки, пропавшая папка _static и запуск workflow вручную.

Три темы на одной странице

  1. Установите sphinx-rtd-theme: pip install sphinx-rtd-theme.
  2. По очереди задайте html_theme равным 'alabaster', 'sphinx_rtd_theme' и 'furo'; после каждой правки соберите и откройте страницу пакета app.services.
  3. Сравните с кадрами в §1. Остановитесь на 'furo'.
Что должно получиться

Три разных вида страницы при одном и том же тексте: описания функций, поля «Параметры» и «Результат» и оглавление совпадают. Имя темы пишется с подчёркиванием (sphinx_rtd_theme), а пакет для установки — через дефисы (sphinx-rtd-theme).

Тема без установки

  1. Задайте html_theme = 'pydata_sphinx_theme' — эта тема не установлена.
  2. Соберите и прочитайте последние строки вывода.
  3. Верните 'furo'.
Что должно получиться

Сборка останавливается до чтения страниц. Первая строка отчёта — Theme error!, в разделе Traceback последняя строка — no theme named 'pydata_sphinx_theme' found (missing theme.toml?): темы с таким именем нет в окружении. Папка docs/build/html остаётся от прошлой сборки, новых страниц нет.

Пропавшая папка _static

  1. Переименуйте docs/source/_static в docs/source/_static_old.
  2. Соберите с -q -E -W --keep-going и проверьте код завершения: echo $?$LASTEXITCODE.
  3. Верните прежнее имя.
Что должно получиться

Строка WARNING: элемент html_static_path '_static' не существует и код 1. Так выглядит сборка на машине Actions, если в репозитории нет файла .gitkeep.

Запуск вручную и сломанная сборка

  1. На вкладке Actions выберите слева «Документация», справа нажмите Run workflow и подтвердите ветку main.
  2. Допишите в любой докстринг одиночную * перед цифрой, как в главе 4.13, §7, закоммитьте и отправьте.
  3. Откройте запуск, найдите шаг с ошибкой и строку WARNING. Откройте сайт.
  4. Исправьте докстринг и отправьте ещё один коммит.
Что должно получиться

Ручной запуск проходит и публикует сайт заново. Запуск со звёздочкой падает на шаге sphinx-build с предупреждением Inline emphasis start-string without end-string, задание deploy не начинается, на сайте остаётся прежняя версия. Запуск с исправлением проходит.

§9Проверьте себя

Что меняется при смене темы и что нет?

Меняются шаблоны, стили и расположение навигации. Текст страниц, описания функций и оглавление остаются прежними: их строит Sphinx до применения темы.

Почему Sphinx и Furo записаны в отдельный docs/requirements.txt?

Программе они для работы не нужны. Отдельный список ставят только там, где собирают документацию: на своём компьютере и в GitHub Actions.

Почему источником Pages выбран GitHub Actions?

Папка docs/build в репозиторий не попадает. Готовые страницы собирает машина Actions из исходников и передаёт в Pages напрямую.

Что будет с сайтом, если коммит сломал сборку?

Задание build завершится ошибкой, deploy не начнётся, и на сайте останется последняя исправная версия.

Зачем в workflow ключ -W?

Чтобы предупреждение о разметке или о ненайденном модуле остановило публикацию. Без него на сайт попадёт страница с ошибкой, а запуск будет зелёным.

Итог главы

Тема оформления задаёт вид страниц и меняется одной строкой html_theme, без правок текста. В курсе выбрана Furo: дерево всех страниц слева, светлая и тёмная схема, вёрстка для телефона. Sphinx и тему записывают в отдельный docs/requirements.txt с точными версиями. Публикует сайт GitHub Pages, а собирает его GitHub Actions по файлу .github/workflows/docs.yml: задание build ставит зависимости и выполняет sphinx-build со строгим ключом -W, задание deploy выкладывает папку docs/build/html. Источник Pages в настройках репозитория — GitHub Actions. Сайт обновляется после каждой отправки в main, а сломанная сборка оставляет на сайте прежнюю версию. Следующая глава — практика: весь путь от пустой папки до опубликованного сайта на своём проекте.
