§1Как работать с примерами

Каждый пример главы — содержимое файла proba.py в корне второго архива проекта, того же, что в главе 4.3. Под файлом — ответ команды .venv/bin/mypy proba.py.venv\Scripts\mypy proba.py, полученный запуском. Номера строк в ответе считаются от первой строки файла, поэтому файл нужно копировать целиком, вместе с импортами и пустыми строками.

Порядок работы с каждым примером одинаковый:

  1. Замените содержимое proba.py кодом примера и сохраните файл.
  2. Посмотрите, какие строки подчеркнул Pylance, и наведите указатель на подчёркивание.
  3. Выполните в терминале .venv/bin/mypy proba.py.venv\Scripts\mypy proba.py и сверьте ответ с книгой.
  4. Исправьте ошибки по разбору под примером и запустите проверку снова: ответ должен смениться на Success.

В начале каждого раздела стоит ссылка на параграф главы 4.2, где объяснена запись типа. Здесь запись заново не объясняется: раздел начинается сразу с файла.

Pylance в режиме basic подчёркивает почти те же строки, что mypy, но формулирует сообщения по-своему. Где поведение двух программ различается, об этом сказано в разборе.

§2Простые типы: передано не то значение

Запись простых типов — глава 4.2, §1. Самая частая ошибка с ними — значение не того типа в вызове.

В примере две новые функции с простыми типами и вызовы функций проекта: два верных и три неверных.

Разбор по строкам:

  • Строка 13, format_kopeks(125000) — ошибки нет: передано целое число, как в аннотации kopeks: int.
  • Строка 14 — сумма передана строкой "1250". Так бывает, когда значение прочитано из файла и не переведено в число. Исправление — передать число: format_kopeks(1250), а если значение пришло строкой — format_kopeks(int(value)).
  • Строка 15 — в normalize_name передано число вместо имени.
  • Строка 16 — аргумент передан по имени, и mypy называет его по имени: Argument "limit". Для позиционных аргументов в сообщении стоит номер: Argument 1.
  • Строка 17, share(3, 4) — ошибки нет. Внутри 3 / 4 даёт 0.75, и аннотация результата -> float с этим совпадает: деление / в Python всегда возвращает дробное число.

У int и float есть особое правило: где ожидается float, можно передать int. Целое число считается частным случаем дробного. Обратное не верно:

В строке 5 целое 4937 принято на место float. В строке 7 дробное 5.0 передано туда, где ждут целое количество чеков, и mypy это отклонил, хотя по значению 5.0 равно 5: проверка сравнивает типы, значения она не вычисляет.

§3None: пропущенный return и лишнее присваивание

Запись -> None — глава 4.2, §1.

С аннотацией результата проверка следит за двумя ошибками: функция обещает значение, но не во всех случаях его возвращает, и результат функции -> None пытаются использовать.

  • Строка 4 — Missing return statement, «нет инструкции return». Функция обещает строку, но при kopeks, равном нулю, условие не выполнится, и функция вернёт None. Исправление — вернуть строку и во втором случае: добавить в конце return "выручки нет".
  • Строка 9 — результат print_report сохраняется в переменную, но функция всегда возвращает None: «не возвращает значение». Исправление — вызвать функцию без присваивания: print_report(["Смена"]).

Вторую ошибку Pylance в режиме basic не показывает; первую подчёркивает с правилом reportReturnType.

§4Списки: не тот элемент

Запись списков — глава 4.2, §2.

Аннотация списка проверяет не только присваивание, но и всё, что со списком делают потом: добавление элементов, чтение элемента в переменную.

  • Строки 3–6 — четыре верных объявления, ошибок нет.
  • Строка 8 — в список оценок добавлена строка "5". Сообщение Argument 1 to "append" of "list" — «первый аргумент метода append у списка»: проверка подставила тип элементов int в метод append и сверила с ним аргумент.
  • Строка 9 — в список имён добавлено None. Список, где могут быть пропуски, записывают как list[str | None] — об этом в §9.
  • Строка 10 — вместо объекта Order добавлен словарь с теми же полями. Для проверки это разные типы: у словаря нет полей .waiter и .kopeks, и следующая строка order.kopeks упала бы при запуске. Исправление — orders.append(Order("Сидоров Илья", 77200)).
  • Строка 11 — элемент списка list[int] — целое число, а переменная объявлена строкой. Сообщение Incompatible types in assignment читается как «несовместимые типы при присваивании»: выражение справа имеет тип int, переменная — str.

§5Словари: не тот ключ, не то значение

Запись словарей — глава 4.2, §2. У словаря проверяются и ключи, и значения.

В примере три словаря и четыре неверные записи в них. В конце файла — перебор пар словаря с запросом типа: так видно, что проверка знает тип и ключей, и значений.

  • Строка 5 — значение выручки записано строкой с запятой, как его печатают в отчёте. В словаре хранятся копейки целым числом: revenue["Петрова Анна"] = 248050.
  • Строка 6 — ключ не того типа. Код index и слова Invalid index type означают «неверный тип индекса»: всё, что стоит в квадратных скобках после словаря, сверяется с типом ключей.
  • Строка 7 — в журнал оценок вместо списка записано одно число. Нужно journal["Сидоров"] = [5].
  • Строка 8 — в строке CSV все значения — строки, и row["kopeks"] — тоже строка. Чтобы получить число, его преобразуют: kopeks: int = int(row["kopeks"]). Так сделано в load_orders.
  • Строка 10 — note в ответ на reveal_type. При переборе revenue.items() проверка знает тип и ключа, и значения: total — int.

§6Кортежи: не та длина, не тот порядок

Запись кортежей — глава 4.2, §2. У кортежа tuple[int, int] проверяются длина и тип каждого места.

В примере сначала результат grade_bounds разобран на две переменные, затем пять объявлений кортежей: три верных и два неверных — с лишним элементом и с переставленными элементами.

  • Строка 3–4 — результат grade_bounds разобран на две переменные, и каждая получила тип своего места: low — int.
  • Строка 6 — три элемента там, где обещано два. Проверка сравнивает длину: tuple[int, int, int] не совпадает с tuple[int, int].
  • Строка 8 — элементы переставлены. Длина совпадает, но на первом месте ждут строку, а стоит число.
  • Строки 9–10 — с многоточием подходит кортеж любой длины, в том числе пустой.

Порядок элементов в паре проверка видит только по типам. В tuple[int, int] у grade_bounds что идёт первым — минимум или максимум, — аннотация не сообщает: это пишут в описании функции.

§7Множества: не тот элемент

Запись множеств — глава 4.2, §2.

Сообщение такое же, как у append в §4: метод множества add принимает только элементы объявленного типа.

Старая запись коллекций — List[int], Dict[str, int] с импортом из typing — проверяется так же и даёт те же сообщения.

§8Классы: опечатка в поле, словарь вместо объекта

Запись классов — глава 4.2, §3.

Когда тип — класс, проверка знает его поля и методы. Поэтому она находит и опечатки в именах атрибутов.

  • Строка 10 — опечатка в имени поля: kopek вместо kopeks. mypy не только сообщает, что такого атрибута нет, но и предлагает похожее имя: maybe "kopeks"?. Без аннотации order: Order эта опечатка обнаружилась бы только при запуске.
  • Строка 15 — словарь вместо заказа, как в §4 со списком.
  • Строка 16 — дата передана строкой. Argument 1 to "Shift" — первый аргумент при создании объекта, то есть параметр day метода __init__. Исправление — Shift(date(2026, 9, 21)).
  • Строка 18 — путь передан строкой. При запуске этот вызов сработает: функция open внутри read_rows принимает и строку, и Path. Проверка же сверяет с аннотацией, а в ней записан Path. Есть два исправления: передавать Path("data/smena.csv"), как в main.py, или, если функция должна принимать оба вида, расширить аннотацию до path: str | Path.

§10Объединения: работа без проверки варианта

Запись объединений — глава 4.2, §5. В первом примере вариант проверен через isinstance, во втором — нет.

Внутри условия isinstance(value, str) тип сужен до str (строка 3), после условия — до int (строка 5): строки туда уже не доходят, остаётся второй вариант. Вызовы с числом и со строкой прошли, с дробным числом — нет: float в перечне вариантов не значится.

Без проверки варианта проверка отклонит код, даже если для одного из вариантов он верен:

Для строки выражение "125" * 100 даёт строку из ста повторов "125". Сообщение Incompatible return value type (got "int | str", expected "int") — «тип возвращаемого значения несовместим: получено int | str, ожидалось int». Объединения используют там, где данные действительно приходят в разном виде. Когда вариант один, объединение только добавляет проверок в вызывающий код.

§11Генераторы и функции-аргументы: не та функция

Запись Iterator и Callable — глава 4.2, §6. Первый пример показывает, что проверка знает тип значений, которые отдаёт генератор.

Переменная цикла получила тип элемента — int.

Во втором примере параметр fix записан как Callable[[str], str] — «функция, которая принимает строку и возвращает строку». В него по очереди передают три функции.

Строки 10 и 11 проходят: normalize_name и метод str.upper принимают строку и возвращают строку. В строке 12 передана len — она возвращает число и принимает любой объект с длиной, в сообщении он назван Sized. Проверка сравнила описание переданной функции с ожидаемым и нашла несовпадение в результате.

§12Псевдонимы: какой тип видит проверка

Запись псевдонимов — глава 4.2, §7. Пример показывает, что проверка видит за псевдонимом исходный тип.

Для проверки Kopeks и int — один и тот же тип: результат показан как builtins.int. Поэтому отличить копейки от рублей проверка не сможет: передать в total словарь с рублями — не ошибка типа.

§13Any: ошибка, которую проверка пропускает

Запись Any — глава 4.2, §8. Пример показывает, что для значения типа Any проверка ничего не сверяет. Тот же Any Pylance показывал в главе 4.1 у параметров без аннотаций.

У строки нет метода to_kopeks, и при запуске будет AttributeError, но проверка ошибок не нашла: для Any она ничего не сверяет. Any ставят там, где тип действительно неизвестен заранее, например у данных из внешней библиотеки без аннотаций. Убирать им замечание проверки нельзя: замечание исчезнет вместе с самой проверкой. В работах курса Any не используется.

§14Переменные: пустая коллекция без аннотации

Где переменным нужна аннотация — глава 4.2, §9. Проверка сама сообщает о таком месте:

Need type annotation — «нужна аннотация типа». В скобках mypy подсказывает форму записи: вместо <type> подставляют типы, например totals: dict[str, int] = {}, как в revenue_by_waiter. Pylance в режиме basic об этом случае не сообщает.

§16Проверьте себя

mypy ответил Argument 1 to "append" of "list" has incompatible type "str"; expected "int". Что произошло?

В список, объявленный как list[int], методом append добавляют строку. Нужно добавить целое число.

Чем сообщение с кодом index отличается от сообщения с кодом assignment у словаря?

index — неверный тип ключа, того, что стоит в квадратных скобках. assignment — неверный тип значения справа от знака =.

Какие две ошибки проверка находит у кортежа tuple[str, int]?

Не ту длину — например, три элемента вместо двух — и не тот порядок: число на первом месте, строка на втором.

Почему average_check(4937, 5) проходит проверку при total: float, а average_check(4937.5, 5.0) — нет?

Где ожидается float, разрешено передать int. Второй параметр — count: int, и дробное 5.0 туда не подходит, хотя по значению равно пяти.

Функция возвращает Order | None. Почему проверка не даёт сразу обратиться к result.kopeks?

В результате может оказаться None, у которого нет поля kopeks. Сначала нужна проверка if result is not None: внутри неё тип сужается до Order.

Что вернёт revenue.get("Сидоров Илья") для revenue: dict[str, int] и как получить всегда число?

Тип результата — int | None: если ключа нет, вернётся None. Со значением по умолчанию — revenue.get("Сидоров Илья" — результат всегда int.

Что означает сообщение Missing return statement?

Функция обещает вернуть значение, но в одной из веток return со значением нет, и там вернётся None.

Почему Any нельзя ставить, чтобы убрать замечание проверки?

С Any проверка перестаёт сверять значение: вызов несуществующего метода проходит проверку и завершается ошибкой только при запуске.

Почему у totals = {} нужна аннотация, а у count = 0 — нет?

По нулю проверка выводит тип int. По пустому словарю нельзя узнать тип ключей и значений, и mypy сообщает Need type annotation.

Итог главы

Почти все ошибки в примерах — «передан не тот тип»: mypy называет в сообщении, что пришло и что ожидалось, а код в квадратных скобках указывает место — вызов, присваивание или return. У коллекций проверяется содержимое: элементы списка и множества, ключи и значения словаря, длина и порядок кортежа. Когда тип — класс, проверка находит опечатки в именах полей. С X | None она требует сначала убедиться, что значение не None, и после условия сужает тип. За псевдонимом проверка видит исходный тип, а для Any не сверяет ничего. В главе 4.5 те же сообщения появятся в собственном коде: аннотации расставляются в проекте, где их нет.

§1Как работать с примерами

Каждый пример главы — содержимое файла proba/main.go во втором архиве проекта, том же, что в главе 4.3. Под файлом — ответ команды go run ./proba, полученный запуском. Номера строк в ответе считаются от первой строки файла, поэтому файл нужно копировать целиком, вместе с package и импортами.

Порядок работы с каждым примером одинаковый:

  1. Замените содержимое proba/main.go кодом примера и сохраните файл.
  2. Посмотрите, какие строки подчеркнул gopls, и наведите указатель на подчёркивание.
  3. Выполните в терминале go run ./proba и сверьте ответ с книгой.
  4. Исправьте ошибки по разбору под примером и запустите снова: программа должна собраться и напечатать результат.

Команда go run сначала собирает программу. Если сборка не удалась, она печатает ошибки компилятора — строки вида proba/main.go:15:33: … под заголовком # example.com/otchet-kafe/proba — и ничего не запускает. Если сборка прошла, программа выполняется, и в ответе её вывод. Так в одном ответе видны оба рода ошибок: те, что находит компилятор, и те, что случаются при работе.

В начале каждого раздела стоит ссылка на параграф главы 4.2, где объяснена запись типа. Здесь запись заново не объясняется: раздел начинается сразу с файла. gopls показывает в редакторе те же сообщения, что и компилятор, с тем же текстом.

§2Простые типы: передано не то значение

Запись простых типов — глава 4.2, §1. Самая частая ошибка с ними — значение не того типа в вызове. В примере функция isBig и вызовы функций проекта: один верный и три неверных.

Разбор по строкам:

  • Строка 14, FormatKopeks(125000) — ошибки нет: передано целое число, как в подписи kopeks int.
  • Строка 15 — сумма передана строкой "1250". Так бывает, когда значение прочитано из файла и не переведено в число. Исправление — передать число: FormatKopeks(1250), а если значение пришло строкой — сначала перевести его: kopeks, err := strconv.Atoi(value).
  • Строка 16 — в NormalizeName передано число вместо имени.
  • Строка 17 — порог передан словами. Сообщение называет функцию isBig, но не номер аргумента: место показывают строка и столбец — 17:28 указывает ровно на "сто тысяч".

Слова untyped string constant в сообщениях означают «строка, записанная прямо в коде». У такой константы ещё нет окончательного типа, и компилятор пробует перевести её в тип параметра. Число 42 в строку не переводится, строка в число — тоже, отсюда ошибка.

С дробными числами правило то же, и оно отличается от Python: там, где ждут float64, целое передать можно только константой, записанной в коде. Переменная типа int не подойдёт.

Строки 10 и 11 собираются: константа 4937 переводится в float64 без потерь, а 5.0 — в int, потому что дробной части у неё нет. В строке 14 переданы переменные. У sum уже есть тип int, и компилятор не переводит его в float64 сам: variable of type int. Исправление — явный перевод: averageCheck(float64(sum), checks). В строке 15 5.5 нельзя сделать целым без потери — (truncated).

Та же строгость действует в арифметике: значения разных типов нельзя складывать и умножать.

Строка 9 собирается: int делится на int. Если бы программа запустилась, она напечатала бы 987 — целое деление отбрасывает дробную часть. Строка 10 — mismatched types int and float64, «несовпадающие типы»: целое умножается на дробное. Строка 11 — исправленный вариант: целое явно переведено в float64. Сообщения с mismatched types начинаются словами invalid operation — «недопустимая операция», и называют саму операцию: sum * share.

§3Результат: пропущенный return и функция без результата

Запись результата — глава 4.1, §3. С результатом компилятор следит за двумя ошибками: функция обещает значение, но возвращает его не во всех случаях, и результат функции без результата пытаются использовать.

  • Строка 9 — missing return, «нет инструкции return». Функция обещает строку, но если kopeks не больше нуля, условие не выполнится, и вернуть будет нечего. Место ошибки — закрывающая скобка функции: здесь выполнение дошло бы до конца без return. Исправление — вернуть строку и во втором случае: добавить перед скобкой return "выручки нет". В Python функция в этом случае тихо вернула бы None; в Go такое невозможно.
  • Строка 12 — результат PrintReport сохраняется в переменную, но у функции нет результата: (no value) used as value, «отсутствующее значение использовано как значение». Исправление — вызвать функцию без присваивания: ui.PrintReport([]string{"Смена"}).

§4Срезы: не тот элемент

Запись срезов — глава 4.2, §2. Тип среза проверяет не только объявление, но и всё, что со срезом делают потом: добавление элементов, чтение элемента в переменную.

  • Строки 6–9 — четыре верных объявления, ошибок нет. Строка 10 нужна, чтобы groups считалась использованной.
  • Строка 12 — в срез оценок добавлена строка "5". Сообщение in argument to append — «в аргументе функции append»: компилятор подставил тип элементов int в append и сверил с ним аргумент.
  • Строка 13 — в срез имён добавлен nil. У строки нулевое значение — пустая строка "", а nil строкой быть не может. Если в данных бывают пропуски, их хранят пустой строкой или заводят срез указателей []*string.
  • Строка 14 — вместо структуры Order добавлен словарь с теми же ключами. Для компилятора это разные типы: у словаря нет полей .Waiter и .Kopeks. Исправление — создать заказ: order, err := domain.NewOrder("Сидоров Илья", 77200) и добавить его.
  • Строка 15 — элемент среза []int — целое число, а переменная объявлена строкой: in variable declaration, «в объявлении переменной».

§5Словари: не тот ключ, не то значение

Запись словарей — глава 4.2, §2. У словаря проверяются и ключи, и значения. В примере три словаря и четыре неверные записи в них.

  • Строка 8 — значение выручки записано строкой с запятой, как его печатают в отчёте. В словаре хранятся копейки целым числом: revenue["Петрова Анна"] = 248050.
  • Строка 9 — ключ не того типа: in map index, «в индексе словаря». Всё, что стоит в квадратных скобках после словаря, сверяется с типом ключей.
  • Строка 10 — в журнал оценок вместо среза записано одно число. Нужно journal["Сидоров"] = []int{5}.
  • Строка 11 — в строке CSV все значения — строки, и row["kopeks"] — тоже строка: map index expression of type string. Чтобы получить число, его преобразуют: kopeks, err := strconv.Atoi(row["kopeks"]). Так сделано в LoadOrders.

Множество в Go — словарь map[string]bool, поэтому ошибки с ним те же: ключ не того типа отклоняется сообщением in map index.

§6Несколько результатов: не то число, не тот порядок

Несколько результатов — глава 4.1, §3. Компилятор требует принять их все: столько переменных, сколько значений возвращает функция.

Сообщение assignment mismatch: 2 variables but services.GradeBounds returns 3 values читается как «несовпадение при присваивании: две переменные, а функция возвращает три значения». Третье значение — ошибка, и её нельзя молча потерять. Исправление — принять все результаты: low, high, err := …, а если какой-то не нужен, поставить на его место _. Во второй строке забыт результат-ошибка у CalculateAverage.

Число результатов компилятор проверяет, а их порядок — только по типам. У GradeBounds минимум и максимум одного типа int, и если перепутать их местами, программа соберётся:

Ошибок сборки нет, а в отчёте минимум больше максимума. Компилятор не может знать, что первое значение — минимум: оба int. В Python у кортежа tuple[str, int] перестановку находила проверка, потому что типы мест различались; для tuple[int, int] не находила бы и она. Защита здесь — имена результатов в подписи (low, high int, err error), которые видны в подсказке редактора, и фраза о порядке в комментарии документации.

§7Структуры: опечатка в поле, словарь вместо структуры

Запись структур — глава 4.2, §3. Когда тип значения — структура, компилятор знает её поля и находит опечатки в именах.

  • Строка 15 — order.Kopek undefined (type domain.Order has no field or method Kopek): у заказа нет поля Kopek, есть Kopeks. В Python без аннотаций такая опечатка обнаружилась бы только при запуске. Сообщение называет тип, в котором искалось поле, — по нему видно, что компилятор правильно понял, что за значение слева от точки.
  • Строка 16 — поле Waiter есть, но это строка, и поля Kopeks у строки нет: type string has no field or method Kopeks.
  • Строка 17 — unknown field Name in struct literal: при создании структуры указано поле, которого в ней нет. Поле имени называется Waiter.
  • Строка 18 — вместо среза заказов передан срез словарей с теми же ключами. Типы разные, и функция его не примет.

§8Значение или ничего: nil там, где его быть не может

Три способа записать «значение или ничего» — глава 4.2, §4. Первая ошибка — попытка вернуть nil вместо структуры, по привычке к return None из Python.

cannot use nil as domain.Order value in return statement: у структуры нет значения nil. Исправление зависит от выбранного способа: вернуть пустую структуру и признак — return domain.Order{}, false с подписью (domain.Order, bool) — или сделать результат указателем *domain.Order, у которого nil есть.

С указателем компилятор такую ошибку уже не найдёт, и появляется другая — обращение к полю через пустой указатель. Она собирается и проявляется только при работе:

Первая строка вывода показывает, что программа собралась и запустилась. На строке 23 она остановилась: panic — аварийная остановка, invalid memory address or nil pointer dereference — «обращение по пустому указателю». Ниже — трассировка: где именно случилась паника, main.go:23. Путь к файлу в трассировке у вас будет свой, а числа вида 0x… меняются от запуска к запуску. exit status 2 — код завершения программы.

Исправление — проверить указатель перед обращением: if found != nil { fmt.Println(found.Kopeks) }. В Python проверка mypy требовала такое условие для Order | None; компилятор Go для указателя его не требует, поэтому проверку пишут по привычке, а находят пропущенную — тесты.

§9Интерфейсы: нет метода

Интерфейсы — глава 4.2, §5. Значение подходит под интерфейс, если у него есть все методы интерфейса. Компилятор это проверяет и называет пропущенный метод.

  • Строка 20 — ошибки нет: shift — указатель *domain.Shift, у него метод TotalKopeks есть.
  • Строка 21 — передана сама смена, без указателя: *shift разыменовывает указатель. Сообщение длинное, главное в конце: method TotalKopeks has pointer receiver, «у метода получатель-указатель». Метод объявлен как func (s *Shift) TotalKopeks(), и есть он только у *Shift, а у Shift — нет. Исправление — передавать указатель, как в строке 20.
  • Строка 22 — у числа методов нет: missing method TotalKopeks.

Сообщения об интерфейсах состоят из двух частей через двоеточие: сначала общее «нельзя использовать как Priced», затем причина — какого метода не хватает или почему он не подходит.

§10Функции-аргументы: не та функция

Тип функции — глава 4.2, §6. Параметр fix записан как func(string) string — «функция, которая принимает строку и возвращает строку». В него по очереди передают три функции.

Строки 21 и 22 собираются: NormalizeName и strings.ToUpper принимают строку и возвращают строку. В строке 23 передана utf8.RuneCountInString — она принимает строку, но возвращает число. Сообщение показывает её полный тип func(s string) (n int) рядом с ожидаемым func(string) string: имена параметров для совпадения типов не важны, важны типы и их порядок.

§11Новый тип: копейки и рубли

Новый тип и псевдоним — глава 4.2, §7. Пример показывает, чем они отличаются для компилятора.

  • Строка 18 собирается: Revenue — псевдоним, и map[string]int под него подходит без преобразования.
  • Строка 22 — mismatched types Kopeks and Rubles: оба типа хранят целое число, но это разные типы, и сложить копейки с рублями нельзя. Ради этого новые типы и заводят. В Python псевдоним Kopeks = int такую ошибку не находил.
  • Строка 23 — то же с обычным int: переменная count имеет тип int, и умножить на неё Kopeks без перевода нельзя. Исправление — price * Kopeks(count).
  • Строка 24 собирается: 3 — константа без типа, и компилятор переводит её в Kopeks сам.

§12any: ошибка, которую компилятор пропускает

Тип any — глава 4.2, §8. В отличие от Any в Python, со значением any компилятор не разрешает ничего, кроме передачи дальше:

mismatched types any and untyped int: к значению неизвестного типа нельзя прибавить число. Чтобы работать со значением, сначала нужно утверждение типа. Короткая форма value.(int) компилятор устраивает, но переносит проверку на время работы:

Первый вызов напечатал 126: внутри any было число. Второй остановил программу: interface conversion: interface {} is string, not int — «внутри строка, а не число». Строка main.parse(...) в трассировке без адреса: компилятор встроил маленькую функцию в место вызова. Компилятор эту ошибку пропустил: какой тип окажется внутри any, становится известно только при работе. Исправление — форма с признаком n, ok := value.(int) или переключатель switch v := value.(type), как в главе 4.2, а лучше — настоящий тип параметра вместо any.

§13Переменные: лишние и нулевые

Объявления переменных — глава 4.2, §9. Компилятор Go строже Python к лишнему коду: неиспользованные переменные и импорты — ошибки сборки.

  • Строка 5 — "strings" imported and not used: пакет импортирован, но ни одно его имя не используется. В VS Code с расширением Go лишние импорты удаляются сами при сохранении файла.
  • Строка 10 — declared and not used: heading: переменная объявлена и ни разу не прочитана. Обычно это след незаконченной правки: значение вычислили и забыли использовать.
  • Строка 11 — no new variables on left side of :=. Запись := объявляет новую переменную, а total уже объявлена в строке 9. Чтобы изменить значение, пишут обычное присваивание: total = 125000.

§15Проверьте себя

Компилятор ответил cannot use "5" (untyped string constant) as int value in argument to append. Что произошло?

В срез []int через append добавляют строку. Нужно добавить целое число.

Почему averageCheck(4937, 5) собирается при total float64, а averageCheck(sum, checks) с переменными int — нет?

4937 — константа без типа, компилятор переводит её в float64 сам. У переменной sum тип уже есть — int, и его переводят явно: float64(sum).

Что означает missing return и почему место ошибки — закрывающая скобка функции?

Функция обещает результат, но в одной из веток return нет. Выполнение в этой ветке дошло бы до закрывающей скобки, не вернув значения, — туда компилятор и указывает.

Перепутанные high, low, err := GradeBounds(…) собираются. Почему компилятор не нашёл ошибку?

Оба значения типа int, а компилятор сверяет только типы. Что первое значение — минимум, он не знает. Защита — имена результатов в подписи и комментарий документации.

Почему *shift не подходит под интерфейс с методом TotalKopeks, а shift подходит?

Метод объявлен с получателем-указателем (s *Shift) и есть только у *Shift. *shift — значение типа Shift, у него этого метода нет.

Почему price + tip при Kopeks и Rubles — ошибка, хотя оба хранят целое число?

type Kopeks int и type Rubles int создают два разных новых типа. Операции между разными типами запрещены без явного перевода, и копейки с рублями случайно не сложить.

Какие из ошибок главы компилятор не находит?

Обращение через пустой указатель, неверное утверждение типа у any, запись в нулевой словарь и перепутанный порядок значений одного типа. Первые три останавливают программу при работе с panic, четвёртая даёт неверный результат без остановки.

Итог главы

Почти все ошибки в примерах — «передан не тот тип»: компилятор называет значение, его тип и тип, который ожидался, а слова после in указывают место — аргумент, присваивание, ключ словаря, return. Числа разных типов не смешиваются ни в вызове, ни в выражении; константы без типа компилятор переводит сам, переменные — нет. Проверяются число результатов, поля структур, методы интерфейсов и типы функций-аргументов. Новый тип не смешивается даже с типом, на котором основан. Неиспользованные переменные и импорты — ошибки сборки. Пропускает компилятор то, что зависит от данных при работе: пустой указатель, содержимое any, нулевой словарь, порядок значений одного типа. В главе 4.5 те же сообщения появятся в целом проекте: двенадцать ошибок в архиве, который не собирается.
