§1Что редактор делает без расширений

Расширение Python от Microsoft вместе с языковым сервером Pylance устанавливается в VS Code одним пакетом и выполняет две задачи из этой темы.

ВозможностьКак пользоваться
Подсказка с докстрингом при наведении на имя функцииУказатель на имя, либо CtrlCmd + K, затем CtrlCmd + I
Подсказка при наборе аргументов вызоваОткрывается сама после открывающей скобки; вызвать заново — CtrlCmd + Shift + Пробел

Заготовку докстринга по подписи функции встроенные средства не создают. Для этого ставят отдельное расширение.

§2Расширение autoDocstring

autoDocstring — расширение VS Code, которое читает подпись функции и вставляет заготовку докстринга: краткую строку, раздел с параметрами по именам аргументов, раздел результата и раздел исключений, если в теле есть raise. Текст описаний пишет человек, разметку и перечень имён — расширение.

Установка: откройте панель расширений (CtrlCmd + Shift + X), введите в поиске идентификатор и нажмите Install.

Расширение ищут по идентификатору: в поиске есть несколько расширений с похожими названиями, и идентификатор отличает нужное однозначно.

§3Как вызвать генератор

Разберём вставку на функции revenue_by_waiter из файла app/services/orders.py стартового архива. Порядок такой:

  1. Откройте файл и поставьте курсор на строку с def — ту, у которой нужно описание.
  2. Нажмите End (CtrlCmd + →) и затем Enter: под подписью появится пустая строка с отступом тела.
  3. Вызовите генератор любым из трёх способов: наберите три двойные кавычки и нажмите Enter; либо нажмите CtrlCmd + Shift + 2; либо откройте палитру команд (CtrlCmd + Shift + P) и выберите Generate Docstring.
  4. Заполните поля заготовки, переходя между ними клавишей Tab.
На полях: пустая строка под подписью нужна

Генератор вставляет заготовку на место курсора. Если вызвать его, когда курсор стоит в первой колонке строки def, описание встанет выше функции и код перестанет работать. Если курсор окажется на первой строке тела, закрывающие кавычки попадут в одну строку с кодом. Поэтому сначала делают пустую строку — шаг 2 из списка.

Оставленные в коде _description_ — это докстринг, который повторяет перечень имён параметров, уже известный из подписи. Проверка из §9 на незаполненные описания не жалуется: докстринг формально есть. Она заметит только _summary_ без точки на конце — правилом D415, и это видно в §11. Поэтому заготовку заполняют, пока функция в работе.

§4Настройка формата в проекте

По умолчанию расширение вставляет формат google. Формат задают явно, чтобы у всех в команде получалась одинаковая разметка. Настройка хранится в файле .vscode/settings.json внутри проекта и попадает в репозиторий вместе с кодом.

Значение параметра docstringFormat выбирается из перечня форматов расширения:

ЗначениеЧто вставляет
googleРазделы Args:, Returns:, Raises: — формат курса
google-notypesТо же без повтора типов в скобках
numpyЗаголовки разделов с чертой из дефисов
sphinxПоля :param:, :returns:, :raises:
pep257Краткая строка и место под описание, без разделов
one-line-sphinxПоля reStructuredText в сжатой записи

Для проектов курса подходит google-notypes: типы остаются в подписи функции и в докстринге не повторяются. Начать можно с google и убирать типы вручную, пока формат не стал привычным.

§5Где лежат настройки

У VS Code два уровня настроек. Настройки проекта лежат в папке .vscode рядом с кодом и действуют на всех, кто откроет этот репозиторий. Настройки пользователя действуют на все проекты этого компьютера и в репозиторий не попадают.

Оба файла открываются через палитру команд: Preferences: Open Workspace Settings (JSON) для проекта и Preferences: Open User Settings (JSON) для пользователя. Путь при этом искать не нужно.

На полях: папку .vscode держат в репозитории

В .gitignore учебных проектов .vscode/ не вносят. Файл настроек проекта — часть договорённостей команды: формат докстрингов, включённые проверки, выбранный интерпретатор. Личные настройки в этот файл не пишут, для них есть настройки пользователя.

§7Свой шаблон

Встроенные форматы меняются через шаблон на языке mustache: в нём подстановки вида {{name}} заменяются данными из подписи функции. Шаблон кладут в репозиторий и указывают путь в настройках проекта.

Этот шаблон отличается от встроенного google одним: типы в разделе Args: не подставляются, потому что они уже есть в подписи. Разделы Args:, Raises: и Returns: вставляются только тогда, когда у функции есть параметры, raise в теле и возвращаемое значение.

§8Сниппет вместо расширения

Заготовку можно вставлять и средствами самого редактора, без расширения. Сниппет — шаблон текста, который вставляется по короткому слову и клавише Tab. Сниппеты проекта лежат в файле с расширением .code-snippets в папке .vscode.

Наберите dsg и нажмите Tab — вставится этот текст, курсор встанет в первое поле, переход между полями по Tab. Имена параметров сниппет не подставляет: он вставляет заранее записанный текст, одинаковый для любой функции. Зато установки он не требует и работает в любой сборке редактора.

§9Проверка докстрингов программой

Генератор вставляет разметку, но не показывает места, где описания нет. Их находит проверка кода. В курсе используется Ruff — программа проверки кода на Python, в которую входят правила pydocstyle: они отвечают за докстринги и обозначаются кодами с буквой D.

Правила включаются в файле pyproject.toml в корне проекта:

Три части этого файла означают следующее. Набор "D" включает правила о докстрингах вместе с обычными проверками кода. Строка convention = "google" согласует правила с выбранным форматом: часть правил, относящихся к другим форматам, отключается, чтобы требования не противоречили друг другу. Последний раздел снимает требование докстрингов с папки тестов: имя тестовой функции там само описывает проверяемый случай.

По коду правила его находят в документации Ruff, где описано, что оно проверяет и как исправить.

Правило D417 отличается от остальных тем, что сравнивает докстринг с кодом: перечень параметров в разделе Args: с подписью функции. Добавленный аргумент, для которого забыли строку описания, находится сразу. Остальные правила проверяют наличие описания и его оформление.

У части замечаний есть готовое исправление. Пример: заготовка генератора оставляет краткую строку _summary_ без точки на конце, и правило D415 предлагает её поставить.

На полях: правило про повелительную форму

Среди правил pydocstyle есть D401: первая строка докстринга записывается повелительной формой английского глагола. Конвенция google это правило не включает, и для русских описаний в форме «Считает…», «Возвращает…» замечаний не будет. Текущий перечень правил, входящих в конвенцию, приведён в документации Ruff по ссылке в конце главы.

§11Проверка в редакторе и в запросе на слияние

Чтобы замечания появлялись во время набора кода, ставят расширение Ruff, его идентификатор — charliermarsh.ruff. После установки нарушения подчёркиваются в файле и перечисляются в панели Problems (CtrlCmd + Shift + M), а часть из них исправляется действием Quick Fix по сочетанию CtrlCmd + ..

Путь пропущенного описания

1 · Код Функция дописана, докстринг забыт. программа работает
2 · Редактор Расширение Ruff подчёркивает строку def и пишет замечание в панель Problems. видно сразу
3 · Терминал ruff check app печатает файл, строку и код правила. перед коммитом
4 · Запрос на слияние Та же команда выполняется на стороне репозитория и отмечает проверку непройденной. до разбора работы

Шаги 2 и 3 зависят от одного файла настроек — pyproject.toml, поэтому редактор и терминал показывают одинаковые замечания.

§12Мини-практика: десять минут

  1. Установите расширение njpwerner.autodocstring через панель расширений.
  2. Создайте в проекте файл .vscode/settings.json с параметрами из §4.
  3. Откройте функцию без докстринга, поставьте курсор под подписью, наберите три кавычки и нажмите Enter. Заполните вставленные поля, переходя по Tab.
  4. Добавьте в pyproject.toml разделы из §9 и выполните ruff check app. Разберите каждое замечание по таблице §10.
  5. Исправьте замечания и добейтесь вывода All checks passed!.
  6. Добавьте в функцию новый параметр, не дописывая раздел Args:, и запустите проверку снова: появится D417. Верните докстринг в соответствие с подписью.

§13Частые вопросы

Обычно думаютРасширение создаёт документацию за разработчика.
На самом делеРасширение вставляет разметку и имена параметров из подписи. Описания остаются полями _description_, и текст в них пишет человек.
Обычно думаютПроверка Ruff показывает, что докстринг правильный.
На самом делеПроверка находит отсутствие докстринга, нарушения оформления и расхождение списка параметров с подписью. Верность описания по смыслу она не проверяет: докстринг с текстом _description_ для неё в порядке.
Обычно думаютНастройки редактора у каждого свои, в репозиторий их класть не нужно.
На самом делеФормат докстрингов и набор правил проверки — договорённость команды, и хранится она в .vscode/settings.json и pyproject.toml внутри репозитория. Личные настройки остаются в настройках пользователя.
Обычно думаютРаз есть генератор, докстринги можно расставить в конце разработки одним проходом.
На самом делеГенератор подставляет имена и разметку, а смысл описания восстанавливается чтением собственного кода. Пока функция в работе, эти сведения есть; через месяц их приходится выяснять заново.

§14Проверьте себя

Что вставляет autoDocstring и что остаётся человеку?

Расширение вставляет разметку выбранного формата, имена параметров из подписи, признак необязательности со значением по умолчанию, раздел Raises: при наличии raise в теле и раздел результата. Человек пишет краткую строку и описания на месте полей _description_.

Чем настройки проекта отличаются от настроек пользователя?

Настройки проекта лежат в .vscode/settings.json внутри репозитория и действуют у всех, кто его откроет: туда пишут формат докстрингов и общие правила. Настройки пользователя лежат в папке профиля VS Code, действуют на все проекты этого компьютера и в репозиторий не попадают.

Зачем в pyproject.toml строка convention = "google"?

Она согласует правила проверки с выбранным форматом: правила, относящиеся к другим форматам, отключаются. Без неё включённый набор "D" выдаёт замечания, требующие несовместимого оформления.

Что находит правило D417 и чем оно отличается от остальных?

Оно сравнивает параметры в подписи функции с перечнем в разделе Args: и находит расхождение, которое возникает после правки подписи: добавленный аргумент без описания или описание удалённого аргумента. Остальные правила проверяют наличие докстринга и его оформление, а это — соответствие докстринга коду.

Почему с папки тестов снимают требование докстрингов?

Имя тестовой функции описывает проверяемый случай: test_average_empty_list_raises. Отдельное описание повторяло бы имя. Поэтому в настройках проверки для папки тестов правила D отключают.

Проверка ruff check прошла без замечаний. Означает ли это, что документация в порядке?

Нет. Проверка отвечает за наличие докстрингов, их оформление и совпадение перечня параметров с подписью. Верность описания по смыслу и его соответствие поведению функции проверяет человек на разборе запроса на слияние.

Итог главы

Редактор с расширением Python показывает докстринг в подсказке, но заготовку по подписи не создаёт: для этого ставят расширение njpwerner.autodocstring. Оно вставляет разметку выбранного формата, имена параметров, признак необязательности и раздел исключений; описания пишет человек. Формат задают в .vscode/settings.json внутри репозитория, потому что это договорённость команды. Свой шаблон подключают файлом mustache, а простую заготовку можно получить сниппетом редактора без установки расширений. Пропущенные и неверно оформленные докстринги находит проверка: правила pydocstyle включаются в pyproject.toml набором "D" с конвенцией google и запускаются командой ruff check в редакторе и в проверках запроса на слияние. Правило D417 сравнивает перечень параметров в докстринге с подписью функции. Верность описания по смыслу проверяет человек. В следующей главе всё это применяется к своему проекту: практика на паре и домашнее задание.

  2. Уровни настроек и расположение файла настроек пользователя — документация VS Code, раздел Settings.
  3. Правила pydocstyle, их коды и конвенции — документация Ruff, перечень правил pydocstyle.
  4. Синтаксис сниппетов — документация VS Code, Snippets.

§2Почему нет генератора заготовок

В ветке Python для VS Code ставят расширение autoDocstring: оно читает подпись функции и вставляет заготовку с разделами Args:, Returns: и именами параметров. Для Go такого расширения нет. В комментарии Go нет разделов, которые можно было бы заполнить из подписи: параметры и ошибки описывают обычными предложениями (глава 4.7, §5). Заготовка свелась бы к имени функции, а имя gopls подсказывает при наборе, как показано в §1.

Поэтому порядок работы другой. В Python генератор вставляет разметку, после чего поля заполняют вручную. В Go текст пишут сразу, а затем программа проверяет, что комментарий есть и начинается с имени. Эта проверка разобрана во второй половине главы.

§3Сниппет комментария

Если хочется, чтобы редактор напоминал о строении подробного комментария, его записывают сниппетом. Сниппет — шаблон текста, который вставляется по короткому слову и клавише Tab. Сниппеты проекта лежат в файле с расширением .code-snippets в папке .vscode:

Наберите над функцией docf и нажмите Tab — вставятся три строки, курсор встанет в первое поле, переход между полями тоже по Tab. Ключ scope ограничивает сниппет файлами Go. Имя функции сниппет не подставляет: он вставляет заранее записанный текст, одинаковый для любой функции. В первое поле имя набирают с подсказкой gopls из §1.

§4Проверка комментариев программой

Подсказки помогают написать комментарий, но не показывают, где его нет. Это находит проверка кода. Компилятор и go vet комментарии не проверяют. В курсе используется revive — программа проверки стиля кода на Go. Одно из её правил, exported, требует комментарий у каждого экспортируемого имени и проверяет, что он начинается с этого имени. Второе, package-comments, требует комментарий пакета.

Строка устроена так же, как у компилятора: файл, строка, столбец и сообщение. exported type Order should have comment or be unexported — «у экспортируемого типа Order должен быть комментарий, или его нужно сделать неэкспортируемым». Второй вариант — переименовать в order со строчной буквы — подходит, только если имя действительно не нужно другим пакетам. В проекте нужны все, поэтому исправление одно — комментарий. Двадцать семь строк — это двадцать два экспортируемых имени и пять пакетов, включая main: столько комментариев предстоит написать.

По умолчанию revive завершается с кодом 0, даже если нашёл замечания. Для проверок, которые должны «падать» при замечаниях, добавляют флаг -set_exit_status: с ним revive завершается с кодом 1, и go run добавляет в конец вывода строку exit status 1.

Сообщения о форме проверены на опыте: в clock.go комментарий пакета // Пакет utils форматирует строки. дал package comment should be of the form "Package utils ...", комментарий // Возвращает текущую дату. над TodayLabel — comment on exported function TodayLabel should be of the form "TodayLabel ...". Комментарий типа вида // Kopeks — сумма. замечаний не дал: первым словом стоит имя.

Правило сравнивает только первое слово с именем объявления. Верность описания по смыслу оно не проверяет: комментарий // FormatKopeks делает всё. пройдёт проверку.

На полях: те же правила в staticcheck

У staticcheck из главы 4.3 есть похожие правила: ST1000 — нет комментария пакета, ST1020, ST1021, ST1022 — комментарий функции, типа или переменной не начинается с имени. По умолчанию они выключены и включаются флагом -checks. Требования «комментарий обязателен у каждого экспортируемого имени» в staticcheck нет, поэтому в курсе используется revive.

§7Где лежат настройки

У VS Code два уровня настроек. Настройки проекта лежат в папке .vscode рядом с кодом и действуют на всех, кто откроет этот репозиторий. Настройки пользователя действуют на все проекты этого компьютера и в репозиторий не попадают.

УровеньФайлКогда применять
Проект.vscode/settings.json в корне репозиторияПрограмма проверки и момент запуска — общие для команды
Пользователь %APPDATA%\Code\User\settings.json ~/Library/Application Support/Code/User/settings.json ~/.config/Code/User/settings.json Личные привычки: тема, шрифт, сочетания клавиш

Оба файла открываются через палитру команд: Preferences: Open Workspace Settings (JSON) для проекта и Preferences: Open User Settings (JSON) для пользователя. Папку .vscode держат в репозитории: файл настроек проекта — часть договорённостей команды.

§8Проверка в запросе на слияние

Путь пропущенного комментария

1 · Код Функция дописана, комментарий забыт. программа собирается
2 · Редактор После сохранения revive пишет предупреждение в панель Problems. видно сразу
3 · Терминал revive ./... печатает файл, строку и имя без комментария. перед коммитом
4 · Запрос на слияние Та же команда с -set_exit_status выполняется на стороне репозитория и отмечает проверку непройденной. до разбора работы

Шаги 2–4 выполняет одна и та же программа с настройками по умолчанию, поэтому редактор и проверка репозитория показывают одинаковые замечания.

§9Мини-практика: десять минут

  1. Во втором архиве создайте файл .vscode/settings.json с двумя строками из §5. Если расширение предложит установить revive, согласитесь.
  2. Откройте internal/utils/formatter.go, сохраните его и посмотрите замечания в панели Problems.
  3. Напишите комментарий над FormatKopeks, начиная с имени, которое подскажет gopls после // Form. Сохраните файл: одно замечание должно пропасть.
  4. Создайте сниппет из §3 и вставьте им комментарий над FormatTitle.
  5. Добавьте файл internal/utils/doc.go с комментарием пакета. Сохраните — пропадёт замечание should have a package comment.

§10Частые вопросы

Обычно думаютЕсли revive молчит, документация в порядке.
На самом делеrevive проверяет, что комментарий есть и начинается с имени. Верность описания по смыслу и соответствие поведению функции он не проверяет: это делает человек на разборе запроса на слияние.
Обычно думаютЗамечание revive можно убрать, переименовав функцию со строчной буквы.
На самом делеПереименование убирает имя из интерфейса пакета, и все вызовы из других пакетов перестанут собираться. Так поступают только с именами, которые и не должны быть экспортированы.
Обычно думаютНастройки редактора у каждого свои, в репозиторий их класть не нужно.
На самом делеПрограмма проверки и момент её запуска — договорённость команды, и хранится она в .vscode/settings.json внутри репозитория. Личные настройки остаются в настройках пользователя.

§11Проверьте себя

Почему для Go нет генератора заготовок комментариев, как autoDocstring для Python?

В комментарии Go нет разделов, которые можно заполнить из подписи: параметры и ошибки описывают предложениями. Заготовка свелась бы к имени функции, а его gopls подсказывает при наборе после //.

Какие две строки в .vscode/settings.json включают revive в редакторе?

"go.lintTool": "revive" — какой программой проверять, и "go.lintOnSave": "package" — проверять весь пакет при сохранении файла.

Что означает exported function NormalizeName should have comment or be unexported?

У экспортируемой функции NormalizeName нет комментария документации. Исправление — добавить комментарий вплотную над func, начиная с имени.

Комментарий есть, а revive пишет should be of the form "TodayLabel ...". Что не так?

Комментарий начинается не с имени функции. Первым словом должно стоять TodayLabel.

Зачем в проверках запроса на слияние флаг -set_exit_status?

Без него revive завершается с кодом 0 даже при замечаниях, и проверка считается пройденной. С флагом код завершения — 1, и шаг отмечается непройденным.

Почему неэкспортируемая squashSpaces не попала в замечания?

Правило exported проверяет только имена с заглавной буквы — те, что видны из других пакетов. Для служебных имён комментарий по правилу курса необязателен.

Итог главы

Расширение Go без настроек показывает комментарий документации в подсказке, подсказывает имя объявления в начале комментария и выравнивает разметку при сохранении. Генератора заготовок, как autoDocstring в Python, для Go нет: разделов в комментарии нет, и текст пишут сразу; строение подробного комментария можно держать сниппетом. Пропущенные комментарии и комментарии, которые начинаются не с имени, находит revive — в терминале, в редакторе при сохранении после двух строк в .vscode/settings.json и в проверках запроса на слияние с флагом -set_exit_status.
