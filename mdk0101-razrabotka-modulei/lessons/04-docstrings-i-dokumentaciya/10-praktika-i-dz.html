§1Работа на паре: чужой модуль

Берётся проект «Отчёт кафе» в том виде, каким он стал после практики в главе 4.4: аннотации расставлены, описаний нет ни одного. Если практика сделана, работа продолжается в своей папке; если нет — во втором архиве. Задача: задокументировать пакет app/ целиком и довести проверку Ruff до чистого вывода.

Тела функций в проекте писал не студент, и для этой работы это полезно. В своём коде описание пишется по памяти, и пропущенное условие заметно не сразу. В чужом коде приходится открывать тело функции, чтобы выяснить единицы измерения суммы, поведение на пустом списке и порядок значений в возвращаемой паре. Эти сведения и переносят в докстринг.

§2Порядок выполнения

  1. Откройте в VS Code свою папку после главы 4.4 или распакованный второй архив.
  2. Создайте окружение и установите зависимости: python3 -m venv .venv, затем .venv/bin/pip install -r requirements.txt. Ruff, mypy и pytest перечислены в requirements.txt.
  3. Запустите проект: .venv/bin/python main.py. Отчёт должен напечататься — дальше это поведение менять нельзя.
  4. Запустите тесты и проверку типов: .venv/bin/python -m pytest -q — проходят двенадцать, .venv/bin/mypy app — Success. Так подтверждается, что работа начинается с того места, где закончилась первая часть темы.
  5. Откройте .vscode/settings.json: формат докстрингов google в нём уже задан, как в главе 4.9. Если параметра нет, добавьте его.
  6. Проверьте, что в pyproject.toml включены набор "D" и конвенция google. Запустите .venv/bin/ruff check app --output-format=concise и сохраните вывод: это перечень мест, которые предстоит закрыть. В стартовом архиве их 33.
  7. Задокументируйте модули: первой строкой каждого файла — за что он отвечает и чего в нём нет.
  8. Задокументируйте публичные функции. Для каждой найдите близкий случай из главы 4.8 и держите его рядом.
  9. Отдельно пройдите по функциям, которые возбуждают исключения, пишут файлы или меняют переданный объект: добавьте разделы Raises: и Note:.
  10. Добавьте докстринг пакета в app/__init__.py с перечнем вложенных пакетов и точкой входа.
  11. Запускайте ruff check app после каждых двух-трёх функций, пока вывод не станет All checks passed!.
  12. Выполните python -c "import app.services.orders as m; help(m)" и прочитайте получившуюся справку подряд. Места, где описание непонятно без кода, перепишите.
На полях: проверка чтением справки

Вывод help() — та же документация без вёрстки. Если по ней вызвать функцию нельзя и приходится открывать исходник, описание неполное. При чтении докстрингов прямо в файле рядом виден код, и пропущенное условие восполняется по нему незаметно для самого читателя; в выводе help() кода нет, поэтому пропуск виден.

§4Домашняя работа: lesson_04

В личном репозитории дисциплины создайте папку lesson_04. Папки lesson_01, lesson_02 и lesson_03 не изменяйте.

Основа работы — ваш проект Student Tools из домашнего задания темы 02: средняя, минимальная и максимальная оценка, пакеты, тесты, README. Скопируйте его в lesson_04 и добавьте к нему две функции, чтобы в проекте оказались случаи разного вида:

Что добавитьТребованияБлизкий случай
save_report в новом модуле app/services/report_file.py Записывает готовый отчёт в текстовый файл в кодировке UTF-8, возвращает число записанных строк, существующий файл перезаписывает Случай 8 главы 4.8
grade_bounds в app/services/calculator.py Возвращает пару «минимум, максимум», на пустом списке возбуждает ValueError Случай 7 главы 4.8

Обе функции должны вызываться из main.py и быть покрыты тестами: обычный список и пустой список для расчёта, запись в существующий и в новый файл для отчёта.

Работа делается в два шага, как тема. Сначала весь проект получает аннотации типов по порядку из главы 4.4, и mypy app отвечает Success. Затем пишутся докстринги по правилам глав 4.5–4.9.

§6Требования к аннотациям и докстрингам

В аннотациях проекта

У каждой функцииТипы всех параметров, кроме self, и тип результата; у функций без результата — -> None.
Точные типы коллекцийlist[int], tuple[int, int], dict[str, int] — с типом содержимого, без голых list и dict.
Без Any и подавленийНи Any, ни # type: ignore: каждое замечание mypy исправлено аннотацией.

В каждом докстринге проекта

Первая строкаОдно предложение о действии, с точкой, в форме «Считает…», «Возвращает…», «Записывает…» — одинаково во всём проекте.
Типы не повторяютсяТипы указаны аннотациями в подписи; в разделе Args: их дублировать не нужно.
Ограничения указаныДопустимые значения оценок, требование непустого списка, существование папки для файла.
Единицы измерения указаныЧисло знаков после запятой, кодировка файла, порядок значений в паре.
Исключения перечисленыКласс ошибки и условие, при котором функция её возбуждает.
Побочные действия описаныПерезапись файла, изменение переданного объекта.
Пересказа тела нетОписание не перечисляет вызовы внутри функции построчно.

§7Проверка перед сдачей

  1. Скачайте свою работу из репозитория в отдельную папку, создайте новое окружение и установите зависимости.
  2. Запустите проект: результат должен совпадать с описанным в README.
  3. Выполните python -m pytest -v: проходят все тесты, их не меньше семи.
  4. Выполните mypy app: вывод Success: no issues found.
  5. Выполните ruff check app: вывод All checks passed!.
  6. Выполните поиск по проекту по строкам _summary_ и _description_: совпадений быть не должно.
  7. Откройте docs/help.txt и прочитайте подряд. По каждой функции должно быть понятно, что передавать и что получится.
  8. Проверьте, что в репозиторий не попали .venv/, __pycache__/ и файл отчёта, созданный при запуске.

Максимум — 10 баллов. Работа с заготовками _description_ в коде, с Any или # type: ignore вместо аннотаций и работа, в которой описание расходится с поведением функции, возвращаются на доработку.

§9Порядок сдачи

  1. Создайте задачу в своём репозитории с названием работы.
  2. Создайте ветку lesson-04-docstrings и работайте в ней.
  3. Оформите запрос на слияние в main: в описании укажите выбранный формат, команду проверки и её вывод.
  4. Пришлите ссылку на запрос на слияние.
  5. Замечания исправляйте в той же ветке: запрос обновится сам.

Проверка ruff check запускается и на стороне репозитория, поэтому её вывод в запросе виден до разбора работы.

§10Что будет в следующей теме

Докстринги написаны, проверка проходит, справка читается в терминале. Следующий шаг — собрать из этих же докстрингов сайт документации: страницы с оглавлением, перечнем модулей и поиском. Этим занимается Sphinx.

В следующей теме разбираются запуск sphinx-quickstart и состав созданных папок, настройка conf.py с указанием путей к исходникам, расширения autodoc и napoleon, файлы .rst и директива automodule, сборка одной командой, команда sphinx-apidoc для документирования каталога целиком, темы оформления и публикация готового сайта через GitHub Pages. Материал этой темы там становится входными данными: сайт собирается из докстрингов, которые вы сейчас написали.
