§1Работа на паре: чужой модуль

Берётся эталонный архив первого практикума темы 03 — отчёт кафе. Код в нём рабочий и разложен по пакетам, докстрингов в нём нет. Задача: задокументировать пакет app/ целиком и включить проверку.

Работа над чужим кодом выбрана намеренно. В своём коде описание пишется по памяти, и пропуск заметен не сразу. В чужом видно, каких сведений не хватает: приходится читать тело функции, чтобы понять единицы измерения суммы, поведение на пустом списке и порядок значений в возвращаемой паре. Ровно эти сведения и попадают в докстринг.

Что нужно на пареОткуда взять
Архив с проектомСтраница практикума темы 03, первая работа, эталонный архив
Окружение .venv с установленным Ruffpip install ruff после создания окружения

§2Порядок выполнения

  1. Распакуйте архив, создайте окружение, установите зависимости и Ruff, запустите проект и убедитесь, что отчёт печатается.
  2. Создайте .vscode/settings.json с форматом google по образцу из главы 4.5.
  3. Добавьте в pyproject.toml разделы с набором "D" и конвенцией google. Запустите ruff check app и сохраните вывод: это перечень мест, которые предстоит закрыть.
  4. Задокументируйте модули: первой строкой каждого файла — за что он отвечает и чего в нём нет.
  5. Задокументируйте публичные функции. Для каждой найдите близкий случай из главы 4.4 и держите его рядом.
  6. Отдельно пройдите по функциям, которые возбуждают исключения, пишут файлы или меняют переданный объект: добавьте разделы Raises: и Note:.
  7. Добавьте докстринг пакета в app/__init__.py с перечнем вложенных пакетов и точкой входа.
  8. Запускайте ruff check app после каждых двух-трёх функций, пока вывод не станет All checks passed!.
  9. Выполните python -c "import app.services.orders as m; help(m)" и прочитайте получившуюся справку подряд. Места, где описание непонятно без кода, перепишите.
На полях: проверка чтением справки

Вывод help() — это та же документация, только без вёрстки. Если по ней вызвать функцию нельзя и приходится открывать исходник, описание неполное. Такая проверка занимает минуту и находит больше, чем перечитывание докстрингов в файле, где рядом виден код.

§4Домашняя работа: lesson_04

В личном репозитории дисциплины создайте папку lesson_04. Папки lesson_01, lesson_02 и lesson_03 не изменяйте.

Основа работы — ваш проект Student Tools из домашнего задания темы 02: средняя, минимальная и максимальная оценка, пакеты, тесты, README. Скопируйте его в lesson_04 и добавьте к нему две функции, чтобы в проекте оказались случаи разного вида:

Что добавитьТребованияБлизкий случай
save_report в новом модуле app/services/report_file.py Записывает готовый отчёт в текстовый файл в кодировке UTF-8, возвращает число записанных строк, существующий файл перезаписывает Случай 8 главы 4.4
grade_bounds в app/services/calculator.py Возвращает пару «минимум, максимум», на пустом списке возбуждает ValueError Случай 7 главы 4.4

Обе функции должны вызываться из main.py и быть покрыты тестами: обычный список и пустой список для расчёта, запись в существующий и в новый файл для отчёта.

§6Требования к докстрингам

В каждом докстринге проекта

Первая строкаОдно предложение о действии, с точкой, в форме «Считает…», «Возвращает…», «Записывает…» — одинаково во всём проекте.
Типы не повторяютсяТипы указаны аннотациями в подписи; в разделе Args: их дублировать не нужно.
Ограничения указаныДопустимые значения оценок, требование непустого списка, существование папки для файла.
Единицы измерения указаныЧисло знаков после запятой, кодировка файла, порядок значений в паре.
Исключения перечисленыКласс ошибки и условие, при котором функция её возбуждает.
Побочные действия описаныПерезапись файла, изменение переданного объекта.
Пересказа тела нетОписание не перечисляет вызовы внутри функции построчно.

§7Проверка перед сдачей

  1. Скачайте свою работу из репозитория в отдельную папку, создайте новое окружение и установите зависимости.
  2. Запустите проект: результат должен совпадать с описанным в README.
  3. Выполните python -m pytest -v: проходят все тесты, их не меньше семи.
  4. Выполните ruff check app: вывод All checks passed!.
  5. Выполните поиск по проекту по строкам _summary_ и _description_: совпадений быть не должно.
  6. Откройте docs/help.txt и прочитайте подряд. По каждой функции должно быть понятно, что передавать и что получится.
  7. Проверьте, что в репозиторий не попали .venv/, __pycache__/ и файл отчёта, созданный при запуске.

Максимум — 10 баллов. Работа с заготовками _description_ в коде и работа, в которой описание расходится с поведением функции, возвращаются на доработку.

§9Порядок сдачи

  1. Создайте задачу в своём репозитории с названием работы.
  2. Создайте ветку lesson-04-docstrings и работайте в ней.
  3. Оформите запрос на слияние в main: в описании укажите выбранный формат, команду проверки и её вывод.
  4. Пришлите ссылку на запрос на слияние.
  5. Замечания исправляйте в той же ветке: запрос обновится сам.

Проверка ruff check запускается и на стороне репозитория, поэтому её вывод в запросе виден до разбора работы.

§10Что будет в следующей теме

Докстринги написаны, проверка проходит, справка читается в терминале. Следующий шаг — собрать из этих же докстрингов сайт документации: страницы с оглавлением, перечнем модулей и поиском. Этим занимается Sphinx.

В следующей теме разбираются запуск sphinx-quickstart и состав созданных папок, настройка conf.py с указанием путей к исходникам, расширения autodoc и napoleon, файлы .rst и директива automodule, сборка одной командой, команда sphinx-apidoc для документирования каталога целиком, темы оформления и публикация готового сайта через GitHub Pages. Материал этой темы там становится входными данными: сайт собирается из докстрингов, которые вы сейчас написали.

Итог главы

Работа на паре идёт на чужом рабочем коде без докстрингов: так видно, каких сведений в коде не хватает. Порядок один и тот же — настроить формат и проверку, описать модули, затем публичные функции по образцам главы 4.4, отдельно пройти по исключениям и побочным действиям, довести ruff check до чистого вывода и прочитать получившуюся справку подряд. Домашняя работа делается в папке lesson_04 личного репозитория: проект темы 02 с двумя новыми функциями, докстринги во всём пакете, настроенная проверка, тесты, дополненный README и сохранённый вывод справки. Сдача идёт через задачу, ветку и запрос на слияние. Следующая тема собирает из этих докстрингов сайт документации на Sphinx.
