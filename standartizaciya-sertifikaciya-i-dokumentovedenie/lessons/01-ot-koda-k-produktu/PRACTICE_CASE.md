# Meeting Room Booking API — материалы для аудита

Вы принимаете проект у команды разработки. Решите, можно ли передать его следующей команде.
Это учебный кейс: запуск backend не требуется. Проверяются полнота переданных сведений
и возможность подтвердить готовность. Слова разработчика не заменяют протокол испытаний.

## Что заявляет команда

- REST API работает, PostgreSQL подключён.
- Есть авторизация.
- Можно создавать комнаты и бронировать их.
- GET /rooms возвращает список комнат.
- POST /rooms создаёт комнату.
- POST /bookings создаёт бронирование.

## Что передано

```text
booking-service/
├── src/
│   └── main.py
├── .env
└── database.sql
```

Содержимое файлов и секреты в рамках кейса не выдаются.

## Что известно дополнительно

1. Инструкции запуска нет.
2. Версия Python нигде не указана.
3. Пароли находятся в .env, но .env.example отсутствует.
4. Документации API нет.
5. Неизвестно, какие функции заказчик должен проверить.
6. Требования находятся в переписке Telegram.
7. Структура базы данных не описана.
8. Критериев приёмки нет.

## Пожелания из переписки

> Сервис должен быть удобным и быстро работать. Нужна нормальная авторизация.
> Пользователь должен видеть свободные комнаты. Бронирование должно работать без проблем.

## Задание

Создайте `booking-service/docs/handoff_audit.md` по шаблону из урока.
Заполните пять разделов: требования, документация, проверка соответствия, качество, итог.

Для замечания укажите конкретный пробел, его влияние на передачу и способ устранения
или проверки. Предлагаемые пороги обозначайте как предложения для согласования.
Не выдавайте отсутствие результатов тестирования за доказательство ошибки в коде.
Если данных не хватает, пишите «не проверено» и перечисляйте нужные доказательства.

В итоге оставьте один статус: `READY` или `NOT READY`, с обоснованием.

## Ритм работы: 15 минут

- 3 минуты: изучить кейс и перечислить пробелы.
- 8 минут: заполнить пять разделов аудита.
- 4 минуты: проверить конкретность замечаний и сформулировать решение.

## Сдаваемый результат

Один Markdown-файл: `docs/handoff_audit.md`. На обсуждении покажите одно требование,
способ его проверки и основание вашего решения о передаче.
