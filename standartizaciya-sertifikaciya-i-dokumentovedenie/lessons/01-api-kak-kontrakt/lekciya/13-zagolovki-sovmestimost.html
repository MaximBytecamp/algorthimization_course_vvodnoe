104Совместимость каждая компания определяет сама

Одно и то же изменение — новое поле в ответе — GitHub считает совместимым, а Azure нет.

В списке совместимых изменений GitHub есть «Adding a response field» — добавление поля в ответ.

Поэтому политика совместимости записывается явно. В учебном проекте принято правило GitHub, и клиенты обязаны игнорировать неизвестные поля: docs/VERSIONING.md. Список breaking changes GitHub разобран на слайде 69.

106Deprecation и Sunset в каждом ответе

Пометку deprecated в OpenAPI увидит тот, кто читает документацию. Заголовок в ответе увидит программа, которая всё ещё вызывает устаревшую операцию.

настоящий ответ учебного API
GET /api/v1/tickets/open?limit=1

HTTP/1.1 200
deprecation: @1789516800
sunset: Mon, 01 Mar 2027 00:00:00 GMT
ЗаголовокДокументСтатус
DeprecationRFC 9745 ↗Standards Track
SunsetRFC 8594 ↗Informational

107429: одинаковое имя заголовка — разный смысл

Код 429 и Retry-After определены в RFC. Заголовки X-RateLimit-* стандартом не являются, и компании понимают их по-разному.

Стандарт в работе — draft-ietf-httpapi-ratelimit-headers ↗, активный черновик, версия 11. Он вводит заголовки RateLimit и RateLimit-Policy.

настоящий ответ учебного API
POST /api/v1/tickets   # третий запрос при лимите 2 в минуту

HTTP/1.1 429
retry-after: 60
x-ratelimit-limit: 2
x-ratelimit-remaining: 0
x-ratelimit-reset: 60
content-type: application/problem+json

{
  "type": ".../problems/http-429",
  "title": "Too many requests",
  "status": 429,
  "detail": "Write limit of 2 requests per minute exceeded"
}
Доказательство: как GitHub описывает x-ratelimit-reset

108ETag и If-Match: не потерять чужую правку

Два оператора открыли одно обращение. Первый закрыл его, второй через минуту меняет описание по старой копии. Условный запрос не даёт второму затереть изменение первого.

КтоСила правила
Zalando, правило 182 ↗MAY
Azure ↗DO — поддерживать If-Match и If-None-Match, возвращать ETag
GitHub ↗большинство endpoints отдают etag; 304 не расходует лимит
1. копия не изменилась — тело не передаётся
GET /api/v1/tickets/a8d04cb9-…
If-None-Match: "4fec2a976840743a"

HTTP/1.1 304
etag: "4fec2a976840743a"
2. обращение уже изменили — сервер отказывает
PATCH /api/v1/tickets/a8d04cb9-…
If-Match: "4fec2a976840743a"      # версия до чужой правки

HTTP/1.1 412
content-type: application/problem+json

{
  "title": "Precondition failed",
  "detail": "Ticket was changed after the version in If-Match was read"
}

109Idempotency-Key: распространённая практика без стандарта

POST не идемпотентен. Если ответ потерялся в сети и клиент повторил запрос, появится второе обращение. Ключ идемпотентности позволяет серверу узнать повтор.

настоящие ответы учебного API, сокращено
POST /api/v1/tickets  Idempotency-Key: 8e03978e-…  {"title": "Не работает VPN"}
HTTP/1.1 201   id: 6dfeb4e3-…

POST /api/v1/tickets  Idempotency-Key: 8e03978e-…  {"title": "Не работает VPN"}
HTTP/1.1 201   id: 6dfeb4e3-…   # тот же id, обращений по-прежнему 4

POST /api/v1/tickets  Idempotency-Key: 8e03978e-…  {"title": "Не работает почта"}
HTTP/1.1 422   "Idempotency-Key was already used with a different request body"

Длина ключа и срок хранения взяты из Stripe и Zalando, правило 230 ↗, код 422 — из черновика IETF.

110Идентификатор запроса: имя выбирает компания

Одна операция проходит через клиент, gateway и сервис. Общий идентификатор позволяет найти её записи во всех логах. Стандартного имени у этого заголовка нет.

КтоЗаголовок
Zalando, правило 233 ↗X-Flow-ID
Azure ↗x-ms-client-request-id
Учебный проектX-Request-Id
клиент передал свой идентификатор
GET /api/v1/tickets/a8d04cb9-…
X-Request-Id: support-case-1842

HTTP/1.1 200
x-request-id: support-case-1842
значение не прошло проверку формата (тест test_unsafe_request_id_is_replaced)
GET /api/v1/tickets
X-Request-Id: bad value; drop table

HTTP/1.1 200
x-request-id: 3c1f…            # UUID сервера
Доказательство: правило Zalando 233

111CORS: заголовок пришёл, а скрипт его не видит

Браузерный клиент на другом домене получает от сервера ETag и Location, но JavaScript прочитает их, только если сервер явно разрешил.

app/main.py (фрагмент)
app.add_middleware(
    CORSMiddleware,
    allow_origins=CORS_ORIGINS,
    expose_headers=[
        "ETag", "Location", "X-Request-Id", "Retry-After",
        "Deprecation", "Sunset",
        "X-RateLimit-Limit", "X-RateLimit-Remaining", "X-RateLimit-Reset",
    ],
)
настоящий ответ учебного API
GET /api/v1/tickets/open
Origin: http://localhost:5173

HTTP/1.1 200
access-control-allow-origin: http://localhost:5173
access-control-expose-headers: ETag, Location, X-Request-Id, Retry-After, Deprecation, Sunset, X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset

Добавили в контракт новый заголовок ответа — добавьте его в expose_headers, иначе браузерный клиент его не получит.

112OAuth 2.0 описывают вместе с сервером авторизации

OpenAPI позволяет описать OAuth 2.0 со схемами authorizationCode и clientCredentials. Но схема в контракте — обещание клиенту, и обещать можно только то, что работает.

Что сравниваемУчебный стендProduction
Кто выдаёт токентокены заданы переменными окружениясервер авторизации по OAuth 2.0 / OpenID Connect
Схема в OpenAPIBearerAuth: type: http, scheme: bearertype: oauth2 с flows и scopes
Что проверяет сервиссовпадение строки токенаподпись, срок действия, scopes

OpenAPI 3.2.0, OAuth Flows Object ↗ описывает адреса авторизации и выдачи токена. Zalando, правило 104 ↗ требует защищать все endpoints.

Если описать в учебном контракте oauth2 без сервера авторизации, Swagger UI покажет кнопку входа, которая никуда не ведёт. Такое описание нарушает главное свойство контракта: он должен совпадать с поведением API.

Схему OAuth 2.0 добавляют в тот же pull request, что и подключение сервера авторизации.

## [1.1.0] - 2026-09-16

### Added

- Заголовок X-Request-Id в каждом ответе.
- ETag, 304 Not Modified на совпавший If-None-Match.

- GET /api/v1/tickets/open — используйте GET /api/v1/tickets?status=open.
