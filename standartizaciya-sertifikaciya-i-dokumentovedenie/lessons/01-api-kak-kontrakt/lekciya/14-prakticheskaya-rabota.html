116Не копируем Service Desk без изменений

В практической работе вы выбираете собственную предметную область и строите контракт для неё.

Например: Books, Events, Cinema, Warehouse, Delivery, Games, Pets, Music, Reservations.

После выбора необходимо:

  1. определить ресурсы;
  2. спроектировать URI;
  3. выбрать HTTP methods;
  4. определить request/response schemas;
  5. определить status codes;
  6. создать собственный Style Guide;
  7. реализовать API;
  8. проверить OpenAPI;
  9. оформить документацию.
DOMAIN→RESOURCES→CONTRACT→IMPLEMENTATION→VALIDATION

117Контракт является частью repository

Изменение контракта оформляется так же, как изменение кода. Git заново не изучаем.

  1. Save
  2. Source Control
  3. Commit
  4. Push
  5. GitHub
  6. GitHub Actions

Сообщение commit должно описывать изменение контракта:

документ
docs(api): define ticket error contract
новая возможность
feat(api): add ticket pagination

Перед commit выполните python scripts/export_openapi.py: иначе CI найдёт расхождение openapi/openapi.json с кодом.

118Диагностика стандарта

Если CI не проходит, двигайтесь от сообщения об ошибке к правилу, а от правила к файлу.

  1. какой именно test или шаг упал;
  2. какой endpoint указан в сообщении;
  3. существует ли operationId;
  4. определён ли success response;
  5. соответствует ли response_model возвращаемым данным;
  6. обновлена ли OpenAPI schema в openapi/;
  7. не нашёл ли oasdiff breaking change в job breaking-changes;
  8. обновлён ли CHANGELOG;
  9. сохранён ли файл;
  10. отправлен ли новый commit.
  1. CI FAIL
  2. RULE
  3. FILE
  4. CONTRACT
  5. FIX
пример сообщения
FAILED tests/test_contract.py::test_every_operation_has_operation_id
AssertionError: GET /api/v1/tickets/{ticket_id} has no operationId

120Проверяем понимание, а не память

Студент должен своими словами объяснить ответы на эти вопросы.

  1. Почему REST и HTTP — не одно и то же?
  2. Почему Swagger и OpenAPI — не одно и то же?
  3. Почему GET /deleteUser является плохим контрактом?
  4. Почему POST и PUT имеют разную семантику?
  5. Почему 401 и 403 нельзя считать одинаковыми?
  6. Почему OpenAPI version и API version — разные вещи?
  7. Что делает breaking change опасным?
  8. Зачем нужен operationId?
  9. Почему Problem Details лучше произвольного JSON?
  10. Зачем API Style Guide, если уже существует OpenAPI?
  11. Что проверяет Spectral?
  12. Почему успешные тесты приложения ещё не гарантируют качественный API contract?
