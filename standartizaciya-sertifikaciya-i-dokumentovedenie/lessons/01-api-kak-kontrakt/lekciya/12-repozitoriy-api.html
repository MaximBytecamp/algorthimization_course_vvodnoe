95Один файл — разные решения компаний

Репозиторий API содержит не только код. Шаблоны pull request, формы issue, владельцы кода, политика безопасности и журнал изменений есть у всех крупных проектов, но каждая компания устраивает их по-своему.

ФайлЗачем нуженКак устроен у других
.github/PULL_REQUEST_TEMPLATE.mdчек-лист изменения контрактаKubernetes ↗ · OpenAPI Initiative ↗ · GitHub Docs ↗ · Azure ↗
.github/ISSUE_TEMPLATE/*.ymlформы с обязательными полямиAzure ↗ · Kubernetes ↗ · Stripe ↗
.github/CODEOWNERSкто утверждает измененияOpenAPI Initiative ↗ · Azure ↗ · Kubernetes OWNERS ↗
SECURITY.mdкак сообщить об уязвимостиAzure ↗ · VS Code ↗ · Kubernetes ↗
CHANGELOG.mdистория изменений для потребителейStripe ↗ · Kubernetes ↗
.github/dependabot.ymlобновление зависимостейOpenAPI Initiative ↗ · GitHub Docs ↗ · FastAPI ↗

На следующих слайдах у каждого файла есть цитата из документации GitHub или стандарта в оригинале, перевод и настоящие файлы компаний. Полный список с доказательствами лежит в учебном проекте: docs/STANDARDS.md.

Правила компании обязательны только внутри этой компании. Для учебного проекта выбрано подходящее, и каждый выбор записан вместе с источником.

96Шаблон pull request: что проверить до слияния

Шаблон подставляется в описание каждого нового pull request. Автору он напоминает, что проверить, а ревьюеру показывает, где искать ответ.

ПроектЧто требует шаблон
Kubernetes ↗тип PR командой /kind api-change или /kind deprecation, блок release note
OpenAPI Initiative ↗отметить, нужны ли изменения JSON Schema спецификации
GitHub Docs ↗ссылку на issue и проверку содержания экспертом
Azure ↗выбрать один из трёх шаблонов: data plane, control plane, SDK
Box ↗самопроверку и запуск yarn lint

Регистр в имени файла не важен: Kubernetes и GitHub Docs называют его PULL_REQUEST_TEMPLATE.md.

Как это сделано в учебном проекте
.github/PULL_REQUEST_TEMPLATE.md (фрагмент)
## Тип изменения

- [ ] совместимое изменение контракта (MINOR)
- [ ] исправление без изменения контракта (PATCH)
- [ ] **breaking change** (MAJOR)
- [ ] только документация

## Проверки

- [ ] контракт выгружен: python scripts/export_openapi.py
- [ ] изменение записано в CHANGELOG.md
- [ ] устаревающие элементы помечены deprecated: true

97Формы issue: обязательные поля вместо свободного текста

Issue form — YAML-файл, из которого GitHub строит форму с полями. Пока обязательное поле пустое, обращение не отправить.

ПроектФорматЧто спрашивает
Azure ↗YAML-формаобязательные «API Spec link» и «API Spec version»
Kubernetes ↗YAML-формачто произошло, что ожидали, как воспроизвести
Stripe Node SDK ↗YAML-формаописание, шаги, ожидаемое поведение
VS Code ↗Markdownсвободный текст по подсказкам

Из Azure в учебный проект взяты обязательные поля «версия API» и «операция», из Kubernetes — «что произошло / что ожидали».

98Кто утверждает изменения контракта

CODEOWNERS связывает файлы и папки с людьми или командами. GitHub сам запрашивает у них review, а защита ветки может сделать этот review обязательным.

.github/CODEOWNERS (фрагмент)
*                        @MaximBytecamp
/openapi/                @MaximBytecamp
/.spectral.yaml          @MaximBytecamp
/docs/API_STYLE_GUIDE.md @MaximBytecamp

В команде вместо имени указывают группу, например @org/api-reviewers. У Azure ↗ свои владельцы у спецификации каждого сервиса. Kubernetes использует другую систему: файлы OWNERS в папках читает бот Prow.

99Как сообщить об уязвимости

Уязвимость не обсуждают в публичном issue: пока её не исправили, описание помогает атакующему. SECURITY.md говорит, куда писать вместо этого.

ПроектВариант
Azure ↗полный стандартный текст Microsoft: не писать в issue, отправить отчёт в MSRC, перечень нужных сведений
VS Code ↗короткая версия того же блока Microsoft со ссылкой на общую политику
Kubernetes ↗файл SECURITY_CONTACTS: ответственные и ссылка на процесс
Учебный проектdocs/SECURITY.md: поддерживаемые версии, приватный отчёт через GitHub, что указать в отчёте

100Журнал изменений в разных масштабах

Keep a Changelog задаёт принципы, а форма журнала зависит от размера проекта.

ПроектКак устроен журнал
Stripe Node SDK ↗один файл, генерируется из фрагментов .change.md, у пунктов ссылки на PR
Kubernetes ↗папка CHANGELOG/, отдельный файл на каждую минорную версию

101Breaking change ловит CI, а не review

Переименованное поле легко пропустить в длинном diff. oasdiff сравнивает два файла OpenAPI и перечисляет изменения, которые сломают клиентов.

.github/workflows/ci.yml (фрагмент)
breaking-changes:
  if: github.event_name == 'pull_request'
  steps:
    - uses: actions/checkout@v5
    - run: git fetch --depth=1 origin ${{ github.base_ref }}
    - uses: oasdiff/oasdiff-action/breaking@v0.1.17
      with:
        base: "origin/${{ github.base_ref }}:openapi/openapi.yaml"
        revision: "HEAD:openapi/openapi.yaml"
        fail-on: ERR
Тот же результат при локальном запуске oasdiff
локальный запуск oasdiff: в ревизии поле title переименовано в subject
$ oasdiff breaking base.yaml revision.yaml --fail-on ERR
4 changes: 4 error, 0 warning, 0 info
error	[response-required-property-removed] at /specs/revision.yaml
	in API GET /api/v1/tickets
		removed the required property `items/items/title` from the response with the `200` status

error	[response-required-property-removed] at /specs/revision.yaml
	in API POST /api/v1/tickets
		removed the required property `title` from the response with the `201` status

# ещё две такие же ошибки: GET и PATCH /api/v1/tickets/{ticket_id}

Тесты в этом PR проходят: переименование согласовано во всём коде. Остановил слияние только oasdiff, а защита ветки main требует обе проверки. Открыть прогон ↗.

102Адрес в поле type должен открываться

Problem Details различает виды ошибок по адресу в поле type. Стандарт требует, чтобы по этому адресу была документация.

В версии 1.0.0 учебного проекта type указывал на example.edu, где страницы нет. В 1.1.0 скрипт scripts/build_docs.py собирает страницу для каждого кода ошибки, а workflow docs.yml публикует их на GitHub Pages вместе с ReDoc.

Документация опубликована: maximbytecamp.github.io/api-standard-template ↗, страница http-412 ↗.

103Правило без источника легко оспорить

В учебном проекте для каждого правила записано, откуда оно взято, насколько оно обязательно и как то же самое решили другие компании.

docs/STANDARDS.md (фрагмент)
## 9. Ограничение частоты запросов: 429 и Retry-After

**В проекте:** app/limits.py

**Источник:** RFC 6585, раздел 4, Standards Track.

> The response representations SHOULD include details
> explaining the condition, and MAY include a Retry-After
> header indicating how long to wait before making a new request.

Перевод: ответ SHOULD объяснять причину и MAY содержать
заголовок Retry-After ...

**Как это делают другие:** Zalando (правило 153), GitHub ...
