1API как публичный контракт программы

На этом занятии нас интересует не только серверный код. Мы рассматриваем API как контракт между двумя программами: что клиент вправе ожидать от сервера и как проверить, что сервер это выполняет.

Стандартизировать необходимо:

  • адреса ресурсов
  • HTTP-методы
  • параметры
  • структуру JSON
  • HTTP status codes
  • формат ошибок
  • версионирование
  • документацию
  • безопасность
  • правила изменения API
  • проверку соответствия этим правилам
  1. CLIENTклиентская программа
  2. API CONTRACTURL · METHOD · PARAMETERS · BODY · RESPONSE · ERRORS · VERSION
  3. SERVERреализация на FastAPI

2Что в этой теме означает «сертификация»

Для обычного REST API нет единого международного органа, который выдаёт разработчику сертификат «правильного API». Поэтому в рамках дисциплины мы разделяем два процесса.

процесс 1

Стандартизация

Создание набора правил, которым API должен соответствовать: как называть адреса, какие коды возвращать, как описывать ошибки.

процесс 2

Проверка соответствия

Доказательство того, что API эти правила действительно выполняет. Доказательство — результат проверки, а не мнение автора.

3Сегодня создаём новый учебный API

До этого занятия учебного API не существует. Мы создаём отдельный учебный стенд, а production-сервисы не изменяем.

Предметная область — Service Desk API, система регистрации обращений в службу поддержки. Сотрудник сообщает о проблеме, специалист меняет статус обращения, пока проблема не решена.
