§2Где все сходятся

Есть решения, которые совпадают у всех. Это и есть настоящая «общепринятая практика» — и отступать от неё стоит, только имея очень вескую причину.

Адрес — существительноеДействие выражается методом, а не именем пути. Ни один свод не предлагает /getTickets.единогласно
Код ответа описывает исход200 не возвращается вместо 201 или 404, ошибка не прячется в теле успешного ответа.единогласно
Единый формат ошибокФормат может быть свой, но он один на весь API и содержит машиночитаемый признак вида ошибки.единогласно
Версия объявлена явноГде именно — расходятся, но что версия должна быть видна клиенту, согласны все.единогласно
Совместимость определена письменноЧто считать поломкой, решает владелец API, но решение должно быть записано.единогласно
Описание машиночитаемоOpenAPI как формат контракта не оспаривает никто из пятерых.единогласно

§4Как выбирать между вариантами

  1. Посмотрите, кто ваши клиенты. Это решает больше всего: у публичного API и у трёх внутренних сервисов разные ответы почти на все спорные вопросы.
  2. Возьмите вариант, который дешевле поддерживать. Версия в пути видна в журналах; версия в заголовке не засоряет адреса. Любой выбор здесь — компромисс.
  3. Проверьте, чем будете проверять. Правило, которое нечем проверить, работать не будет — как бы солидно ни выглядел его источник.
  4. Запишите решение и отвергнутые варианты. ADR из главы 5.4. Через год вопрос зададут снова.
  5. Не смешивайте варианты в одном API. Часть операций с версией в пути, часть в заголовке — худший из возможных исходов.

§5Как ссылаться на источник

Ссылка на правило в своём стандарте должна выдержать два испытания: её можно открыть, и открывший увидит именно то, о чём речь.

Плохая ссылка
  • «как принято в индустрии»
  • «см. документацию Zalando»
  • ссылка на главную страницу свода
  • пересказ своими словами без цитаты
Хорошая ссылка
  • Zalando, правило 176 «MUST support problem JSON»
  • адрес с якорем на конкретное правило
  • цитата в оригинале
  • перевод под цитатой

Этому же правилу подчинён весь справочник: где приводится требование стандарта, рядом стоит английский оригинал, перевод и адрес источника. Не из педантизма — из практики: правило без проверяемого источника рано или поздно объявят выдумкой автора.

Проверяйте статус документа

У RFC он указан в начале: Standards Track, Informational, Experimental. У черновиков IETF бывает пометка «expired» — так случилось с Idempotency-Key из главы 4.3. Статус не запрещает пользоваться решением, но определяет, на что вы опираетесь: на стандарт или на сложившуюся практику.

§6Три уровня доказательности

УровеньЧто этоПримеры из справочника
СтандартRFC со статусом Standards TrackRFC 9110 (методы), RFC 9457 (ошибки), RFC 9745 (Deprecation)
Практика, описанная документомInformational RFC, черновик, спецификация вне IETFRFC 8594 (Sunset), Semantic Versioning, Keep a Changelog
Правила компанииСвод конкретной организацииZalando 176, GitHub API Versions, Azure Breaking changes

Уровни не ранжируют качество решения — они говорят, насколько широко оно согласовано. Отступить от правила компании можно, объяснив это внутри команды; отступить от Standards Track — значит перестать быть совместимым с чужими инструментами, и это уже разговор другого масштаба.

§8Частые ошибки

«В индустрии принято»По половине вопросов индустрия не сходится. Называйте конкретный источник.
Копировать чужой свод целикомПравила Zalando написаны под масштаб Zalando. Берут решения, а не объём.
Ссылка на главную страницу сводаЧитатель не найдёт нужное правило. Нужен адрес с якорем и номер.
Игнорировать статус документаЧерновик мог истечь, Informational не обязывает. Это влияет на то, как вы обосновываете решение.
Смешивать варианты в одном APIЧасть операций по одному правилу, часть по другому — хуже любого последовательного выбора.
Брать чужой свод и не адаптировать проверкиПравило без способа проверки не работает, из какого бы свода оно ни пришло.

§9Проверьте себя

  3. Почему расхождение между сводами Azure и Microsoft Graph — полезный аргумент в споре?
  4. Из чего состоит хорошая ссылка на правило чужого свода?
  5. Чем отличается отступление от Standards Track RFC от отступления от правила компании?
