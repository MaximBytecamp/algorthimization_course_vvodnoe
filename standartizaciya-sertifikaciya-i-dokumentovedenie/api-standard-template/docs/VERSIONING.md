# Политика версионирования

Источники правил и варианты у других компаний — [STANDARDS.md, разделы 5–8](STANDARDS.md#5-версия-контракта-semantic-versioning).

## Какие номера есть в проекте

| Номер | Где записан | Пример | Что означает |
|---|---|---|---|
| Версия спецификации OpenAPI | `openapi` в `openapi/openapi.json` | `3.1.0` | формат, которым описан контракт; выбирает FastAPI |
| Версия контракта | `info.version`, `app/main.py` | `1.1.0` | состояние публичного контракта по SemVer |
| Мажорная версия в пути | префикс маршрутов | `/api/v1` | с какой несовместимой редакцией работает клиент |
| Версия развёртывания | Git | `commit 4ab219…` | какой код сейчас запущен |

Эти номера меняются независимо. `openapi: 3.1.0` не означает, что API имеет версию 3.1.

## Semantic Versioning для `info.version`

- **MAJOR** — несовместимое изменение. Выпускается новым префиксом `/api/v2`.
- **MINOR** — совместимая новая функциональность.
- **PATCH** — совместимое исправление описания или поведения.

## Breaking changes

Компании определяют совместимость по-разному: GitHub считает добавление поля в ответ
совместимым, Azure — нет (цитаты в [STANDARDS.md, раздел 7](STANDARDS.md#7-что-считать-breaking-change-у-компаний-разные-ответы)).
В этом проекте принято правило GitHub, поэтому клиенты MUST игнорировать неизвестные поля ответа.

Несовместимыми считаются и допускаются только в новой мажорной версии:

- удаление или переименование endpoint;
- удаление или переименование поля ответа;
- изменение типа поля;
- добавление обязательного параметра или обязательного поля запроса;
- удаление значения из enum;
- ужесточение требований аутентификации или лимитов.

Проверка автоматическая: job `breaking-changes` в `.github/workflows/ci.yml` сравнивает
`openapi/openapi.yaml` в pull request с версией в `main` и падает при breaking change.

## Совместимые изменения

Допускаются в MINOR:

- новый endpoint;
- новый необязательный параметр или заголовок запроса;
- новое поле ответа;
- новый заголовок ответа.

## Deprecation

`ACTIVE → DEPRECATED → MIGRATION PERIOD → SUNSET → REMOVED`

1. Операция помечается `deprecated: true`, в описании указываются замена и дата отключения
   (Zalando, правило 187).
2. Каждый ответ устаревшей операции содержит заголовки (Zalando, правило 189):
   - `Deprecation: @<секунды Unix>` — когда операция признана устаревшей ([RFC 9745](https://www.rfc-editor.org/rfc/rfc9745.html));
   - `Sunset: <HTTP-date>` — когда она перестанет отвечать ([RFC 8594](https://www.rfc-editor.org/rfc/rfc8594.html)).
3. Изменение записывается в `CHANGELOG.md` в раздел **Deprecated**.
4. Период миграции — не меньше одного семестра учебного стенда.
5. Удаление выполняется только в следующей мажорной версии.

Пример в проекте — `GET /api/v1/tickets/open`:

```http
HTTP/1.1 200 OK
Deprecation: @1789516800
Sunset: Mon, 01 Mar 2027 00:00:00 GMT
```

Замена: `GET /api/v1/tickets?status=open`.
