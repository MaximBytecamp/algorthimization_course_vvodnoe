Стандарт репозитория студента

Единые правила для репозиториев, в которых студенты сдают работы по всем дисциплинам: структура папок, имена файлов, README, сообщения коммитов и получение новых материалов от преподавателя. Правила собраны по тому, как устроены популярные репозитории на GitHub и что в них смотрят при найме, и по документации GitHub.

Что даёт стандарт

  • Студенту не нужно заново разбираться в каждой дисциплине: папки, имена и порядок сдачи одинаковые на всех курсах.
  • Преподаватель проверяет работы по одному пути: homework/03-lists/task_02.py лежит там же у каждого студента.
  • Работодатель открывает репозиторий и за полминуты понимает, чей он, что в нём и как запустить код.
  • Новые задания каждый день переносятся в репозиторий студента, создавать его заново не нужно.

Что смотрит работодатель

Выводы из статей о найме начинающих разработчиков и из документации GitHub. Под каждым выводом — откуда он взят.

На проект — 30–60 секунд

Столько внимания достаётся репозиторию кандидата. Технический специалист не разбирается в коде, чтобы понять, что за проект: это должно быть видно из README.

Регулярность заметна

График активности показывает, насколько регулярно человек пишет код. BloomTech советует не меньше пяти дней с коммитами в неделю, лучший проект — первым среди закреплённых.

BloomTech →

Отсюда три решения стандарта. Репозиторий создаётся из шаблона кнопкой Use this template. Форк не подходит: коммиты в нём не попадают в график. Все работы идут в ветку main: это ветка по умолчанию. Почта коммитов — служебная …@users.noreply.github.com: она привязана к аккаунту и не раскрывает настоящий адрес.

Разделение по владельцу — основа стандарта. Студент и преподаватель никогда не правят один и тот же файл, поэтому обновление из шаблона проходит без конфликтов.

Сообщения коммитов

Формула: <папка> <номер>: <что сделано>. Первое слово совпадает с папкой, поэтому по истории видно, какая работа менялась.

ТакНе так
homework 01: задачи 1–3update
homework 01: исправлен вывод в задаче 2fix, fix2
problems 1.3: задачи 1–5файлы
exam 01: вариант 2, задачи 1–10кр
materials: обновление из шаблона курса (коммит бота)—

Все работы — в ветке main. Ветки и Pull Request используются только в дисциплинах, где их проходят; такая дисциплина пишет об этом в своём docs/SUBMIT.md.

Новые материалы без пересоздания

Репозиторий, созданный кнопкой Use this template, не связан с шаблоном общей историей: GitHub копирует файлы одним коммитом. Поэтому кнопки «подтянуть изменения шаблона» у такого репозитория нет.

СпособКак работаетПочему не подходит или подходит
Форк и кнопка Sync forkфорк помнит исходный репозиторий, GitHub предлагает забрать изменения одной кнопкойнет: коммиты в форке не попадают в график активности профиля
git merge --allow-unrelated-histories с шаблономстудент добавляет шаблон вторым адресом и сливает его ветку со своейнет: первое слияние даёт конфликт в каждом файле, который преподаватель изменил после создания копии; первокурснику их не разобрать
Готовое действие actions-template-syncпо расписанию открывает Pull Request с изменениями шаблонанет: каждому студенту нужно включить в настройках разрешение на Pull Request от Actions и сливать их; конфликты решаются в пользу шаблона, то есть могут затереть решение
Свой workflow с правилом владельцараз в сутки скачивает шаблон, заменяет файлы преподавателя, добавляет недостающие, не трогает остальное, делает коммит в mainда: от студента ничего не требуется, конфликтов нет, решения не перезаписываются

Как устроен выбранный способ

  1. Workflow в шаблоне

    Файл .github/workflows/update-materials.yml копируется студенту вместе с шаблоном и запускается каждый день в 06:00 по Москве и по кнопке Run workflow. Права: contents: write, этого хватает для коммита в свой репозиторий.

  2. Имя шаблона берётся из GitHub

    GitHub хранит, из какого шаблона создан репозиторий (поле template_repository). Workflow берёт имя оттуда, поэтому один и тот же файл подходит для всех дисциплин. В самом шаблоне workflow ничего не делает.

  3. Правило владельца

    Скрипт update_materials.py берётся из свежей копии шаблона, так что преподаватель может менять правило без участия студентов. Файлы преподавателя заменяются, недостающие файлы добавляются, остальные не трогаются, ничего не удаляется.

  4. Коммит от бота

    Изменения сохраняются коммитом materials: обновление из шаблона курса от github-actions[bot]. Студент забирает их на компьютер кнопкой Sync Changes.

Проверено 22.10.2026 на закрытом репозитории, созданном из python-start-template: изменённый студентом конспект заменён версией шаблона, удалённый homework/README.md возвращён, решение в exams/exam-01/task_01.py сохранено.

ОграничениеТокен GitHub Actions не может менять файлы в .github/workflows/. Если изменится файл workflow, студенты, создавшие репозиторий раньше, получат новую версию только вручную. Поэтому логика вынесена в скрипт, а workflow оставлен минимальным.

Для преподавателя

Выдать новую работу

  1. Строка в таблице

    В homework/README.md (или practice/, exams/) дописать строку: папка, задание, срок.

  2. Заготовка, если нужна

    Папка homework/NN-тема/ с README.md и пустыми task_NN.py. Студент получит её, только если у него ещё нет такой папки.

  3. Конспект и материалы

    lectures/…md и materials/…/ — по shared/REPO_TEMPLATES.md.

  4. Коммит и push в шаблон

    На следующее утро материалы будут у всех студентов.

Чего не делать

  • Не переименовывать и не удалять выданные файлы: у студентов старые останутся, а новые добавятся рядом.
  • Не менять заготовки после выдачи: у студента, который уже начал, они не обновятся. Исправление — в README.md папки вида работ или в docs/.
  • Не класть решения и ответы в шаблон: он открытый.
