1. Задача

Отдел поддержки работает в сервисе заявок helpdesk. Сборочный конвейер выложил на сервер версию 2.4.1 — каталог /tmp/helpdesk-release-2.4.1. Сейчас на сервере работает версия 2.3: предыдущий инженер запустил её вручную из своего домашнего каталога от своей учётной записи. Конфигурация и пароли лежат там же и открыты всем.

Задача — выложить 2.4.1 так, как принято на остальных серверах компании: программы, настройки и данные по стандарту FHS, служба работает от отдельной учётной записи, у каждой роли ровно те права, которые ей нужны.

2. Стенд

Копия сервера разворачивается в вашей виртуальной машине. Скачайте скрипты стенда и приёмки и разверните стенд:

cd ~/Downloads
wget https://algorthimization-course-vvodnoe.vercel.app/op05-operacionnye-sistemy-i-sredy/proekty/ekspluataciya-servera/materials/helpdesk-stand.sh
wget https://algorthimization-course-vvodnoe.vercel.app/op05-operacionnye-sistemy-i-sredy/proekty/ekspluataciya-servera/materials/helpdesk-acceptance.sh
sudo bash helpdesk-stand.sh

Стенд создаёт каталог релиза в /tmp и запускает версию 2.3 из домашнего каталога вашей учётной записи. Учётные записи команды, каталоги службы и правила sudo стенд удаляет — их создаёте вы.

Состав релиза

3. Требования

1. Учётные записи

  1. 1.1
    Служебная учётная запись helpdesk: системная (UID меньше 1000), без входа в систему, домашний каталог /var/lib/helpdesk.
  2. 1.2
    Разработчики ivanov и petrova — группа helpdesk-dev; поддержка smirnova — группа helpdesk-support. Каждому задан пароль.
  3. 1.3
    Никто из команды не состоит в группе sudo.
  4. 1.4
    Разработчики без пароля запускают от имени helpdesk только /usr/local/bin/helpdesk-ctl. Других команд через sudo им не разрешено. Правило — отдельный файл в /etc/sudoers.d, редактируется через visudo, права 440.

2. Размещение файлов

  1. 2.1
    Программы — /usr/local/bin; настройки и секреты — /etc/helpdesk; база — /var/lib/helpdesk; веб-интерфейс — /srv/helpdesk/static; журналы — /var/log/helpdesk; файл с PID службы — /run/helpdesk.
  2. 2.2
    После выкладки копия релиза из /tmp удалена.

3. Доступ

  1. 3.1
    Права выставлены по матрице доступа ниже. Права шире, чем в матрице, считаются ошибкой.
  2. 3.2
    Новые файлы, которые разработчики кладут в /srv/helpdesk/static, получают группу helpdesk-dev и доступны на изменение второму разработчику.
  3. 3.3
    Файлы, которые создаёт служба, недоступны группе на запись и закрыты для остальных: маска задаётся параметром UMASK в helpdesk.conf.

4. Служба

  1. 4.1
    Версия 2.3 остановлена.
  2. 4.2
    Версия 2.4.1 запущена командой helpdesk-ctl start от имени helpdesk. Если служба не стартует, helpdesk-ctl печатает причину — её нужно устранить, ослаблять права ради запуска нельзя.

4. Распределение работ в паре

  • Инженер 1 · учётные записи и sudoслужебная учётная запись, пользователи и группы, правило sudo, проверка правила от имени разработчика через sudo -u ivanov sudo -l.
  • Инженер 2 · размещение и правакаталоги по FHS, перенос файлов релиза, владельцы и права по матрице, общий каталог с setgid, маска службы.
  • Вместеостановка версии 2.3, запуск 2.4.1, приёмка, общий скрипт provision.sh.

5. Результат работы

В репозитории пары, кроме общих файлов:

provision.shскрипт, который на только что развёрнутом стенде выполняет всю выкладку. Проверка повторяемости: стенд заново, sudo bash provision.sh, приёмка — все пункты OK.
access-matrix.mdматрица доступа с фактическими правами: для каждого ресурса строка ls -ld или stat и команда, которой проверен доступ каждой роли.
runbook.mdжурнал работ: время, кто из пары, команда, результат. Ошибки и их исправление тоже записываются.
screenshots/отказ запуска службы и его причина; вывод приёмки со всеми OK.

6. Приёмка

Скрипт приёмки ничего не меняет, только проверяет сервер и печатает OK или FAIL по каждому пункту. Работа принята, когда на стенде, развёрнутом заново, после вашего решения все пункты OK. Требования, которые скрипт проверить не может, проверяет преподаватель по документам.

sudo bash ~/Downloads/helpdesk-acceptance.sh | tee acceptance.txt

Пункт FAIL — это подсказка, какое требование не выполнено. Подгонять сервер под скрипт в обход требований нельзя: при защите пара объясняет каждое действие из журнала.

7. Куда смотреть

Что изучить и чем себя проверить по каждой задаче. Сначала попробуйте разобраться сами, открывайте, когда застряли.

Осмотр сервера

Первые 10–15 минут ничего не меняйте. Изучите, что пришло в релизе, что уже работает на сервере и от чьего имени. Программы релиза — обычные скрипты: прочитайте их, прежде чем запускать.

Инструментыls -lR, less, pgrep -af, ps -o user,pid,cmd
